At about seven thousand lines, `InteractiveMode` is the largest file in the
project, and it is one class. It is the glue between three things: the
[AgentSession](/docs/src/core/agent-session.ts) that does the work, the terminal
UI built from components, and the user typing into an editor. It is created by
[main.ts](/docs/src/main.ts) only when both stdin and stdout are terminals.

The size comes from breadth rather than depth. Most of the file is small
private methods: one per slash command (`handleModelCommand`, `handleCloneCommand`
and so on), one per selector overlay, plus path formatting for the startup
resource listing, login flows, and extension UI plumbing. The control flow that
matters is short: construct, `init`, `run`, then react to editor submissions and
session events until shutdown. This walkthrough follows that spine, then the
pieces of state that cut across it: extension dialogs and overlays, logins, and
the program status reported to the terminal.

The visual pieces live in [components](/docs/src/modes/interactive/components/index.ts)
such as [assistant-message.ts](/docs/src/modes/interactive/components/assistant-message.ts)
and [tool-execution.ts](/docs/src/modes/interactive/components/tool-execution.ts),
while [chat-viewport.ts](/docs/src/modes/interactive/chat-viewport.ts) lays them out.
Whether pi is working, waiting for the user, done or failed is tracked by
[program-status-reporter.ts](/docs/src/modes/interactive/program-status-reporter.ts).

## !!steps What main hands in

`InteractiveModeOptions` is the startup context that `main` collected
and that the TUI has to surface once it exists. Diagnostics and warnings are
passed in as data rather than printed, because the terminal is not ready to
show them yet. The initial prompt and images come from `@file` arguments, the
extra messages from additional positional arguments, and `terminal` exists so
tests can substitute a fake.

```ts ! interactive-mode.ts
export interface InteractiveModeOptions {
	/** Providers that were migrated to auth.json (shows warning) */
	migratedProviders?: string[];
	/** Diagnostics collected before the interactive TUI was initialized. */
	startupDiagnostics?: AgentSessionRuntimeDiagnostic[];
	/** Warning message if session model couldn't be restored */
	modelFallbackMessage?: string;
	/** Cwd to trust after reload if it gained a .pi directory during this implicitly trusted session. */
	autoTrustOnReloadCwd?: string;
	/** Initial message to send on startup (can include @file content) */
	initialMessage?: string;
	/** Images to attach to the initial message */
	initialImages?: ImageContent[];
	/** Additional messages to send after the initial message */
	initialMessages?: string[];
```

## !!steps State held by one class

Fields fall into groups: the component tree (containers for header, chat,
pending messages, status, widgets, editor and footer), editor and selector
state, tracking maps for streaming output, and extension UI state. The
`pendingTools` map ties a tool call id to the component rendering it, which is
how a result arriving later finds its row.

Because the session can be replaced by `/new` or a switch, `session` is not a
field. It is a getter that reads `runtimeHost.session` each time.

```ts ! interactive-mode.ts
	// Streaming message tracking
	private streamingComponent: AssistantMessageComponent | undefined = undefined;
	private readonly entriesRenderedByBoundaryCompaction = new Set<string>();
	private streamingMessage: AssistantMessage | undefined = undefined;

	// Tool execution tracking: toolCallId -> component
	private pendingTools = new Map<string, ToolExecutionComponent>();
// ...
	// Convenience accessors
	// !mark(1:3)
	private get session(): AgentSession {
		return this.runtimeHost.session;
	}
	private get agent() {
		return this.session.agent;
	}
```

## !!steps The constructor wires the runtime hooks

Two callbacks are registered on the runtime. Before a session is invalidated,
`resetExtensionUI` removes everything the outgoing extensions put on screen:
stacked dialogs, overlays, widgets, custom editors, headers and footers. When a
new session is bound, the mode re-renders and re-applies the theme. This is the interactive
counterpart of `rebindSession` in [rpc-mode.ts](/docs/src/modes/rpc/rpc-mode.ts).

The renderer is created from the TUI mode setting, and `ui` is a reference that
looks the renderer up lazily so the mode can be swapped later.

```ts ! interactive-mode.ts
	constructor(runtimeHost: AgentSessionRuntime, options: InteractiveModeOptions = {}) {
		this.runtimeHost = runtimeHost;
		setCapabilityOverrides(this.settingsManager.getTerminalCapabilityOverrides());
		const tuiMode = options.tuiMode ?? this.settingsManager.getTuiMode();
		this.options = { ...options, tuiMode };
		this.autoTrustOnReloadCwd = options.autoTrustOnReloadCwd;
		this.runtimeHost.setBeforeSessionInvalidate(() => {
			this.resetExtensionUI();
		});
		this.runtimeHost.setRebindSession(async () => {
			await this.rebindCurrentSession({ renderBeforeBind: true });
			this.themeController.applyFromSettings();
		});
```

## !!steps init: a UI that accepts text before it is ready

`init` runs once. It mounts the containers, then installs a minimal set of
handlers: Ctrl+C, Ctrl+D, and a submit handler that only says startup is still
in progress and puts the text back. Typing is accepted but nothing is sent.

The UI is started before extensions are initialized, with a comment explaining
why: `session_start` handlers may open interactive dialogs. The first program
status (`idle`) is reported as soon as the terminal is running. The terminal
holds it until it has confirmed OSC 7501 support, so an early report is not lost.

```ts ! interactive-mode.ts
		// Accept text while startup completes, but only enable interrupt, exit, and submission feedback.
		this.defaultEditor.onAction("app.clear", () => this.handleCtrlC());
		this.defaultEditor.onCtrlD = () => this.handleCtrlD();
		this.defaultEditor.onSubmit = (text) => this.handleStartupSubmit(text);
		this.ui.setFocus(this.editor);

		// Start the UI before initializing extensions so session_start handlers can use interactive dialogs
		this.ui.start();
		this.isInitialized = true;
		// !mark
		this.programStatus.report();
		this.ensurePngTranscoder();

		this.themeController.applyFromSettings();
```

## !!steps init: tools, then real handlers, then extensions

Next `init` makes sure the `fd` and `rg` binaries exist, downloading them if
needed. They are awaited in parallel after the TUI is mounted, so a slow
download shows status instead of a frozen screen. Only after that are the real
key and submit handlers installed, which is the moment input starts working.

Then `rebindCurrentSession` initializes extensions and shows loaded resources,
and only after that are initial messages rendered, so resource listings appear
before the conversation.

```ts ! interactive-mode.ts
		const [fdPath] = await Promise.all([
			ensureTool("fd", (status) => this.showManagedToolStatus(status)),
			ensureTool("rg", (status) => this.showManagedToolStatus(status)),
		]);
		this.fdPath = fdPath;

		// Enable the remaining input handlers only after managed-tool setup completes.
		this.setupKeyHandlers();
		this.setupEditorSubmitHandler();
		this.ui.requestRender();

		// Initialize extensions first so resources are shown before messages
		await this.rebindCurrentSession();

		// Render initial messages AFTER showing loaded resources
		this.renderInitialMessages();
```

## !!steps Changelogs for pi and its extension packages

Early in `init`, before the UI starts, two kinds of changelog are loaded; both
are skipped for resumed sessions and shown once, right after the loaded
resources, by `showStartupNoticesIfNeeded`. Pi's own comes from
`getChangelogForDisplay`. Each
extension installed from a package that ships a changelog gets one too. Packages
are deduplicated by source key, since one package can provide several
extensions. The last version shown is stored per package in settings. A fresh
install only records its version, and a saved version that cannot be parsed is
replaced by the current one instead of showing the whole history.

New entries get the package name put into their headings so they read like
pi's own. They appear under "Extension Updates", or as one "Updated ... to
v..." line each when the changelog is collapsed. All changelog Markdown goes
through `createChangelogMarkdown`, which applies the Markdown transformers
registered for the `changelog` surface.

```ts ! interactive-mode.ts

				continue;
			}

// ...
```

## !!steps run: background checks, warnings, initial prompts

`run` calls `init`, then fires off work it does not wait for: a model catalog
refresh (skipped when offline, with a 15 second abort), a version check, a
package update check and a tmux keyboard check. Each reports through
a notification only if it finds something.

Startup diagnostics are then replayed with severity: errors, warnings, or plain
status. The `initialMessage` and each of `initialMessages` are sent with
`session.prompt`, one after another, and failures are shown rather than thrown.

```ts ! interactive-mode.ts
		// Process initial messages
		if (initialMessage) {
			try {
				await this.session.prompt(initialMessage, { images: initialImages });
			} catch (error: unknown) {
				const errorMessage = error instanceof Error ? error.message : "Unknown error occurred";
				this.showError(errorMessage);
			}
		}

		if (initialMessages) {
			for (const message of initialMessages) {
				try {
					await this.session.prompt(message);
				} catch (error: unknown) {
					const errorMessage = error instanceof Error ? error.message : "Unknown error occurred";
					this.showError(errorMessage);
				}
			}
		}
```

## !!steps The main loop is just prompt, forever

After startup, `run` is an infinite loop: wait for the next input, hand it to
`session.prompt`, show any error. Input arrives through `getUserInput`, which
bridges the editor's callback style to promises. If a submission arrived while
nobody was waiting (the previous prompt was still running), it was pushed onto
`pendingUserInputs` and is returned first; otherwise a one-shot callback is
stored for the submit handler to call.

```ts ! interactive-mode.ts
		// Main interactive loop
		while (true) {
			const userInput = await this.getUserInput();
			try {
				await this.session.prompt(userInput);
			} catch (error: unknown) {
				const errorMessage = error instanceof Error ? error.message : "Unknown error occurred";
				this.showError(errorMessage);
			}
		}
	}
// ...
	async getUserInput(): Promise<string> {
		const queuedInput = this.pendingUserInputs.shift();
		if (queuedInput !== undefined) {
			return queuedInput;
		}

		return new Promise((resolve) => {
			this.onInputCallback = (text: string) => {
				this.onInputCallback = undefined;
				resolve(text);
			};
		});
	}
```

## !!steps The submit handler: commands, bash, queues

`setupEditorSubmitHandler` is a long chain of exact-match checks. Each slash
command is recognized by comparing the trimmed text (with `startsWith` for
commands that take arguments), clears the editor, and calls a handler. Unknown
slash text falls through and is sent as a prompt, so extension commands and
prompt templates are resolved by the session, not here.

Lines beginning with `!` run a shell command; `!!` runs it but leaves the output
out of the model's context. A second bash command is refused while one is
running.

```ts ! interactive-mode.ts
			// Handle bash command (! for normal, !! for excluded from context)
			if (text.startsWith("!")) {
				const isExcluded = text.startsWith("!!");
				const command = isExcluded ? text.slice(2).trim() : text.slice(1).trim();
				if (command) {
					if (this.session.isBashRunning) {
						this.showWarning("A bash command is already running. Press Esc to cancel it first.");
						this.editor.setText(text);
						return;
					}
					this.editor.addToHistory?.(text);
					await this.handleBashCommand(command, isExcluded);
					this.isBashMode = false;
					this.updateEditorBorderColor();
					return;
				}
			}
```

## !!steps Typing while the agent is busy

If compaction is running, ordinary text is queued locally in
`compactionQueuedMessages`, while extension commands run immediately. While the
agent is streaming, the text goes to `session.prompt` with
`streamingBehavior: "steer"`, which makes it a steering message delivered
mid-run. Alt+Enter (`handleFollowUp`) is the same with `"followUp"`, which
waits until the agent is finished. Only an idle agent reaches the last branch,
where the text is passed to the pending `getUserInput` call.

```ts ! interactive-mode.ts
			// Queue input during compaction (extension commands execute immediately)
			if (this.session.isCompacting) {
				if (this.isExtensionCommand(text)) {
					this.editor.addToHistory?.(text);
					this.editor.setText("");
					await this.session.prompt(text);
				} else {
					this.queueCompactionMessage(text, "steer");
				}
				return;
			}

			// If streaming, use prompt() with steer behavior
			// This handles extension commands (execute immediately), prompt template expansion, and queueing
			if (this.session.isStreaming) {
				this.editor.addToHistory?.(text);
				this.editor.setText("");
				await this.session.prompt(text, { streamingBehavior: "steer" });
				this.updatePendingMessagesDisplay();
				this.ui.requestRender();
				return;
			}
```

## !!steps Draining the compaction queue

When compaction ends, `flushCompactionQueue` replays what the user typed. If an
automatic retry is pending, every message is queued as steer or follow-up for
that retry turn. Otherwise the first non-extension message becomes a real
prompt, extension commands before it run first, and the rest are queued behind
it. If sending fails, the queue is restored so nothing the user typed is lost,
and an error is shown.

```ts ! interactive-mode.ts
			// Find first non-extension-command message to use as prompt
			const firstPromptIndex = queuedMessages.findIndex((message) => !this.isExtensionCommand(message.text));
			if (firstPromptIndex === -1) {
				// All extension commands - execute them all
				for (const message of queuedMessages) {
					await this.session.prompt(message.text);
				}
				return;
			}

			// Execute any extension commands before the first prompt
			const preCommands = queuedMessages.slice(0, firstPromptIndex);
			const firstPrompt = queuedMessages[firstPromptIndex];
			const rest = queuedMessages.slice(firstPromptIndex + 1);
```

## !!steps Program status follows the event stream

Terminals that implement the Program Status Protocol (OSC 7501) can show
whether a program is working, waiting for the user, done or failed, which helps
when pi runs in a background tab. `InteractiveMode` owns one
[ProgramStatusReporter](/docs/src/modes/interactive/program-status-reporter.ts)
and passes it every session event before the switch, so run and compaction
state is worked out in one place rather than in each case. The reporter gets
the terminal and the session name through callbacks, because both can change
after construction.

`rebindCurrentSession` calls `reset`, so a session that was just switched to
does not inherit the previous session's `done` or `error`. Dialogs and logins
add `blocked` on top with `setBlocked`, as later steps show.

```ts ! interactive-mode.ts
	/** Reports working, blocked, done, and error states to terminals that support OSC 7501. */
	private readonly programStatus = new ProgramStatusReporter(
		() => this.ui.terminal,
		() => this.sessionManager.getSessionName(),
	);
// ...
	private async rebindCurrentSession(options: { renderBeforeBind?: boolean } = {}): Promise<void> {
		const session = this.session;

		this.unsubscribe?.();
		this.unsubscribe = undefined;
		// !mark
		this.programStatus.reset();
		this.applyRuntimeSettings();
// ...
	private async handleEvent(event: AgentSessionEvent): Promise<void> {
		if (!this.isInitialized) {
			await this.init();
		}

		this.footer.invalidate();
		// !mark
		this.programStatus.handleEvent(event);
```

## !!steps Finishing or failing a message

On `message_end`, the component is switched out of streaming state. An aborted
message gets a readable error, mentioning retry attempts if any. For aborted or
errored messages, every still-pending tool row is completed with an error result
so nothing is left spinning. On success, tool arguments are marked complete,
which triggers diff computation for edit tools.

```ts ! interactive-mode.ts
					if (this.streamingMessage.stopReason === "aborted" || this.streamingMessage.stopReason === "error") {
						if (!errorMessage) {
							errorMessage = this.streamingMessage.errorMessage || "Error";
						}
						for (const [, component] of this.pendingTools.entries()) {
							component.updateResult({
								content: [{ type: "text", text: errorMessage }],
								isError: true,
							});
						}
						this.pendingTools.clear();
						this.maybeSuggestBugReport(this.streamingMessage);
					} else {
						// Args are now complete - trigger diff computation for edit tools
						for (const [, component] of this.pendingTools.entries()) {
							component.setArgsComplete();
						}
```

## !!steps User bash output while the agent works

A `!` command typed while the agent is streaming cannot go into the chat yet:
the session holds its result back until the run ends, so it cannot land between
a tool call and its result. Its `BashExecutionComponent` waits in
`pendingBashComponents`, shown in the pending area above the editor.
`updatePendingMessagesDisplay` rebuilds that area with these boxes first and the
queued steering and follow-up messages after them, so queuing a message does not
hide the output. On `agent_settled`, when the session records the deferred
results, the boxes move into the chat.

New boxes start in the current expand state, and the pending area is one of the
containers that Ctrl+O walks, so the output can be expanded while the agent is
still running.

## !!steps Cache-warming notices collapse into one line

When the [cache warmer](/docs/src/core/cache-warmer.ts) refreshes the prompt
cache, its persisted usage entry is shown as a dim line, if cache notices are
enabled. During a long pause that would add one line per refresh. Instead, if
the previous notice is still the last child of the chat and carries the same
note, the new cost is added to a shared total and the existing line is
invalidated. The text is computed by a closure over `total`, so re-rendering
picks up the new sum. Anything appended in between starts a fresh line. Each
refresh is still stored as its own usage entry.

```ts ! interactive-mode.ts
	private addCacheWarmingUsage(entry: UsageEntry): void {
		if (!this.settingsManager.getShowCacheMissNotices()) return;
		// Back-to-back warms collapse into one line with the cumulative cost.
		const previous = this.cacheWarmingNotice;
		if (previous && this.chatContainer.children.at(-1) === previous.component && previous.note === entry.note) {
			previous.total.cost += entry.usage.cost.total;
			previous.component.invalidate();
			return;
		}
		const total = { cost: entry.usage.cost.total };
		const component = new ThemedText(() => theme.fg("dim", formatCacheWarmingUsage(total.cost, entry.note)), 1, 0);
		this.cacheWarmingNotice = { component, total, note: entry.note };
		this.chatContainer.addChild(new Spacer(1));
		this.chatContainer.addChild(component);
	}
```

## !!steps Extension dialogs form a stack

Extension dialogs (`select`, `confirm`, `input`, `editor` and inline `custom`
components) take the editor slot. A second dialog used to replace the visible
one and leave its promise pending forever. Now they share one stack,
`extensionDialogs`: a new dialog hides the visible one, and closing the visible
one shows the previous dialog, or the editor when none is left. Closing a
dialog lower in the stack just removes it. This also makes dialogs opened from
inside a custom component work.

Each entry carries an optional blocked status, and `showTopExtensionDialog`
reports the visible one under the `extension-dialog` source. `confirm` reports
kind `permission`; select, input and editor report `question` with the dialog
title. An extension that installs a custom editor while a dialog is open no
longer takes the slot; the new editor appears when the last dialog closes.

```ts ! interactive-mode.ts
	/**
	 * Show an extension dialog in the editor slot.
	 * Dialogs form a stack: a new dialog hides the visible one, and closing the visible dialog shows
	 * the previous one again. Every dialog stays answerable, so no dialog promise is left pending,
	 * and dialogs opened from inside another dialog (for example a confirm from a custom component) work.
	 */
	private pushExtensionDialog(component: ExtensionDialogComponent, blocked?: BlockedStatus): void {
		this.disposeActiveSelector();
		this.extensionDialogs.push({ component, blocked });
		this.showTopExtensionDialog();
	}

	/** Remove an extension dialog. If it was visible, show the previous dialog or the editor. */
	private removeExtensionDialog(component: ExtensionDialogComponent): void {
		const index = this.extensionDialogs.findIndex((dialog) => dialog.component === component);
		if (index === -1) return;
		this.extensionDialogs.splice(index, 1);
		if (index === this.extensionDialogs.length) this.showTopExtensionDialog();
	}

	private showTopExtensionDialog(): void {
		const top = this.extensionDialogs.at(-1);
		const component = top?.component ?? this.editor;
		this.editorContainer.clear();
		this.editorContainer.addChild(component);
		this.ui.setFocus(component);
		this.programStatus.setBlocked("extension-dialog", top?.blocked);
		this.ui.requestRender();
	}
```

## !!steps Custom components, overlays and reload

`ctx.ui.custom` hosts both inline components, which join the dialog stack, and
overlays drawn over the screen. The editor text is saved first, using
`getExpandedText` when the editor has it, so a large paste collapsed to a marker
comes back as the full text. An extension can pass `blocked` to say the
component waits for the user. Each blocking overlay gets its own numbered status
source, so closing one leaves other open questions reported. The source stays
set while the overlay is hidden with `setHidden`, because the question is still
unanswered.

Each overlay is recorded in `extensionOverlays` with its `removeOverlay`
function, which `done` and `resetExtensionUI` share. It hides that overlay
rather than the topmost one, clears its blocked status and disposes the
component. Deleting the map entry first makes a second call a no-op. On
`/reload` or a session switch, the reset calls every recorded function, newest
first and including hidden overlays, and leaves pi's own overlays (such as the
easter egg) alone. It used to call `hideOverlay` once, which removed only the
topmost overlay, whoever owned it. As with inline dialogs, the promises of
removed overlays are left pending.

```ts ! interactive-mode.ts
	private resetExtensionUI(): void {
// ...
		// Reload and session switches replace every extension without calling done(): remove their overlays,
		// newest first, the same way done() does, but leave the promises pending as for inline dialogs.
		for (const removeOverlay of [...this.extensionOverlays.values()].reverse()) removeOverlay();
// ...
		const savedText = this.editor.getExpandedText?.() ?? this.editor.getText();

			// An overlay stays blocked until its interaction ends, also while setHidden() hides it.
			const overlayStatusSource =
				isOverlay && options?.blocked ? `extension-overlay:${this.nextBlockingOverlayId++}` : undefined;

			// Shared by done() and resetExtensionUI(). Removing the map entry first makes a second call a no-op.
			const removeOverlay = () => {

			};
// ...
						overlayHandle = this.ui.showOverlay(c, resolveOptions());

						if (overlayStatusSource) this.programStatus.setBlocked(overlayStatusSource, options?.blocked);
// ...
						this.pushExtensionDialog(c, options?.blocked);
```

## !!steps Logins report blocked too

`/login` with an argument resolves the provider with `findMatchingProviders`
from [provider-matching.ts](/docs/src/core/provider-matching.ts), the same exact
id-or-name match, ignoring case, that the shell command
[pi auth login](/docs/src/cli/auth-login.ts) uses. While `loginProvider` waits

## !!steps Ctrl+C, Ctrl+D and graceful shutdown

Ctrl+C clears the editor, and a second press within 500 ms quits. Ctrl+D quits
only when the editor is empty, which `CustomEditor` enforces.

For an interactive quit, the order is deliberate: stop theme syncing, drain
pending keyboard input so key-release escape sequences do not leak into the
parent shell, stop the TUI, then dispose the runtime so extension shutdown
cleanup cannot repaint the final frame. Finally the resume command is printed.
A signal-triggered shutdown instead disposes first, so extension cleanup runs
even if the terminal is dead.

```ts ! interactive-mode.ts
		// Interactive quit (Ctrl+D, Ctrl+C, /quit, extension shutdown()). Stop the
		// TUI before emitting shutdown events so extension UI cleanup cannot repaint
		// the final frame while the process is exiting.
		// Drain any in-flight Kitty key release events before stopping.
		// This prevents escape sequences from leaking to the parent shell over slow SSH.
		this.themeController.disableAutoSync();
		await this.ui.terminal.drainInput(1000);

		this.stop();
		await this.runtimeHost.dispose();

		const resumeCommand = formatResumeCommand(this.sessionManager);
		if (resumeCommand) {
			process.stdout.write(`${chalk.dim("To resume this session:")} ${resumeCommand}\n`);
		}

		process.exit(0);
```

## !!steps Dead terminals and uncaught exceptions

A raw-mode TUI that crashes leaves the user's shell unusable, so
`registerSignalHandlers` installs three layers. SIGTERM (and SIGHUP outside
Windows) start a graceful shutdown. Errors on stdin, stdout or stderr that mean
the terminal is gone (`EIO`, `EPIPE` and similar) go to `emergencyTerminalExit`
with status 129, skipping cleanup that would write to a dead tty. Any other
uncaught exception goes to `uncaughtCrash`, which stops the UI to restore the
terminal, prints the error, records the crash for the `/bug` report, and exits 1.

```ts ! interactive-mode.ts
		const terminalErrorHandler = (error: Error) => {
			if (isDeadTerminalError(error)) {
				this.emergencyTerminalExit();
			}
			throw error;
		};
		// stdin needs the handler too: once the terminal is gone, reads and setRawMode
		// fail with EIO (orphaned background process group) or ENOTTY (revoked tty).
		// Node emits these as stream errors, which are uncaught without a listener.
		for (const stream of [process.stdin, process.stdout, process.stderr]) {
			stream.on("error", terminalErrorHandler);
			this.signalCleanupHandlers.push(() => stream.off("error", terminalErrorHandler));
		}
```
