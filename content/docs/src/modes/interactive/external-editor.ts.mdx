Long prompts are awkward in a terminal input box, so interactive mode can hand the current text to the user's `$EDITOR`-style command and take the result back. `editInExternalEditor` is that round trip: write a temp file, run the editor attached to the terminal, read the file back, clean up.

It is one function with a small result union, called from [interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts) for the main prompt and from [extension-editor.ts](/docs/src/modes/interactive/components/extension-editor.ts) for extension editor dialogs. The BOM handling comes from [text.ts](/docs/src/utils/text.ts).

<Scrollycoding>

## !!steps Inputs and outputs

The caller passes the full command string and the current content. The result is either `complete` with the new text, or `failed` with a message ready to show the user. Failures used to be silent, because the UI redrew over the terminal right away; now the interactive mode puts the message in the status line, and the extension editor shows it inline.

```ts ! external-editor.ts
export interface ExternalEditorOptions {
	command: string;
	content: string;
}

export type ExternalEditorResult = { status: "complete"; content: string } | { status: "failed"; message: string };
```

## !!steps A private temp file

The content goes into a fresh `mkdtemp` directory as `prompt.md`; the `.md` extension makes editors pick Markdown highlighting. The command is split on single spaces, so `code --wait` works but a path with spaces or quoted arguments does not.

A line is printed to stdout first so the user knows why the UI disappeared.

```ts ! external-editor.ts
export async function editInExternalEditor(options: ExternalEditorOptions): Promise<ExternalEditorResult> {
	const directory = mkdtempSync(join(tmpdir(), "pi-editor-"));
	const filePath = join(directory, "prompt.md");
	try {
		writeFileSync(filePath, options.content, "utf-8");
		// !mark
		const [editor, ...editorArgs] = options.command.split(" ");
		process.stdout.write(`Launching external editor: ${options.command}\nPi will resume when the editor exits.\n`);
```

## !!steps Async spawn, not spawnSync

The first comment records a real Windows bug: a synchronous child call can leave Node's console input read active after stdin is paused, so the parent and vim race for input until Ctrl+C. Hence an async `spawn` with `stdio: "inherit"` wrapped in a promise. On Windows the command runs through a shell.

The promise resolves to the exit code, or to the signal name when the editor was killed, or to `null` when it could not be started at all. The second comment explains a known limit that is accepted on purpose: the editor inherits pi's working directory so project-relative paths keep working, even though a Windows editor launched from a deep WSL directory can fail on the long path. Rather than changing the directory, the failure is reported.

```ts ! external-editor.ts
		// Do not use spawnSync here. On Windows, synchronous child_process calls can keep
		// Node/libuv's console input read active after the parent pauses stdin, racing
		// vim/nvim for the console input buffer until Ctrl+C cancels the pending read.
		// Null means the editor could not be launched.
		const exit = await new Promise<number | NodeJS.Signals | null>((resolve) => {
			// The editor inherits pi's cwd so project-relative paths, integrated terminals,
			// and similar editor features keep working. A long cwd can break Windows editors:
			// Windows rejects working directories over MAX_PATH, and WSL launches Windows
			// editors (code, notepad.exe) from the cwd's \\wsl.localhost\... path (#11592).
			// The cwd is intentionally not changed; failures are reported to the user instead.
			const child = spawn(editor, [...editorArgs, filePath], {
				stdio: "inherit",
				shell: process.platform === "win32",
			});
			// !mark(1:2)
			child.on("error", () => resolve(null));
			child.on("close", (code, signal) => resolve(code ?? signal));
		});
```

## !!steps Reporting failure, reading back and cleaning up

A launch failure and a non-zero exit get different messages, and the second one says the prompt was left unchanged. On success the file is read, a leading BOM is stripped, and a single trailing newline is removed (editors add one that the user did not type). The `finally` removes the whole directory, ignoring errors, on every path including failure.

```ts ! external-editor.ts
		if (exit === null) {
			return { status: "failed", message: `Failed to launch external editor: ${options.command}` };
		}
		if (exit !== 0) {
			return {
				status: "failed",
				message: `External editor exited with ${typeof exit === "number" ? `code ${exit}` : exit}; prompt unchanged`,
			};
		}

		// !mark
		return { status: "complete", content: stripBom(readFileSync(filePath, "utf-8")).replace(/\n$/, "") };
	} finally {
		try {
			rmSync(directory, { recursive: true, force: true });
		} catch {
			// Cleanup is best effort.
		}
	}
}
```

</Scrollycoding>

The function does not touch the TUI itself; it only inherits stdio, so the caller is responsible for giving up the terminal around the call. Nothing here validates that the command is non-empty.
