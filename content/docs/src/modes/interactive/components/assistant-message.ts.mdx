`AssistantMessageComponent` turns a model reply into terminal output. Streaming
works by calling `updateContent` again with each new partial `AssistantMessage`:
the container is cleared and refilled in content order. The `Markdown`
components themselves are kept between updates when the same kind of block sits
at the same position, so a streamed answer does not re-parse and re-highlight
the blocks it has already rendered.

Tool calls are not drawn here; they are separate components such as
[tool-execution.ts](/docs/src/modes/interactive/components/tool-execution.ts).
Markdown is post-processed through [markdown-transform.ts](/docs/src/modes/interactive/components/markdown-transform.ts)
using transformers from [extensions/types.ts](/docs/src/core/extensions/types.ts),
and the component is created by [interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts),
which also passes the message id and timestamp that transformers receive.

## !!steps Shell prompt markers and state

The three OSC 133 constants are semantic prompt markers (zone start, end and
final) that supporting terminals use to know where a block of output begins and
ends. A `MarkdownSlot` records one `Markdown` block of the last update and
whether it held text or thinking. The fields hold display settings,
`lastMessage` so the component can re-render itself, the message id and
timestamp for transformers, a per-run map of user toggles for thinking blocks,
and the slots from the previous update.

```ts ! assistant-message.ts
const OSC133_ZONE_START = "\x1b]133;A\x07";
const OSC133_ZONE_END = "\x1b]133;B\x07";
const OSC133_ZONE_FINAL = "\x1b]133;C\x07";

/**
 * A Markdown block of the last update. The next update reuses it at the same position for the same kind of content, so
 * a streamed answer keeps the blocks it already rendered, also once the stream ends.
 */
interface MarkdownSlot {
	kind: "text" | "thinking";
	markdown: Markdown;
}

/**
 * Component that renders a complete assistant message
 */
export class AssistantMessageComponent extends Container {
	private contentContainer: Container;
	private hideThinkingBlock: boolean;
	private markdownTheme: MarkdownTheme;
	private hiddenThinkingLabel: string;
	private outputPad: number;
	private markdownTransformers: readonly MarkdownTransformer[];
	private lastMessage?: AssistantMessage;
	private hasToolCalls = false;
	private isStreaming = false;
	private messageId?: string;
	private timestamp?: string;
	private thinkingVisibilityOverrides = new Map<number, boolean>();
	private markdownSlots: MarkdownSlot[] = [];
```

## !!steps Re-rendering on every change

Each setter stores its value and rebuilds from `lastMessage`. `invalidate` does
the same, so a theme change re-renders content with new colors. Changing the
global `hideThinkingBlock` clears the per-block overrides, so the global
setting wins again. `setOutputPad` also throws away the kept `Markdown`
blocks, because a `Markdown` takes its padding only at construction and a
reused one would keep the old indent.

```ts ! assistant-message.ts
	override invalidate(): void {
		super.invalidate();
		if (this.lastMessage) {
			this.updateContent(this.lastMessage);
		}
	}

	setHideThinkingBlock(hide: boolean): void {
		this.hideThinkingBlock = hide;
		this.thinkingVisibilityOverrides.clear();
		if (this.lastMessage) {
			this.updateContent(this.lastMessage);
		}
	}

// ...
	setOutputPad(padding: number): void {
		this.outputPad = padding;
		// Markdown takes its padding at construction.
		this.markdownSlots = [];
		if (this.lastMessage) {
			this.updateContent(this.lastMessage);
		}
	}
```

## !!steps Marking the output zone

`render` wraps the output in OSC 133 markers, but only when the message has no
tool calls. Messages with tool calls are followed by tool output, so marking
them would end the zone in the wrong place.

```ts ! assistant-message.ts
	override render(width: number): string[] {
		const lines = super.render(width);
		if (this.hasToolCalls || lines.length === 0) {
			return lines;
		}

		lines[0] = OSC133_ZONE_START + lines[0];
		lines[lines.length - 1] = OSC133_ZONE_END + OSC133_ZONE_FINAL + lines[lines.length - 1];
		return lines;
	}
```

## !!steps Reusing Markdown blocks

`updateContent` clears the container but keeps the previous slots. The
`markdownBlock` helper is called for each Markdown block in order: if the slot
at the same index held the same kind, its `Markdown` is reused and only gets
the new text through `setText`; otherwise `create` builds a fresh one. During
streaming the earlier blocks of an answer rarely change, so `Markdown` can keep
its already rendered top-level blocks instead of parsing and highlighting the
whole reply for every token.

```ts ! assistant-message.ts
	updateContent(message: AssistantMessage, isStreaming = this.isStreaming): void {
		this.lastMessage = message;
		this.isStreaming = isStreaming;

		// Clear content container
		this.contentContainer.clear();
		const previousSlots = this.markdownSlots;
		this.markdownSlots = [];
		const markdownBlock = (kind: MarkdownSlot["kind"], text: string, create: () => Markdown): Markdown => {
			const slot = previousSlots[this.markdownSlots.length];
			const markdown = slot?.kind === kind ? slot.markdown : create();
			markdown.setText(text);
			this.markdownSlots.push({ kind, markdown });
			return markdown;
		};
```

## !!steps Lazy spacers

Spacing follows what actually renders. Instead of checking ahead for visible
content, `needsSpacer` starts true and `addVisibleChild` inserts one blank line
right before the next visible block, then clears the flag. The result is a
blank line before the first visible block and after each visible thinking run
that is followed by more content, with nothing trailing before the separately
rendered tool calls.

```ts ! assistant-message.ts
		// Spacers are added lazily, right before the next visible content block. This puts a blank
		// line before the first visible block and after each visible thinking run that is followed
		// by more visible content, while hidden thinking runs without a label contribute nothing.
		let needsSpacer = true;
		const addVisibleChild = (child: Component) => {
			if (needsSpacer) {
				this.contentContainer.addChild(new Spacer(1));
				needsSpacer = false;
			}
			this.contentContainer.addChild(child);
		};
```

## !!steps Text blocks in order

The loop walks the content array in order. Text blocks become trimmed
`Markdown` components with zero vertical padding. The transform is keyed by
role and gets the message id and timestamp. Streaming state is passed as a
getter, not a value: a reused `Markdown` keeps the transform it was built with,
so the closure must read the current `isStreaming` when the stream ends.

```ts ! assistant-message.ts
		// Render content in order
		let thinkingRunIndex = 0;
		for (let i = 0; i < message.content.length; i++) {
			const content = message.content[i];
			if (content.type === "text" && content.text.trim()) {
				// Assistant text messages with no background - trim the text
				// Set paddingY=0 to avoid extra spacing before tool executions
				const text = content.text.trim();
				addVisibleChild(
					markdownBlock(
						"text",
						text,
						() =>
							new Markdown(text, this.outputPad, 0, this.markdownTheme, undefined, {
								transform: createMarkdownTransform(
									"assistant",
									() => this.isStreaming,
									this.markdownTransformers,
									this.messageId,
									this.timestamp,
								),
							}),
					),
				);
```

## !!steps Grouping consecutive thinking blocks

Adjacent thinking blocks are merged into a single run: the inner loop consumes
them, and `i--` hands the first non-thinking block back to the outer loop. Empty
thinking is dropped. Each run gets an index, used for click overrides, and a
hidden run whose label is blank is skipped entirely. It still uses up its index,
so overrides on later runs stay attached to the right run. Before this check
existed, an empty label (for example from `ctx.ui.setHiddenThinkingLabel("")`)
still drew blank rows.

```ts ! assistant-message.ts
			} else if (content.type === "thinking") {
				const thinkingBlocks: string[] = [];
				for (; i < message.content.length; i++) {
					const thinkingContent = message.content[i];
					if (thinkingContent.type !== "thinking") {
						break;
					}
					const thinking = thinkingContent.thinking.trim();
					if (thinking) {
						thinkingBlocks.push(thinking);
					}
				}
				i--;

				if (thinkingBlocks.length === 0) {
					continue;
				}

				const runIndex = thinkingRunIndex++;
				const hidden = this.thinkingVisibilityOverrides.get(runIndex) ?? this.hideThinkingBlock;
				// A hidden run with an empty label renders nothing, including no spacing.
				if (hidden && !this.hiddenThinkingLabel.trim()) {
					continue;
				}
```

## !!steps Click to toggle thinking

A run is either a dimmed italic label or full markdown in the thinking color,
the latter going through the same slot reuse as text. A `MouseRegion` wraps it
so a left click flips only that run and re-renders. Afterwards `needsSpacer` is
set, so a blank line appears only if another visible block follows.

```ts ! assistant-message.ts
				const thinking = thinkingBlocks.join("\n\n");
				const thinkingComponent = hidden
					? new Text(theme.italic(theme.fg("thinkingText", this.hiddenThinkingLabel)), this.outputPad, 0)
					: markdownBlock(
							"thinking",
							thinking,
							() =>
								new Markdown(
									thinking,
									this.outputPad,
									0,
									this.markdownTheme,
									{
										color: (text: string) => theme.fg("thinkingText", text),
										italic: true,
									},
									{
										transform: createMarkdownTransform(
											"assistant-thinking",
											() => this.isStreaming,
											this.markdownTransformers,
											this.messageId,
											this.timestamp,
										),
									},
								),
						);
				addVisibleChild(
					new MouseRegion(thinkingComponent, (event) => {
						if (event.type !== "click" || event.button !== "left") return undefined;
						this.thinkingVisibilityOverrides.set(runIndex, !hidden);
						if (this.lastMessage) this.updateContent(this.lastMessage);
						return { handled: true };
					}),
				);
				// Add spacing only when another visible assistant content block follows.
				// This avoids a superfluous blank line before separately-rendered tool execution blocks.
				needsSpacer = true;
			}
```

## !!steps Truncation, abort and error

After the content, the stop reason adds a footer. `length` is always shown, even
with tool calls, because a truncated reply may stop before the tool call is
complete. `aborted` and `error` are shown only without tool calls, since tool
execution components display those errors. The default "Request was aborted"
message is replaced by "Operation aborted".

```ts ! assistant-message.ts
		// Check if incomplete/failed - show after partial content.
		// For aborted/error tool calls, tool execution components show the error.
		// Length stops can happen before a tool call is complete, so surface them here too.
		const hasToolCalls = message.content.some((c) => c.type === "toolCall");
		this.hasToolCalls = hasToolCalls;
		if (message.stopReason === "length") {
			this.contentContainer.addChild(new Spacer(1));
			this.contentContainer.addChild(
				new Text(theme.fg("error", "Response was truncated before completion."), this.outputPad, 0),
			);
		} else if (!hasToolCalls) {
			if (message.stopReason === "aborted") {
				const abortMessage =
					message.errorMessage && message.errorMessage !== "Request was aborted"
						? message.errorMessage
						: "Operation aborted";
				this.contentContainer.addChild(new Spacer(1));
				this.contentContainer.addChild(new Text(theme.fg("error", abortMessage), this.outputPad, 0));
			} else if (message.stopReason === "error") {
				const errorMsg = message.errorMessage || "Unknown error";
				this.contentContainer.addChild(new Spacer(1));
				this.contentContainer.addChild(new Text(theme.fg("error", `Error: ${errorMsg}`), this.outputPad, 0));
			}
		}
```

The message is the only source of truth: every setter funnels into
`updateContent`, so there is no incremental patching of the tree to keep
consistent. The `Markdown` slots are a cache underneath that rule, not state of
their own; dropping them, as `setOutputPad` does, only costs a re-parse.
