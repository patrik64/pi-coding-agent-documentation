A pi session is not a straight line. Every entry records a `parentId`, so rewinding and continuing creates branches, and [session-manager.ts](/docs/src/core/session-manager.ts) exposes the whole thing as a tree of `SessionTreeNode`. This file is the interactive view of that tree: the user moves through it, filters and searches it, folds branches, labels entries, and picks one to continue from.

The exported `TreeSelectorComponent` is a thin container. The real work is in the private `TreeList` class, which turns the tree into a flat list of rows with indentation, connectors and gutters, and keeps that structure correct as filters hide entries. Smaller helper classes render the search line, the help text and the label editor. Sibling pickers like [session-selector.ts](/docs/src/modes/interactive/components/session-selector.ts) use the same `Container` and `DynamicBorder` pattern.

## !!steps Rows carry their own drawing instructions

Each row of the list is a `FlatNode`: the tree node plus everything needed to draw it without consulting the tree. `indent` is a level number, `showConnector` and `isLast` choose between the `├─` and `└─` forms, and `gutters` lists which ancestor levels still need a vertical line.

`isVirtualRootChild` handles sessions with several roots. Those are treated as children of an invisible root that branches, so each root gets indent 1 but no connector of its own.

```ts ! tree-selector.ts
/** Gutter info: position (displayIndent where connector was) and whether to show │ */
interface GutterInfo {
	position: number; // displayIndent level where the connector was shown
	show: boolean; // true = show │, false = show spaces
}

/** Flattened tree node for navigation */
interface FlatNode {
	node: SessionTreeNode;
	/** Indentation level (each level = 3 chars) */
	indent: number;
	/** Whether to show connector (├─ or └─) - true if parent has multiple children */
	showConnector: boolean;
	/** If showConnector, true = last sibling (└─), false = not last (├─) */
	isLast: boolean;
	/** Gutter info for each ancestor branch point */
	gutters: GutterInfo[];
	// !mark
	/** True if this node is a root under a virtual branching root (multiple roots) */
	isVirtualRootChild: boolean;
}
```

## !!steps Panning sideways only when needed

Deep trees push entry text far to the right. `renderHorizontalViewport` keeps a fixed two-column gutter (the cursor) and clips only the row bodies. It scrolls only if the selected row's anchor, the column where its entry text starts, would leave fewer than a minimum number of visible content columns. That minimum is a third of the viewport clamped between 4 and 20.

When it does scroll, it leaves a few columns of context before the anchor, clamped between 2 and 12, and never scrolls past the widest row. All rows share one offset, so the tree stays aligned while panning.

```ts ! tree-selector.ts
	// Only pan horizontally when needed to keep enough selected-row content visible after its anchor.
	let horizontalScroll = 0;
	if (selectedRow && maxHorizontalScroll > 0) {
		const minVisibleAnchorContentWidth = Math.min(
			MAX_VISIBLE_ANCHOR_CONTENT_WIDTH,
			Math.max(MIN_VISIBLE_ANCHOR_CONTENT_WIDTH, Math.floor(viewportWidth / 3)),
		);
		// !mark(1:5)
		if (selectedRow.anchorCol > viewportWidth - minVisibleAnchorContentWidth) {
			const anchorContextWidth = Math.min(
				MAX_ANCHOR_CONTEXT_WIDTH,
				Math.max(MIN_ANCHOR_CONTEXT_WIDTH, Math.floor(viewportWidth / 4)),
			);
			horizontalScroll = Math.min(maxHorizontalScroll, selectedRow.anchorCol - anchorContextWidth);
		}
	}
```

## !!steps The active branch is listed first

Before flattening, the constructor works out which subtrees contain the current leaf. It does this iteratively: collect nodes in pre-order, then walk that list backwards so children are handled before parents. A recursive version would overflow the stack on a very long session, which is a plausible shape since conversations are deep chains.

The `containsActive` map is then used to sort roots and each node's children so the branch the user is on comes first, and the others follow.

```ts ! tree-selector.ts
		// Determine which subtrees contain the active leaf (to sort current branch first)
		// Use iterative post-order traversal to avoid stack overflow
		const containsActive = new Map<SessionTreeNode, boolean>();
		const leafId = this.currentLeafId;
		{
			// Build list in pre-order, then process in reverse for post-order effect
			const allNodes: SessionTreeNode[] = [];
			const preOrderStack: SessionTreeNode[] = [...roots];
			// ...
			// Process in reverse (post-order): children before parents
			for (let i = allNodes.length - 1; i >= 0; i--) {
				const node = allNodes[i];
				// !mark
				let has = leafId !== null && node.entry.id === leafId;
				for (const child of node.children) {
					if (containsActive.get(child)) {
						has = true;
					}
				}
				containsActive.set(node, has);
			}
		}
```

## !!steps Indentation that does not drift

The indentation rules are written as a comment and implemented a few lines below. A linear chain of messages must not creep rightward, or a long conversation would scroll off screen. So indent increases only where something actually branches.

The child indent is `indent + 1` when the parent has more than one child, and also for the first generation after a branch when already indented, which visually groups the subtree. Otherwise the chain stays flat. Gutter entries are added only when a connector is really drawn, and the vertical line shows only if the node is not the last sibling.

```ts ! tree-selector.ts
			// Calculate child indent
			let childIndent: number;
			// !mark(1:9)
			if (multipleChildren) {
				// Parent branches: children get +1
				childIndent = indent + 1;
			} else if (justBranched && indent > 0) {
				// First generation after a branch: +1 for visual grouping
				childIndent = indent + 1;
			} else {
				// Single-child chain: stay flat
				childIndent = indent;
			}

			// Build gutters for children
			// If this node showed a connector, add a gutter entry for descendants
			// Only add gutter if connector is actually displayed (not suppressed for virtual root children)
			const connectorDisplayed = showConnector && !isVirtualRootChild;
```

## !!steps What the default view hides

`applyFilter` rebuilds `filteredNodes` from the full flat list. Some rules apply in every mode. `usage` entries never appear. Assistant messages that contain only tool calls and no text are hidden, unless they ended in an error or abort, or they are the current leaf, so the user can always see where they are.

The filter mode then decides the rest. The default hides settings and bookkeeping entries (labels, model and thinking changes, custom entries, session info). `no-tools` also hides tool results, `user-only` shows just user messages, `labeled-only` keeps entries with a label, and `all` shows everything except usage.

```ts ! tree-selector.ts
			switch (this.filterMode) {
				case "user-only":
					// Just user messages
					passesFilter = entry.type === "message" && entry.message.role === "user";
					break;
				case "no-tools":
					// Default minus tool results
					// !mark
					passesFilter = !isSettingsEntry && !(entry.type === "message" && entry.message.role === "toolResult");
					break;
				case "labeled-only":
					// Just labeled entries
					passesFilter = flatNode.node.label !== undefined;
					break;
				case "all":
					// Show everything
					passesFilter = true;
					break;
				default:
					// Default mode: hide settings/bookkeeping entries
					passesFilter = !isSettingsEntry;
					break;
			}
```

## !!steps Search, folding and a rebuilt visual structure

After the mode filter, the search query is split on whitespace and every token must appear in the entry's searchable text, which includes its role, content, label, and type specific words like "model" or "compaction". Folded nodes then remove all their descendants, found by one pass that propagates a skip set down the parent chain.

The key step is `recalculateVisualStructure`. Hiding entries changes the tree shape, since a child now hangs off its nearest visible ancestor. It rebuilds visible parent and child maps, recomputes indent, connectors and gutters with the same rules as `flattenTree`, and updates `multipleRoots`. The same logic exists twice, once for the full tree and once for the visible one.

```ts ! tree-selector.ts
		// Filter out descendants of folded nodes.
		if (this.foldedNodes.size > 0) {
			const skipSet = new Set<string>();
			for (const flatNode of this.flatNodes) {
				const { id, parentId } = flatNode.node.entry;
				// !mark
				if (parentId != null && (this.foldedNodes.has(parentId) || skipSet.has(parentId))) {
					skipSet.add(id);
				}
			}
			this.filteredNodes = this.filteredNodes.filter((flatNode) => !skipSet.has(flatNode.node.entry.id));
		}

		// Recalculate visual structure (indent, connectors, gutters) based on visible tree
		// !mark
```

## !!steps Keeping the cursor on the right entry

Changing the filter can hide the selected entry, so the selection is tracked by id rather than by index. `findNearestVisibleIndex` takes an entry id and, if it is not visible, walks up the `parentId` chain until it finds one that is. If nothing visible is found it falls back to the last row.

`lastSelectedId` is only updated when the list is non-empty. That is why switching to a filter with no results and back returns the cursor to where it was.

```ts ! tree-selector.ts
	private findNearestVisibleIndex(entryId: string | null): number {
		if (this.filteredNodes.length === 0) return 0;
		// ...
		// Walk from entryId up to root, looking for a visible entry
		let currentId = entryId;
		while (currentId !== null) {
			const index = visibleIdToIndex.get(currentId);
			if (index !== undefined) return index;
			const node = entryMap.get(currentId);
			if (!node) break;
			// !mark
			currentId = node.node.entry.parentId ?? null;
		}

		// Fallback: last visible entry
		return this.filteredNodes.length - 1;
	}
```

## !!steps Drawing the prefix character by character

`render` builds each row's prefix one character at a time. For every column of the indent area it decides between a gutter line, the connector, or a space. A level is three characters wide, so the connector is `├─ ` or `└─ `.

The second character of the connector doubles as the fold indicator: `⊞` for a folded node, `⊟` for one that can be folded, `─` otherwise. Nodes without a connector show a `⊞` marker before the text instead. Entries on the path to the current leaf get a bullet right before their text.

## !!steps Navigation by branch segments

Left and right arrows are bound to paging, so folding lives on separate keys. The fold-or-up key folds the selected node if it is foldable and not already folded; otherwise it jumps to the start of the previous branch segment. Unfold-or-down does the reverse: unfold if folded, else jump down.

A node is foldable only if it has visible children and is a root or the first node of a segment, meaning its parent has several visible children. `findBranchSegmentStart` going down always follows the first child until it reaches a branch point or a leaf. Going up walks the visible parent chain to the nearest branch point strictly above the cursor.

```ts ! tree-selector.ts
	private isFoldable(entryId: string): boolean {
		const children = this.visibleChildrenMap.get(entryId);
		if (!children || children.length === 0) return false;
		const parentId = this.visibleParentMap.get(entryId);
		// !mark
		if (parentId === null || parentId === undefined) return true;
		const siblings = this.visibleChildrenMap.get(parentId);
		return siblings !== undefined && siblings.length > 1;
	}
```

## !!steps Keys, filters and typing into the search

`handleInput` is one long if-chain over rebindable actions. Up and down wrap around at the ends. Cancel first clears a non-empty search and only calls `onCancel` when the query is already empty. Each direct filter key toggles its mode against the default, so pressing the same key twice returns to the default view, while the cycle keys step through all five modes in a ring.

Anything that is not a recognized binding becomes search input: control characters are rejected and the rest is appended to `searchQuery`. Backspace is handled by hand as well, and every change clears the fold state before re-filtering.

## !!steps A help line built from the live keybindings

The help text is not a string constant. `TREE_HELP_ITEMS` lists keybinding ids and labels, and `formatHelpKeys` looks up the first key currently bound to each, so a rebinding shows up immediately. `compactRawKeys` merges keys with a shared modifier prefix into one chunk joined with slashes, and arrows are shortened to symbols.

`TreeHelp.render` then packs the chunks into lines, wrapping at item boundaries with the separator `·` so a binding is never split across two lines, falling back to ANSI-aware wrapping only for an item wider than the terminal.

```ts ! tree-selector.ts
function compactRawKeys(keys: string[]): string {
	if (keys.length === 1) return keys[0]!;

	const parts = keys.map((key) => {
		const separatorIndex = key.lastIndexOf("+");
		return separatorIndex === -1
			? { prefix: "", suffix: key }
			: { prefix: key.slice(0, separatorIndex + 1), suffix: key.slice(separatorIndex + 1) };
	});
	const prefix = parts[0]!.prefix;
	// !mark(1:3)
	return prefix && parts.every((part) => part.prefix === prefix)
		? `${prefix}${parts.map((part) => part.suffix).join("/")}`
		: keys.join("/");
}
```

## !!steps The container and label editing

`TreeSelectorComponent` assembles the chrome: borders, a title, the help, the search line and the list. The list height is half the terminal, but at least five lines. An empty tree schedules `onCancel` after 100 ms, so the caller can leave a picker that has nothing to show.

Labels are edited inline. Pressing the label key swaps the list for a `LabelInput` in the same slot and routes all input to it. On submit the list's node is updated in memory, `onLabelChange` is called so the caller can persist it, and the list returns. Focus is propagated so the terminal cursor sits in the right place for input methods.

```ts ! tree-selector.ts
	private showLabelInput(entryId: string, currentLabel: string | undefined): void {
		this.labelInput = new LabelInput(entryId, currentLabel);
		this.labelInput.onSubmit = (id, label) => {
			// !mark(1:2)
			this.treeList.updateNodeLabel(id, label);
			this.onLabelChangeCallback?.(id, label);
			this.hideLabelInput();
		};
		this.labelInput.onCancel = () => this.hideLabelInput();

		// Propagate current focused state to the new labelInput
		this.labelInput.focused = this._focused;

		this.treeContainer.clear();
		this.labelInputContainer.clear();
		this.labelInputContainer.addChild(this.labelInput);
	}
```

The component is opened by [interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts), which passes the session tree from [session-manager.ts](/docs/src/core/session-manager.ts) and persists label changes. It reads colors from [theme.ts](/docs/src/modes/interactive/theme/theme.ts) and key hints from [keybinding-hints.ts](/docs/src/modes/interactive/components/keybinding-hints.ts), and frames itself with [dynamic-border.ts](/docs/src/modes/interactive/components/dynamic-border.ts).

One structural note: the whole design rests on `flatNodes` being the immutable, full ordering and `filteredNodes` being a view whose layout fields are mutated in place by `recalculateVisualStructure`. Those fields on the shared `FlatNode` objects therefore describe only the current filter, not the full tree.
