Remote MCP servers often require OAuth. The protocol work (discovery, PKCE, choosing between a Client ID Metadata Document and dynamic client registration, refreshing tokens, the loopback callback server and the two halves of a sign-in) lives in the `@earendil-works/pi-mcp/oauth` package, which moved it out of this file so other applications sign in to MCP servers the same way. What is left here is what only pi knows: where credentials are stored, how processes coordinate a refresh, which client identity pi presents, and how the sign-in talks to pi's UI.

The design rule from the header comment still holds: connections never open a browser on their own. They send the stored access token, try the stored refresh token after a 401, and otherwise fail with `McpOAuthAuthorizationRequiredError`. Only the user starts a sign-in, through the `/mcp` manager in [index.ts](/docs/src/extensions/mcp/index.ts) and [ui.ts](/docs/src/extensions/mcp/ui.ts) or with `pi mcp login` in [cli.ts](/docs/src/extensions/mcp/cli.ts).

Credentials are stored in `mcp-auth.json` through [auth-storage.ts](/docs/src/core/auth-storage.ts). The connection layer in [runtime.ts](/docs/src/extensions/mcp/runtime.ts) creates the auth provider and re-exports the store and the sign-in, so all of this loads lazily with the MCP runtime. [config.ts](/docs/src/extensions/mcp/config.ts) resolves the user's `oauth` block into the settings passed here, and [mcp-servers.ts](/docs/src/core/mcp-servers.ts) supplies the rule for which callbacks pi's metadata documents list.

## !!steps Refresh lock timing and the stored file

Only the lock timing is left of the old constants; refresh skew and request timeouts now live in pi-mcp. A refresh lock is considered abandoned after 20 seconds, and the wait for another process (25 seconds) is deliberately longer than that, so a crashed holder is always taken over before waiters give up.

The file holds one `McpOAuthState` per server: client registration, tokens, and a pending PKCE verifier. Parsing tolerates an empty file and anything that is not an object.

```ts ! oauth.ts
/** A refresh lock that its holder stopped renewing (the process was killed) is taken over after this. */
// !mark
const REFRESH_LOCK_STALE_MS = 20_000;
/** How long to wait for another process's refresh: longer than a stale lock lives. */
// !mark
const REFRESH_LOCK_WAIT_MS = 25_000;
const REFRESH_LOCK_RETRY_MS = 100;

type StoredStates = Record<string, McpOAuthState>;

function parseStates(content: string | undefined): StoredStates {
	if (!content?.trim()) return {};
	const parsed: unknown = JSON.parse(content);
	return typeof parsed === "object" && parsed !== null && !Array.isArray(parsed) ? (parsed as StoredStates) : {};
}
```

## !!steps Credential store keyed by name and URL

The key is the server's namespace (from pi-mcp's `mcpNamespace`) plus its URL, so two servers on the same URL can hold different accounts. Older versions keyed by URL alone, and `load` migrates that legacy entry to the new key the first time a server reads it. Other servers with the same URL must sign in again.

`forServer` returns the `McpOAuthServerStore` interface that pi-mcp's auth provider and sign-in expect: `load`, `save`, and `withRefreshLock`. Every file access goes through `backend.withLock`, so reads and writes are serialized. Without an explicit backend, the store uses `mcp-auth.json` in the agent directory and puts lock files next to it.

```ts ! oauth.ts
function storeKeys(name: string, serverUrl: string): { key: string; legacyKey: string } {
	const legacyKey = String(new URL(serverUrl));
	// !mark
	return { key: `${mcpNamespace(name)}|${legacyKey}`, legacyKey };
}

/** Per-server OAuth state (client registration, tokens, pending PKCE verifier) in `mcp-auth.json`. */
export class McpOAuthCredentialStore {
	private readonly backend: AuthStorageBackend;
	/** Directory for the refresh lock files. Without one, refreshes are only serialized in this process. */
	private readonly lockDir: string | undefined;

	constructor(backend?: AuthStorageBackend, lockDir?: string) {
		this.backend = backend ?? new FileAuthStorageBackend(join(getAgentDir(), "mcp-auth.json"));
		this.lockDir = backend ? lockDir : getAgentDir();
	}

	forServer(name: string, serverUrl: string): McpOAuthServerStore {
		const { key, legacyKey } = storeKeys(name, serverUrl);
		return {
			// !mark
			// The first server to load legacy state takes it over; others with the same URL sign in again.
			load: () =>
				this.backend.withLock((current) => {
					const states = parseStates(current);
					if (states[key] || !states[legacyKey]) return { result: states[key] };
					states[key] = states[legacyKey];
					delete states[legacyKey];
					return { result: states[key], next: serializeStates(states) };
				}),
			save: (state) =>
				this.write((states) => {
					states[key] = state;
				}),
			// !mark
			withRefreshLock: (fn) => this.withRefreshLock(key, fn),
		};
	}
```

## !!steps A lock file so processes do not race a refresh

Many servers rotate refresh tokens: using the same one twice loses the grant. Two pi processes with the same server could do exactly that, so refreshes take a per-server lock file named by a hash of the key. pi-mcp holds this lock from reading the tokens to saving the new ones.

The retry settings poll every 100 ms for up to 25 seconds. `onCompromised` is a no-op on purpose: the default throws from a timer, and a lost lock only risks overlapping refreshes. When another process holds the lock for the whole wait, proper-lockfile's `ELOCKED` is turned into `McpRefreshLockBusyError`. That is the one lock error pi-mcp's sign-in treats as "skip the refresh and go to the browser"; any other error fails the sign-in.

```ts ! oauth.ts
	private async withRefreshLock<T>(key: string, fn: () => Promise<T>): Promise<T> {
		// !mark
		if (!this.lockDir) return fn();
		mkdirSync(this.lockDir, { recursive: true, mode: 0o700 });
		const hash = createHash("sha256").update(key).digest("hex").slice(0, 16);
		const release = await lockfile
			.lock(join(this.lockDir, `mcp-auth-refresh-${hash}`), {
				realpath: false,
				stale: REFRESH_LOCK_STALE_MS,
				retries: {
					retries: REFRESH_LOCK_WAIT_MS / REFRESH_LOCK_RETRY_MS,
					factor: 1,
					minTimeout: REFRESH_LOCK_RETRY_MS,
					maxTimeout: REFRESH_LOCK_RETRY_MS,
				},
				// The default throws from a timer. A lost lock at worst lets two refreshes overlap.
				onCompromised: () => {},
			})
			.catch((error: unknown) => {
				// proper-lockfile reports a lock held by another process as `ELOCKED`.
				// !mark(1:2)
				if (error instanceof Error && "code" in error && error.code === "ELOCKED")
					throw new McpRefreshLockBusyError();
				throw error;
			});
		try {
			return await fn();
		} finally {
			await release().catch(() => undefined);
		}
	}
```

## !!steps Reading and removing credentials

Two more methods serve callers outside a connection. `tokens` lets the extension in [index.ts](/docs/src/extensions/mcp/index.ts) notice that `pi mcp login` in another process (for example one the agent ran) stored credentials for a server waiting on a sign-in, so it can reconnect; it reads the legacy key too but does not migrate it. `remove` backs sign-out in the `/mcp` manager and `pi mcp logout`, reports whether anything was stored, and deletes the legacy entry when that is what the server would have taken over.

```ts ! oauth.ts
	/** The stored tokens of a server, for noticing sign-ins done by another process. Does not take over legacy state. */
	tokens(name: string, serverUrl: string): McpOAuthState["tokens"] {
		const { key, legacyKey } = storeKeys(name, serverUrl);
		const states = this.backend.withLock((current) => ({ result: parseStates(current) }));
		// !mark
		return (states[key] ?? states[legacyKey])?.tokens;
	}

	/** Returns whether credentials were stored for the server. Removes legacy state the server would take over. */
	remove(name: string, serverUrl: string): boolean {
		const { key, legacyKey } = storeKeys(name, serverUrl);
		return this.backend.withLock((current) => {
			const states = parseStates(current);
			// !mark
			const stored = key in states ? key : legacyKey in states ? legacyKey : undefined;
			if (!stored) return { result: false };
			delete states[stored];
			return { result: true, next: serializeStates(states) };
		});
	}
```

## !!steps pi's client identity

pi-mcp takes application specifics as options. pi's are its name and its Client ID Metadata Documents on pi.dev: `client.json`, plus one document per MCP server under a callback ID. `listsRedirectUrl` reuses `isClientMetadataDocumentCallback`, so pi-mcp only picks a document when its redirect URI is one the documents actually list.

`piSettings` guards rebranded builds. With the default `auto` registration, a build whose `APP_NAME` is not `pi` would otherwise sign in with pi's documents and show up to the user as pi, so it is switched to dynamic client registration.

`createMcpAuthProvider` is pi-mcp's provider with this identity mixed in. The provider sends the stored token, refreshes it shortly before expiry or after a 401, and throws the authorization-required error when only a new sign-in helps.

```ts ! oauth.ts
/** pi's Client ID Metadata Documents on pi.dev: `client.json` and `<callback ID>/client.json`. */
const PI_CLIENT_METADATA_DOCUMENTS: McpClientMetadataDocuments = {
	baseUrl: "https://pi.dev/oauth",
	// !mark
	listsRedirectUrl: isClientMetadataDocumentCallback,
};

/** pi's client identity for sign-in and refresh. */
const PI_CLIENT = { clientName: APP_NAME, clientMetadataDocuments: PI_CLIENT_METADATA_DOCUMENTS };

/** `settings` for pi-mcp: a rebranded build would show up as pi with pi's documents, so `auto` registers. */
function piSettings(settings: McpOAuthSettings): McpOAuthSettings {
	const auto = (settings.clientRegistration ?? "auto") === "auto";
	// !mark
	return auto && APP_NAME !== "pi" ? { ...settings, clientRegistration: "dcr" } : settings;
}

/** pi-mcp's `createMcpAuthProvider` with pi's client identity. */
export function createMcpAuthProvider(options: {
	serverUrl: string;
	store: McpOAuthServerStore;
	settings: () => McpOAuthSettings;
	onChallenge: (challenge: OAuthChallenge) => void;
}): McpAuthProvider {
	// !mark
	return createAuthProvider({ ...options, ...PI_CLIENT, settings: () => piSettings(options.settings()) });
}
```

## !!steps What the sign-in needs from the UI

`McpSignInPrompt` is the boundary between the sign-in and whichever UI runs it: the `/mcp` dialog or the `pi mcp login` terminal flow. It shows the authorization URL, and it asks for the redirect URL from the browser's address bar as a fallback for when the browser cannot reach the loopback server, for example over SSH. The prompt is aborted once the callback arrives.

The page the browser lands on is rendered with pi-ai's shared OAuth page helpers.

```ts ! oauth.ts
export interface McpSignInPrompt {
	/** Show the authorization URL to the user and open it in a browser. */
	showAuthorizationUrl(url: URL): void;
	/**
	 * Ask for the redirect URL from the browser address bar, for when the browser cannot reach the
	 * loopback callback (for example over SSH). Aborted once the callback arrives or the sign-in is
	 * cancelled. Resolves to `undefined` or an empty string when the user cancels.
	 */
	promptForRedirectUrl(signal: AbortSignal): Promise<string | undefined>;
}

function renderCallbackPage(page: OAuthCallbackPage): string {
	return page.ok
		? oauthSuccessHtml("Signed in to the MCP server. You may now close this page.")
		: oauthErrorHtml(page.message, page.details);
}
```

## !!steps The sign-in, in pi-mcp's two halves

`signInMcpServer` is now a thin sequence of pi-mcp calls. It starts the loopback callback server first, because the redirect URI (and its port) must be known before the flow begins. pi-mcp listens on the configured callback, else on the port of the stored client's redirect URI so that registration stays valid, else on a free port. Passing pi's documents lets it also serve the server-specific callback path. `startMcpSignIn` then tries a refresh with the stored client; if that works the result is `authorized` and nothing else happens. Otherwise it returns an authorization URL, which the prompt shows.

`waitForLoopbackSignIn` races the browser callback against a pasted redirect URL, and `completeMcpSignIn` exchanges the code and saves the tokens. Aborting `signal` cancels any step with `McpSignInCancelledError`. The `finally` always closes the callback server, whichever way the sign-in ends.

```ts ! oauth.ts
	const { serverUrl, store, challenge, prompt, signal } = options;
	const settings = piSettings(options.settings);
	// !mark(1:7)
	const { callback, redirectUrl } = await listenForLoopbackSignIn({
		serverUrl,
		store,
		settings,
		clientMetadataDocuments: PI_CLIENT_METADATA_DOCUMENTS,
		renderPage: renderCallbackPage,
	});
	try {
		const signIn = { serverUrl, store, settings, redirectUrl, challenge, signal, ...PI_CLIENT };
		// !mark(1:2)
		const authorization = await startMcpSignIn(signIn);
		if (authorization.kind === "authorized") return;
		prompt.showAuthorizationUrl(new URL(authorization.authorizationUrl));
		const response = await waitForLoopbackSignIn({
			callback,
			authorization,
			promptForRedirectUrl: (promptSignal) => prompt.promptForRedirectUrl(promptSignal),
			signal,
		});
		// !mark
		await completeMcpSignIn({ ...signIn, authorization, response });
	} finally {
		await callback.close();
	}
}
```

</Scrollycoding>

The file has the same three layers as before, but only the first is still implemented here: storage (`McpOAuthCredentialStore`), passive use (`createMcpAuthProvider`, called on every request) and active sign-in (`signInMcpServer`, called only on the user's request). The other two are pi-mcp's code configured with pi's identity. All three share `McpOAuthState` in `mcp-auth.json`, so a sign-in done in one process is picked up by the others through `tokens()` and the re-read inside the refresh lock.
