Every tool an MCP server exposes becomes a pi `ToolDefinition` through this file. The work is mostly translation in both directions: an input schema every provider will accept, annotations carried across, a declared output schema, and the server's `CallToolResult` converted into the text and images the model can see.

Two audiences read each result. The model gets bounded, readable content. Codemode scripts get the whole `CallToolResult` as `structuredContent`, never truncated. The parts every MCP client needs the same way (the `mcp__server__tool` naming, input-schema normalization and the 20 KB middle-cut output limit) moved into the `@earendil-works/pi-mcp` package, so other applications name and limit MCP tools exactly like pi; this file imports them. The result schema also became self-contained when codemode stopped knowing about MCP.

The MCP extension in [index.ts](/docs/src/extensions/mcp/index.ts) calls `createMcpToolDefinition` for each discovered tool and `createMcpToolRenderers` for calls shown before a server connects. The resource tools in [resources.ts](/docs/src/extensions/mcp/resources.ts) reuse `toModelContent` and `saveToTempFile`. The file leans on [output-files.ts](/docs/src/utils/output-files.ts) for temp files, [truncate.ts](/docs/src/core/tools/truncate.ts) for size formatting, [render-utils.ts](/docs/src/core/tools/render-utils.ts) and [visual-truncate.ts](/docs/src/modes/interactive/components/visual-truncate.ts) for the TUI, and the types in [types.ts](/docs/src/core/extensions/types.ts).

## !!steps Exposure and where saved output goes

MCP exposure has a `codemode` value that the core tool exposure type lacks. `toToolExposure` maps it to `deferred`: both keep the tool out of the codemode description, and they differ only in which tool the MCP extension activates to reach them.

The collapsed TUI view shows 5 visual lines. The model-facing size limit is no longer defined here: it is pi-mcp's `MCP_OUTPUT_MAX_BYTES`. pi-mcp's limiter only saves the full text when the caller hands it a saver, and `saveToTempFile` is pi's: it writes under a `pi-mcp` prefix with the shared output-file helper.

```ts ! tools.ts
export function toToolExposure(exposure: McpExposure): ToolExposure {
	// !mark
	return exposure === "codemode" ? "deferred" : exposure;
}

/** Visual (wrapped) result lines shown before the output is expanded. */
// !mark
const OUTPUT_PREVIEW_LINES = 5;
/** Tool that reads the resources named by resource links. */
export { READ_MCP_RESOURCE_TOOL };

export interface McpToolDetails {
	server: string;
	tool: string;
	/** Temp file with the full text output, when the model-facing text was truncated. */
	fullOutputPath?: string;
}

/** Saves the full text of a truncated result, or a binary resource, to a temp file and returns its path. */
// !mark(1:3)
export function saveToTempFile(data: string | Uint8Array, extension: string): Promise<string> {
	return writeOutputFile("pi-mcp", extension, data);
}
```

## !!steps Converting one content block

Resource links become a bracketed text line with URI, title, MIME type and size, and name the `read_mcp_resource` tool when the server's resources are readable. Embedded binary resources are decoded: text-like MIME types (text, JSON, or any JSON or XML suffix) are shown as text, other blobs are saved to a temp file with an extension taken from the URI, and the model gets a pointer. Images and everything else go through `toLlmContent`.

```ts ! tools.ts
/** Model-facing content of one block of `server`'s result. */
async function blockToContent(
	server: string,
	block: ContentBlock,
	options: ConvertMcpResultOptions,
): Promise<(TextContent | ImageContent)[]> {
	// !mark
	if (block.type === "resource_link") {
		const details = [block.mimeType, block.size === undefined ? undefined : formatSize(block.size)].filter(Boolean);
		const read = options.readableResources ? `. Read it with ${READ_MCP_RESOURCE_TOOL} (server "${server}")` : "";
		const description = block.description ? `: ${block.description}` : "";
		return [
			{
				type: "text",
				text: `[Resource ${block.uri} "${block.title ?? block.name}"${details.length > 0 ? ` (${details.join(", ")})` : ""}${description}${read}]`,
			},
		];
	}
	// !mark
	if (block.type === "resource" && "blob" in block.resource && !block.resource.mimeType?.startsWith("image/")) {
		const { uri, mimeType, blob } = block.resource;
		const data = Buffer.from(blob, "base64");
		// !mark
		if (isTextMimeType(mimeType)) return [{ type: "text", text: data.toString("utf8") }];
		const kind = `${mimeType ?? "unknown type"}, ${formatSize(data.length)}`;
		try {
			// !mark
			const path = await (options.saveOutput ?? saveToTempFile)(data, extensionOf(uri));
			return [{ type: "text", text: `[Binary resource ${uri} (${kind}) saved to ${path}]` }];
		} catch (error) {
			const reason = error instanceof Error ? error.message : String(error);
			return [{ type: "text", text: `[Binary resource ${uri} (${kind}) could not be saved: ${reason}]` }];
		}
	}
	return toLlmContent({ content: [block] });
}
```

## !!steps The whole result

`convertMcpResult` converts all blocks in parallel, falls back to the structured content when there are no blocks, and guarantees an error result is never empty.

The output limit is pi-mcp's `limitMcpContent`: text over 20 KB keeps its start and end with the middle cut out, in Codex's truncation format, followed by the path of the saved full text; images come after it. pi always passes a saver (the caller's, or `saveToTempFile`), so the model can read the full text with offset and limit.

The script-facing `structuredContent` is the original result minus `_meta`, so truncation never affects scripts, and `isError` is carried onto the result so the agent marks it as an error.

```ts ! tools.ts
export async function convertMcpResult(
	server: string,
	tool: string,
	result: CallToolResult,
	options: ConvertMcpResultOptions = {},
): Promise<AgentToolResult<McpToolDetails>> {
	// !mark(1:6)
	// Without content blocks, toLlmContent falls back to the structured content as JSON.
	const converted: (TextContent | ImageContent)[] =
		result.content.length > 0 ? await toModelContent(server, result.content, options) : toLlmContent(result);
	if (result.isError && textOf(converted) === "") {
		converted.push({ type: "text", text: `MCP tool ${server}/${tool} returned an error` });
	}
	// !mark
	const { content, fullOutputPath } = await limitMcpContent(converted, options.saveOutput ?? saveToTempFile);
	// !mark
	const { _meta: _ignored, ...scriptResult } = result;
	return {
		content,
		details: { server, tool, ...(fullOutputPath ? { fullOutputPath } : {}) },
		structuredContent: scriptResult as unknown as JsonValue,
		// !mark
		...(result.isError ? { isError: true } : {}),
	};
}
```

## !!steps A result schema that describes itself

Every tool declares an output schema for the `CallToolResult` scripts receive, and codemode renders it into the tool's TypeScript declaration. Codemode used to recognise this shape and fill in MCP types itself; now the schema carries everything.

Content blocks get one compact type with the fields scripts read most (`text`, `data`, `mimeType`), open to the rest. `structuredContent` is the server's own output schema when it declares one, and otherwise the empty schema `{}`, since MCP now allows any JSON value there, arrays and null included. `_meta` is no longer declared because conversion drops it, and `additionalProperties` leaves room for fields newer protocol versions add.

```ts ! tools.ts
const CONTENT_BLOCK_SCHEMA = {
	type: "object",
	properties: {
		type: { enum: ["text", "image", "audio", "resource_link", "resource"] },
		text: { type: "string" },
		data: { type: "string" },
		mimeType: { type: "string" },
	},
	required: ["type"],
	additionalProperties: true,
};
// ...
export function createMcpResultSchema(structuredContentSchema: Record<string, unknown> | undefined): TSchema {
	return {
		type: "object",
		properties: {
			// !mark
			content: { type: "array", items: CONTENT_BLOCK_SCHEMA },
			// Servers may send structured content without declaring a schema for it, and it may be any JSON value.
			// !mark(1:3)
			structuredContent: structuredContentSchema
				? relocateSchema(structuredContentSchema, "#/properties/structuredContent")
				: {},
			isError: { type: "boolean" },
		},
		required: ["content"],
		// Fields newer protocol versions add.
		additionalProperties: true,
	} as unknown as TSchema;
}
```

## !!steps Relocating the server's references

Nesting the server's schema under `structuredContent` would break its local references: `#/$defs/Item` would now point at the root of the result schema. `relocateSchema` rewrites every local `$ref` to sit below the new pointer, so `#/$defs/Item` becomes `#/properties/structuredContent/$defs/Item` and resolves to the same subschema.

The walk has to know a little JSON Schema to avoid false rewrites. Under data keywords such as `const` or `enum`, a `$ref` key is a value, not a reference, so the value is copied unchanged. Under map keywords such as `properties` or `$defs`, the keys are names (a property may well be called `$ref`), so only their values are walked.

```ts ! tools.ts
/** Keywords whose values are data, so a `$ref` key in them is not a reference. */
const SCHEMA_DATA_KEYWORDS: ReadonlySet<string> = new Set(["const", "enum", "default", "examples"]);
/** Keywords whose values map names to schemas, so their keys are names, not keywords. */
const SCHEMA_MAP_KEYWORDS: ReadonlySet<string> = new Set([
	"properties",
	"patternProperties",
	"dependentSchemas",
	"dependencies",
	"$defs",
	"definitions",
]);
// ...
function relocateSchema(schema: unknown, pointer: string): unknown {
	if (Array.isArray(schema)) return schema.map((item) => relocateSchema(item, pointer));
	if (typeof schema !== "object" || schema === null) return schema;
	const relocated: Record<string, unknown> = {};
	for (const [key, value] of Object.entries(schema)) {
		// !mark(1:2)
		if (key === "$ref" && typeof value === "string" && (value === "#" || value.startsWith("#/"))) {
			relocated[key] = `${pointer}${value.slice(1)}`;
		// !mark(1:2)
		} else if (SCHEMA_DATA_KEYWORDS.has(key)) {
			relocated[key] = value;
		// !mark
		} else if (SCHEMA_MAP_KEYWORDS.has(key) && typeof value === "object" && value !== null && !Array.isArray(value)) {
			relocated[key] = Object.fromEntries(
				Object.entries(value).map(([name, subschema]) => [name, relocateSchema(subschema, pointer)]),
			);
		} else {
			relocated[key] = relocateSchema(value, pointer);
		}
	}
	return relocated;
}
```

## !!steps Building the tool definition

The definition carries the label `server/tool`, a description that falls back from description to title to a generated sentence, and the exposure and namespace. Only the four boolean annotation hints survive. The input schema goes through pi-mcp's `normalizeMcpInputSchema`, which adds a missing `type: "object"` and an empty `properties`, since some providers reject object schemas without them.

`execute` obtains the client lazily through `getClient`, forwards progress notifications as tool updates, and finishes with `convertMcpResult`.

```ts ! tools.ts
export function createMcpToolDefinition(options: {
	server: string;
	tool: McpTool;
	name: string;
	exposure: McpExposure;
	namespace: ToolNamespace;
	timeoutMs: number;
	getClient: () => Promise<McpToolCaller>;
	/** Whether `read_mcp_resource` can read the server's resources. */
	readableResources?: () => boolean;
}): ToolDefinition<TSchema, McpToolDetails> {
	const { server, tool } = options;
	const title = tool.title ?? tool.annotations?.title;
	const annotations = toToolAnnotations(tool);
	const label = `${server}/${tool.name}`;
	return {
		name: options.name,
		label,
		// !mark
		description: tool.description?.trim() || title || `MCP tool ${tool.name} from server ${server}`,
		// An object schema, which is what TypeBox schemas are at runtime.
		// !mark
		parameters: normalizeMcpInputSchema(tool.inputSchema) as unknown as TSchema,
		outputSchema: createMcpResultSchema(tool.outputSchema),
		exposure: toToolExposure(options.exposure),
		namespace: options.namespace,
		...(annotations ? { annotations } : {}),
		...createMcpToolRenderers(label),
		// !mark(1:3)
		async execute(_toolCallId, params, signal, onUpdate) {
			const client = await options.getClient();
			const result = await client.callTool(tool.name, (params ?? {}) as Record<string, unknown>, {
				signal,
				timeoutMs: options.timeoutMs,
				onProgress: (progress) => {
					const total = progress.total === undefined ? "" : `/${progress.total}`;
					const text = progress.message ?? `Progress ${progress.progress}${total}`;
					onUpdate?.({ content: [{ type: "text", text }], details: { server, tool: tool.name } });
				},
			});
			// !mark
			return convertMcpResult(server, tool.name, result, { readableResources: options.readableResources?.() });
		},
```

## !!steps Collapsed and expanded rendering

`createMcpToolRenderers` is exported separately because the label is needed before the tool is registered (a call can be shown while the server is still connecting). Results are colored by error state and, when collapsed, limited to 5 wrapped lines. The comment explains why: MCP results are often a single long JSON line, so logical lines would not limit anything. When the output was truncated, the full-output path is shown below.

```ts ! tools.ts
/** Renderers of calls to an MCP tool, labeled `server/tool`, also used before the tool is registered. */
export function createMcpToolRenderers(label: string): ToolRenderers {
	return {
		renderCall(args, theme, context) {
			const component = (context.lastComponent as Text | undefined) ?? new Text("", 0, 0);
			component.setText(formatToolCallWithArgs(label, args, theme, context.expanded));
			return component;
		},
		renderResult(result, options, theme, context) {
			const component = (context.lastComponent as Container | undefined) ?? new Container();
			component.clear();
			const output = getTextOutput(result, context.showImages).trim();
			if (!output) return component;
			const color = context.isError ? "error" : "toolOutput";
			const styled = replaceTabs(output)
				.split("\n")
				.map((line) => theme.fg(color, line))
				.join("\n");
			component.addChild(new Spacer(1));
			if (options.expanded) {
				component.addChild(new Text(styled, 0, 0));
			} else {
				// !mark(1:6)
				// Limit wrapped lines, not logical ones: MCP results are often one long JSON line.
				component.addChild(
					new VisualLinePreview({
						text: styled,
						maxVisualLines: OUTPUT_PREVIEW_LINES,
						keep: "start",
						formatHint: (hidden) =>
							`${theme.fg("muted", `... (${hidden} more lines,`)} ${keyHint("app.tools.expand", "to expand")}${theme.fg("muted", ")")}`,
					}),
				);
				// !mark(1:2)
				const fullOutputPath = (result.details as McpToolDetails | undefined)?.fullOutputPath;
				if (fullOutputPath) component.addChild(new Text(theme.fg("muted", `Full output: ${fullOutputPath}`), 0, 0));
			}
			return component;
		},
	};
}
```

The key invariant of the file is that conversion for the model (bounded, human-readable, with files saved on the side) and conversion for scripts (complete) are produced together in one result object. Other modules only need `createMcpToolDefinition`, `createMcpToolRenderers`, `toModelContent` and `saveToTempFile`; naming and limiting come straight from pi-mcp.
