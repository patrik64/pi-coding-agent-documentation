MCP servers can offer resources: files, schemas and other context that is read by URI rather than called like a tool. This file turns them into three ordinary pi tools: `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource`. The names and the JSON listing shape copy Codex and opencode on purpose, so models trained on those tools use them without instruction.

The tools take a `server` argument and span every connected server that has resources, instead of one tool per server. Results are post-processed by helpers from [tools.ts](/docs/src/extensions/mcp/tools.ts): the same output limit and the same content conversion as normal MCP tool calls.

The tool names are defined in [mcp-servers.ts](/docs/src/core/mcp-servers.ts), the definitions use the `ToolDefinition` type from [types.ts](/docs/src/core/extensions/types.ts), and [runtime.ts](/docs/src/extensions/mcp/runtime.ts) decides when to register them and supplies the connected servers.

## !!steps What a resource server looks like

`McpResourceServer` is the narrow interface this file needs from a connection: paged and complete listings of resources and templates, plus `readResource`. Keeping it small means the tools can be tested with plain objects and are decoupled from the client in [runtime.ts](/docs/src/extensions/mcp/runtime.ts).

```ts ! resources.ts
/** A connected server that offers resources. */
export interface McpResourceServer {
	name: string;
	timeoutMs: number;
	resourcesPage(cursor: string | undefined, options: McpRequestOptions): Promise<ListResourcesResult>;
	resourceTemplatesPage(cursor: string | undefined, options: McpRequestOptions): Promise<ListResourceTemplatesResult>;
	allResources(options: McpRequestOptions): Promise<Resource[]>;
	allResourceTemplates(options: McpRequestOptions): Promise<ResourceTemplate[]>;
	readResource(uri: string, options: McpRequestOptions): Promise<ReadResourceResult>;
}

/** MCP App user interfaces, which only hosts that render them can use. */
export function isMcpAppResource(item: { uri?: string; uriTemplate?: string; mimeType?: string }): boolean {
	const uri = item.uri ?? item.uriTemplate ?? "";
	return uri.startsWith("ui://") || /;\s*profile\s*=\s*"?mcp-app"?/i.test(item.mimeType ?? "");
}

/** A listed resource or template without `_meta` and icons, tagged with its server. */
function listed<T extends { _meta?: unknown }>(server: string, item: T): Record<string, unknown> {
	const { _meta, icons: _icons, ...rest } = item as T & { icons?: unknown };
	return { server, ...rest };
}
```

## !!steps Hiding MCP App interfaces

Resources with a `ui://` URI or a `profile=mcp-app` MIME type are user interfaces for hosts that can render them. A text-only model cannot use them, so `isMcpAppResource` lets every listing filter them out. `listed` also drops `_meta` and icons and tags each item with its server name.

```ts ! resources.ts
/** MCP App user interfaces, which only hosts that render them can use. */

}

/** A listed resource or template without `_meta` and icons, tagged with its server. */
function listed<T extends { _meta?: unknown }>(server: string, item: T): Record<string, unknown> {
	// !mark
	const { _meta, icons: _icons, ...rest } = item as T & { icons?: unknown };
	return { server, ...rest };
}
```

## !!steps Tool parameters and output schemas

Listing tools take an optional `server` and `cursor`. Reading requires both `server` and `uri`. The output schemas describe the JSON payload, including an `errors` array for servers that could not be listed. The schemas are plain objects, cast to `TSchema` at the point of use.

```ts ! resources.ts
const stringProperty = (description: string) => ({ type: "string", description });
const SERVER_FILTER = stringProperty("MCP server name. Omit to list every server with resources.");
const CURSOR = stringProperty("Opaque cursor from a previous call with the same server; omit for the first page.");
const LIST_PARAMETERS = {
	type: "object",
	properties: { server: SERVER_FILTER, cursor: CURSOR },
	additionalProperties: false,
};
const READ_PARAMETERS = {
	type: "object",
	properties: {
		server: stringProperty(
			"MCP server name exactly as configured. Must match the 'server' field returned by list_mcp_resources.",
		// !mark(1:5)
		),
		uri: stringProperty("Resource URI to read. Must be one of the URIs returned by list_mcp_resources."),
	},
	required: ["server", "uri"],
	additionalProperties: false,
};
```

## !!steps Argument handling and the result wrapper

`stringArgument` treats missing and null as absent, rejects non-strings, and trims. `jsonResult` sends the JSON text through `limitMcpContent`, so a huge listing is truncated for the model and the full text is saved to a temp file, while `structuredContent` keeps the whole payload for scripts.

```ts ! resources.ts
function stringArgument(params: unknown, key: string): string | undefined {
	const value = (params as Record<string, unknown> | undefined)?.[key];
	if (value === undefined || value === null) return undefined;
	if (typeof value !== "string") throw new Error(`${key} must be a string`);
	// !mark
	return value.trim() || undefined;
}

function errorMessage(error: unknown): string {
	return error instanceof Error ? error.message : String(error);
}

async function jsonResult(
	tool: string,
	server: string | undefined,
	payload: Record<string, unknown>,
): Promise<{ content: (TextContent | ImageContent)[]; details: McpToolDetails; structuredContent: JsonValue }> {
	// !mark
	const { content, fullOutputPath } = await limitMcpContent([{ type: "text", text: JSON.stringify(payload) }]);
	return {
		content,
		details: { server: server ?? "", tool, ...(fullOutputPath ? { fullOutputPath } : {}) },
		// !mark
		structuredContent: payload as unknown as JsonValue,
	};
}
```

## !!steps One page of one server, or everything

With a `server`, `list` returns a single page and passes the cursor through. Without one, it asks every server for all of its pages in parallel, sorted by name, and uses `Promise.allSettled` so one failing server becomes an entry in `errors` instead of failing the call. A cursor without a server is rejected, because cursors are only meaningful per server.

```ts ! resources.ts
		const serverName = stringArgument(params, "server");
		const cursor = stringArgument(params, "cursor");
		const visible = (item: T) => !isMcpAppResource(item as { uri?: string; uriTemplate?: string; mimeType?: string });
		if (serverName) {
			const server = findServer(serverName);
			const result = await page(server, cursor, { signal, timeoutMs: server.timeoutMs });
			return {
				server: server.name,
				[key]: result.items.filter(visible).map((item) => listed(server.name, item)),
				...(result.nextCursor === undefined ? {} : { nextCursor: result.nextCursor }),
			};
		}
		// !mark
		if (cursor) throw new Error("cursor can only be used when a server is specified");
		const servers = [...options.servers()].sort((a, b) => a.name.localeCompare(b.name));
		// !mark
		const results = await Promise.allSettled(
			servers.map((server) => all(server, { signal, timeoutMs: server.timeoutMs })),
		);
		const items: Record<string, unknown>[] = [];
		const errors: { server: string; error: string }[] = [];
		results.forEach((result, index) => {
			const server = servers[index].name;
			// !mark(1:3)
			if (result.status === "fulfilled")
				items.push(...result.value.filter(visible).map((item) => listed(server, item)));
			else errors.push({ server, error: errorMessage(result.reason) });
		});
		return { [key]: items, ...(errors.length > 0 ? { errors } : {}) };
	};
```

## !!steps The listing tools

The two listing tools differ only in which methods they call and which key they use. Both are marked `readOnlyHint` and take their exposure from [tools.ts](/docs/src/extensions/mcp/tools.ts) through `toToolExposure`, so a deferred or codemode setup applies to resources as well.

```ts ! resources.ts
	const listResources: ToolDefinition<TSchema, McpToolDetails> = {
		name: LIST_MCP_RESOURCES_TOOL,
		label: LIST_MCP_RESOURCES_TOOL,
		description:
			"Lists resources provided by MCP servers. Resources allow servers to share data that provides context to language models, such as files, database schemas, or application-specific information. Prefer resources over web search when possible.",
		parameters: LIST_PARAMETERS as unknown as TSchema,
		outputSchema: LIST_OUTPUT_SCHEMA as unknown as TSchema,
		// !mark(1:2)
		exposure: toToolExposure(options.exposure),
		annotations: readOnly,
		async execute(_toolCallId, params, signal) {
			const payload = await list(
				params,
				signal,
				"resources",
				async (server, cursor, requestOptions) => {
					const result = await server.resourcesPage(cursor, requestOptions);
					return { items: result.resources, nextCursor: result.nextCursor };
				},
				(server, requestOptions) => server.allResources(requestOptions),
			);
			return jsonResult(LIST_MCP_RESOURCES_TOOL, stringArgument(params, "server"), payload);
		},
	};
```

## !!steps Reading a resource

`read_mcp_resource` validates both arguments and looks up the server. When a read returns several contents (a directory, for example), each is preceded by a text label with its URI so the model can tell them apart. The blocks are then converted like any tool output, and an empty result gets an explicit "is empty" text rather than nothing.

```ts ! resources.ts
			const serverName = stringArgument(params, "server");
			const uri = stringArgument(params, "uri");
			if (!serverName) throw new Error("server must be provided");
			if (!uri) throw new Error("uri must be provided");
			const server = findServer(serverName);
			const result = await server.readResource(uri, { signal, timeoutMs: server.timeoutMs });
			// !mark(1:3)
			// Several contents (for example a directory) are labeled with their URIs.
			const blocks: ContentBlock[] = result.contents.flatMap((contents) => [
				...(result.contents.length > 1 ? [{ type: "text" as const, text: `${contents.uri}:` }] : []),
				{ type: "resource" as const, resource: contents },
			]);
			const converted = await toModelContent(server.name, blocks);
			const { content, fullOutputPath } = await limitMcpContent(
				// !mark
				converted.length > 0 ? converted : [{ type: "text", text: `Resource ${uri} is empty.` }],
			);
			const contents = result.contents.map(({ _meta: _ignored, ...rest }) => rest);
```

`createMcpResourceToolDefinitions` takes a `servers` callback instead of a fixed list, so the tools see servers that connect after registration. Failures to find a server produce a message naming the servers that do have resources, which helps a model correct a wrong name on the next call.
