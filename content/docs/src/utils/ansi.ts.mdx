`ansi.ts` is a vendored, trimmed copy of two small MIT-licensed libraries by Sindre Sorhus, kept in-repo to avoid a dependency. It exposes `stripAnsi`, used when output must be measured or stored as plain text, for example in [bash-executor.ts](/docs/src/core/bash-executor.ts) and tool rendering, and `splitIncompleteAnsiSuffix`, which lets a streaming caller hold back an escape sequence cut in half by a chunk boundary. The pattern has also diverged from upstream: it handles private-parameter CSI sequences such as mouse reports.

The license header is preserved at the top of the file, as the MIT terms require.

## !!steps The pieces of the pattern

The regex is now assembled at module level from named parts instead of inside an `ansiRegex()` function. An OSC sequence starts with `ESC ]` and ends at a string terminator, which may be BEL, `ESC \` or the 8-bit `0x9c`. A CSI sequence is an introducer, optional intermediates, numeric parameters separated by `;` or `:`, and a final byte.

`CSI_START` gained a first alternative for private-parameter sequences. A terminal in mouse mode reports clicks as `ESC[<35;59;1M`, and the old pattern treated the `<` as the final byte, which left `35;59;1M` in tool output. Now one `<`, `=` or `>` is accepted as a prefix, but only directly after a real CSI introducer. After a bare `ESC` those bytes still end the sequence, because `ESC =` and `ESC >` (keypad modes) are complete on their own and must not swallow digits of the text that follows.

```ts ! ansi.ts
// Valid string terminator sequences are BEL, ESC\, and 0x9c
const ST = "(?:\\u0007|\\u001B\\u005C|\\u009C)";

// OSC sequences: ESC ] ... ST
const OSC_START = "\\u001B\\]";

// CSI and related: ESC/C1, optional intermediates, optional params (supports ; and :), then final byte.
// A private prefix (<, =, >) is accepted only right after a real CSI introducer (ESC [ or 0x9B), so
// ESC[<35;59;1M (SGR mouse report) is stripped whole. After a bare ESC these bytes stay final bytes:
// ESC = and ESC > (keypad modes) must not swallow the digits of the text that follows.
// !mark
const CSI_START = "(?:(?:\\u001B\\[|\\u009B)[<=>]|[\\u001B\\u009B][[\\]()#;?]*)(?:\\d{1,4}(?:[;:]\\d{0,4})*)?";
const CSI_FINAL = "[\\dA-PR-TZcf-nq-uy=><~]";
```

## !!steps Complete and unfinished sequences

Two regexes are built from the parts. `ansiRegex` matches complete sequences and is compiled once with the global flag; the old `onlyFirst` option, which nothing used, is gone.

`unfinishedAnsiAtEndRegex` matches a sequence that has started but not finished at the very end of the text: an OSC without its terminator (a trailing `ESC` is allowed, since it may be the first half of `ESC \`), or a CSI start without its final byte, including a lone `ESC`. It exists for streamed output, where a chunk boundary can fall in the middle of a sequence.

```ts ! ansi.ts
// Complete sequences. OSC is non-greedy until the first ST.
const ansiRegex = new RegExp(`(?:${OSC_START}[\\s\\S]*?${ST})|${CSI_START}${CSI_FINAL}`, "g");

// Unfinished sequence at the end of the text: OSC without its ST (a trailing ESC may start ESC\),
// or CSI without its final byte.
const unfinishedAnsiAtEndRegex = new RegExp(
	`(?:${OSC_START}(?:[^\\u0007\\u009C\\u001B]|\\u001B(?!\\\\))*|${CSI_START})$`,
);

// Longest unfinished sequence held back while streaming. Longer ones are processed as-is.
const MAX_PENDING_ANSI_LENGTH = 256;
```

## !!steps Splitting streamed output

Stripping each chunk of a command's output separately broke sequences that straddled two chunks: the first half did not match the regex and stayed in the text, and the second half arrived as plain characters. `splitIncompleteAnsiSuffix` lets a streaming caller hold back the unfinished tail and prepend it to the next chunk. [bash-executor.ts](/docs/src/core/bash-executor.ts) does exactly that for user bash commands, and flushes whatever is still pending when the command ends.

It shares the plain-text fast path with `stripAnsi`, and only searches the last 256 characters, so a long OSC that never terminates cannot make every later chunk wait.

```ts ! ansi.ts
export function splitIncompleteAnsiSuffix(value: string): { complete: string; pending: string } {
	if (!value.includes("\u001B") && !value.includes("\u009B")) {
		return { complete: value, pending: "" };
	}
	// !mark(1:2)
	const windowStart = Math.max(0, value.length - MAX_PENDING_ANSI_LENGTH);
	const match = unfinishedAnsiAtEndRegex.exec(value.slice(windowStart));
	if (!match) {
		return { complete: value, pending: "" };
	}
	const splitAt = windowStart + match.index;
	return { complete: value.slice(0, splitAt), pending: value.slice(splitAt) };
}
```

## !!steps stripAnsi and its fast path

The function rejects non-strings with a `TypeError`. It then returns early when the value contains neither `ESC` nor the 8-bit CSI character, skipping the regex for the common plain-text case. The comment explains why `lastIndex` need not be reset: `replace` handles that itself.

```ts ! ansi.ts
export function stripAnsi(value: string): string {
	if (typeof value !== "string") {
		throw new TypeError(`Expected a \`string\`, got \`${typeof value}\``);
	}

	// !mark(1:4)
	// Fast path: ANSI codes require ESC (7-bit) or CSI (8-bit) introducer
	if (!value.includes("\u001B") && !value.includes("\u009B")) {
		return value;
	}

	// Even though the regex is global, we don't need to reset the `.lastIndex`
	// because unlike `.exec()` and `.test()`, `.replace()` does it automatically
	// and doing it manually has a performance penalty.
	return value.replace(ansiRegex, "");
}
```
