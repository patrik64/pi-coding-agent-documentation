Tools that run commands need to know which shell to launch, which environment to give it, how to clean its output, and how to kill it and its descendants. This file answers those four questions for macOS, Linux and Windows.

Consumers are [bash-executor.ts](/docs/src/core/bash-executor.ts), [bash.ts](/docs/src/core/tools/bash.ts) and [powershell.ts](/docs/src/core/tools/powershell.ts). The bin directory it prepends to `PATH` comes from [config.ts](/docs/src/config.ts), which is also where tools such as fd and ripgrep are installed by [tools-manager.ts](/docs/src/utils/tools-manager.ts).

## !!steps Shell configuration and legacy WSL bash

`ShellConfig` is the shell binary plus the args that precede the command. The legacy WSL launcher `bash.exe` in the Windows system directory cannot take `-c` reliably, so it gets `-s` and the command is sent on stdin via `commandTransport: "stdin"`. Everything else uses `-c`.

The launcher is recognized by comparing against `System32\bash.exe` and `Sysnative\bash.exe` under `SystemRoot`, so Windows installed on another drive or in another folder is handled; a `SystemRoot` that is not an absolute drive path matches nothing. The conventional `C:\Windows` pattern is only a fallback for when `SystemRoot` is unset. A comment notes that the same logic lives in the durable package and must be kept in sync.

```ts ! shell.ts
export interface ShellConfig {
	shell: string;
	args: string[];
	commandTransport?: "argv" | "stdin";
}

// Keep in sync with packages/durable/src/env/node.ts.
function isLegacyWslBashPath(path: string): boolean {
	const normalized = win32.normalize(path).toLowerCase();
	const systemRoot = process.env.SystemRoot;
	if (systemRoot) {
		if (!/^[a-z]:[\\/]/i.test(systemRoot)) return false;
		return ["System32", "Sysnative"].some(
			(directory) => normalized === win32.join(systemRoot, directory, "bash.exe").toLowerCase(),
		);
	}
	// Fall back to conventional launcher paths only when the Windows directory is unknown.
	return /^[a-z]:\\windows\\(?:system32|sysnative)\\bash\.exe$/.test(normalized);
}

function getBashShellConfig(shell: string): ShellConfig {
	return isLegacyWslBashPath(shell) ? { shell, args: ["-s"], commandTransport: "stdin" } : { shell, args: ["-c"] };
}
```

## !!steps Checking that a shell exists

Every existence check in this file goes through `shellPathExists`, a plain `access(F_OK)`. On Unix that is exactly what `existsSync` does. On Windows, `existsSync` adds a stat call that fails with `EACCES` for Windows Store app aliases, so a runnable Store-installed shell used to be rejected as missing.

```ts ! shell.ts
// Matches harness-v2's pathExists (packages/durable/src/env/node.ts).
// On Unix this is identical to existsSync() (both are access(F_OK)), just
// spelled with try/catch. On Windows we explicitly avoid existsSync(): its
// extra stat check rejects runnable Store aliases (nodejs/node#36790).
function shellPathExists(path: string): boolean {
	try {
		accessSync(path, constants.F_OK);
		return true;
	} catch {
		return false;
	}
}
```

## !!steps Looking up an executable

On Windows it runs `where` and then checks the first hit with `shellPathExists`. On Unix it trusts `which` without an existence check, so Termux and unusual filesystems work. Both have a 5 second timeout and swallow errors.

```ts ! shell.ts
function findExecutableOnPath(executable: string): string | null {
	if (process.platform === "win32") {
		// Windows: use 'where' and check the returned path.
		try {
			const result = spawnSync("where", [executable], {
				encoding: "utf-8",
				timeout: 5000,
				windowsHide: true,
			});
			if (result.status === 0 && result.stdout) {
				const firstMatch = result.stdout.trim().split(/\r?\n/)[0];
				if (firstMatch && shellPathExists(firstMatch)) {
					return firstMatch;
				}
			}
		} catch {
			// Ignore errors
		}
		return null;
	}
```

## !!steps Resolution order for bash

An explicit path wins and throws if missing, with no silent fallback. On Windows it tries Git for Windows under `ProgramFiles` and `ProgramFiles(x86)`, then `bash.exe` on `PATH`. The error message lists install options and which paths were searched.

```ts ! shell.ts
export function getShellConfig(customShellPath?: string): ShellConfig {
	// 1. Check user-specified shell path
	if (customShellPath) {
		if (shellPathExists(customShellPath)) {
			return getBashShellConfig(customShellPath);
		}
		throw new Error(`Custom shell path not found: ${customShellPath}`);
	}

	if (process.platform === "win32") {
		// 2. Try Git Bash in known locations
		const paths: string[] = [];
		const programFiles = process.env.ProgramFiles;
		if (programFiles) {
			paths.push(`${programFiles}\\Git\\bin\\bash.exe`);
		}
```

## !!steps Unix fallback

On Unix the order is `/bin/bash`, `bash` on PATH, then plain `sh -c`, so a minimal container still works.

```ts ! shell.ts
	// Unix: try /bin/bash, then bash on PATH, then fallback to sh
	if (shellPathExists("/bin/bash")) {
		return getBashShellConfig("/bin/bash");
	}

	const bashOnPath = findExecutableOnPath("bash");
	if (bashOnPath) {
		return getBashShellConfig(bashOnPath);
	}

	return { shell: "sh", args: ["-c"] };
}
```

## !!steps Finding PowerShell

PowerShell is Windows-only. The lookup prefers PowerShell 7 and checks each candidate on `PATH` first, then in its installation directory, because those directories can be on any drive and need not be on `PATH`: `pwsh.exe`, then `ProgramFiles\PowerShell\7\pwsh.exe`, then `powershell.exe`, then Windows PowerShell under `SystemRoot`. The fixed args skip profiles, disable prompts and bypass execution policy.

```ts ! shell.ts
export const POWERSHELL_ARGS = ["-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass", "-Command"] as const;
// ...
	let shell = findExecutableOnPath("pwsh.exe");
	// Installation directories may be on any drive and need not be on PATH.
	const programFiles = process.env.ProgramFiles;
	if (!shell && programFiles) {
		const pwsh7 = win32.join(programFiles, "PowerShell", "7", "pwsh.exe");
		if (shellPathExists(pwsh7)) shell = pwsh7;
	}

	shell ??= findExecutableOnPath("powershell.exe");
	const systemRoot = process.env.SystemRoot;
	if (!shell && systemRoot) {
		const windowsPowerShell = win32.join(systemRoot, "System32", "WindowsPowerShell", "v1.0", "powershell.exe");
		if (shellPathExists(windowsPowerShell)) shell = windowsPowerShell;
	}
```

## !!steps Environment with the managed bin directory

`getShellEnv` prepends pi's bin directory to `PATH` so commands the model runs can find the downloaded `fd` and `rg`. It looks up the actual key case-insensitively because Windows calls it `Path`, and it does not add the directory twice.

```ts ! shell.ts
export function getShellEnv(): NodeJS.ProcessEnv {
	const binDir = getBinDir();
	const pathKey = Object.keys(process.env).find((key) => key.toLowerCase() === "path") ?? "PATH";
	const currentPath = process.env[pathKey] ?? "";

	const hasBinDir = pathEntries.includes(binDir);
	const updatedPath = hasBinDir ? currentPath : [binDir, currentPath].filter(Boolean).join(delimiter);
```

## !!steps Sanitizing binary output

Control characters other than tab, newline and carriage return are removed, along with `U+FFF9` to `U+FFFB`, which crash the string-width measurement used by the terminal UI. The regex only matches single UTF-16 code units, so surrogate pairs cannot be split.

```ts ! shell.ts
export function sanitizeBinaryOutput(str: string): string {
	// All removed characters are single UTF-16 code units, so surrogate pairs are never split.
	return str.replace(/[\x00-\x08\x0B\x0C\x0E-\x1F\uFFF9-\uFFFB]/g, "");
}
```

## !!steps Tracking detached children

Commands run in their own process group so they can be killed as a unit. Their pids are tracked in a set so `killTrackedDetachedChildren` can kill all of them when pi receives a shutdown signal.

```ts ! shell.ts
const trackedDetachedChildPids = new Set<number>();

export function trackDetachedChildPid(pid: number): void {
	trackedDetachedChildPids.add(pid);
}

export function untrackDetachedChildPid(pid: number): void {
	trackedDetachedChildPids.delete(pid);
}

export function killTrackedDetachedChildren(): void {
	for (const pid of trackedDetachedChildPids) {
		killProcessTree(pid);
	}
	trackedDetachedChildPids.clear();
}
```

## !!steps Killing a whole tree on Windows

On Windows it runs `taskkill /F /T` from the System32 directory so a poisoned `PATH` cannot substitute it, and consumes the async `error` event. The directory falls back to `C:\Windows` when `SystemRoot` is unset or empty; the `||` replaced a `??`, which let an empty value through.

```ts ! shell.ts
export function killProcessTree(pid: number): void {
	if (process.platform === "win32") {
		// Use the trusted System32 executable so cleanup does not depend on PATH.
```

## !!steps Killing a process group on Unix

On Unix it sends `SIGKILL` to the negative pid, which targets the whole process group, and falls back to the single pid if that throws. On macOS the group is stopped with `SIGSTOP` first. macOS delivers a group signal to members one by one, so a killed child can wake its waiting shell before the shell itself is signalled, and in `a; b` the shell could start `b` during cancellation. Stopping the group first narrows that window; as the comment says, it is best-effort rather than an atomic freeze, and a failed stop never prevents the kill. Linux signals the whole group under one lock, so it needs no such step.

```ts ! shell.ts
		if (process.platform === "darwin") {
			// macOS signals group members individually after releasing the group lock. A killed
			// child can wake its waiting shell before that shell is signalled, letting `a; b`
			// start b during cancellation (#11252). Stop the group first to reduce this race;
			// this is best-effort, not an atomic freeze. SIGKILL also kills stopped processes.
			// Linux holds tasklist_lock across group signalling; child exit notification needs
			// its write lock, so the shell is signalled before observing the killed child's exit.
			try {
				process.kill(-pid, "SIGSTOP");
			} catch {
				// A failed stop must not prevent the kill attempt or its single-process fallback.
			}
		}
		// Use SIGKILL on Unix/Linux/Mac
		try {
			process.kill(-pid, "SIGKILL");
		} catch {
			// Fallback to killing just the child if process group kill fails
			try {
				process.kill(pid, "SIGKILL");
			} catch {
				// Process already dead
			}
		}
```

</Scrollycoding>

The kill path is `SIGKILL` only, with no graceful `SIGTERM` first, so commands get no chance to clean up. The negative-pid trick only works if the child was spawned detached into its own group, which is why tracking and detaching go together.
