Version checks, catalog downloads and tool downloads are simple GETs that should survive a flaky connection. `fetchWithRetry` retries transport failures and transient HTTP statuses a couple of times, and enforces both an overall deadline and a per-attempt one.

It is used by [version-check.ts](/docs/src/utils/version-check.ts), [tools-manager.ts](/docs/src/utils/tools-manager.ts) and [remote-catalog-provider.ts](/docs/src/core/remote-catalog-provider.ts). The doc comment is explicit that it must not be used for model requests.

<Scrollycoding>

## !!steps Options and retryable statuses

Retryable statuses are 408, 425, 429 and the 5xx gateway family. Defaults are two retries and status retries on.

```ts ! management-http.ts
const RETRYABLE_STATUS_CODES = new Set([408, 425, 429, 500, 502, 503, 504]);

export interface FetchRetryOptions {
	/** Number of additional attempts after the initial request. Defaults to two. */
	maxRetries?: number;
	/** Retry transient HTTP responses as well as transport failures. Defaults to true. */
	retryOnStatus?: boolean;
	/** Overall time budget shared by all attempts. */
	timeoutMs?: number;
	/** Per-attempt timeout. A new timeout is created for every attempt. */
	attemptTimeoutMs?: number;
}
```

## !!steps The contract

The comment explains scope: transport-level, immediate, no backoff delay. Caller cancellation and the overall `timeoutMs` end the whole operation, while `attemptTimeoutMs` only aborts the current try.

```ts ! management-http.ts
/**
 * Fetch a management HTTP resource with a bounded immediate retry.
 *
 * This is intentionally a transport-level helper for idempotent management
 * requests (version checks, catalogs, and downloads). It must not be used for
 * agent/model operations: those can fail after the HTTP request starts and are
 * retried by their semantic caller instead.
 *
 * Caller cancellation and timeoutMs are terminal. attemptTimeoutMs aborts
 * only the current attempt so a hung connection can be retried.
 */
```

## !!steps Normalizing options and signals

`maxRetries` is floored and clamped at zero, with non-finite values replaced by 2. The overall timeout signal is created once, outside the loop, so it covers every attempt. Each iteration first throws if the caller or the deadline has already aborted.

```ts ! management-http.ts
	const maxRetries =
		options.maxRetries === undefined || !Number.isFinite(options.maxRetries)
			? 2
			: Math.max(0, Math.floor(options.maxRetries));
	const retryOnStatus = options.retryOnStatus ?? true;
	const parentSignal = init?.signal ?? undefined;
	const timeoutSignal =
		options.timeoutMs !== undefined && options.timeoutMs > 0 ? AbortSignal.timeout(options.timeoutMs) : undefined;
	const attemptTimeoutMs =
		options.attemptTimeoutMs !== undefined && options.attemptTimeoutMs > 0 ? options.attemptTimeoutMs : undefined;

	for (let attempt = 0; ; attempt++) {
		parentSignal?.throwIfAborted();
		timeoutSignal?.throwIfAborted();
```

## !!steps Combining signals per attempt

A new per-attempt timeout is created each time and merged with the others using `AbortSignal.any`. The fetch is called with the merged signal.

```ts ! management-http.ts

			(signal): signal is AbortSignal => signal !== undefined,
		);
		const signal = signals.length > 1 ? AbortSignal.any(signals) : signals[0];
```

## !!steps Retrying on status

A retryable status with attempts left drains the body with `cancel()` so the connection can be released, then the loop continues. Any other response, including an error status after retries are used up, is returned to the caller.

```ts ! management-http.ts
			const shouldRetry = retryOnStatus && RETRYABLE_STATUS_CODES.has(response.status) && attempt < maxRetries;
			if (!shouldRetry) return response;
			try {
				await response.body?.cancel();
			} catch {
				// The response is being discarded before a retry. There is nothing useful to
				// do if cancelling its body also fails.
			}
```

## !!steps Deciding whether an error is final

Errors are rethrown when the caller aborted, the overall deadline fired, or retries are exhausted. A bare `AbortError` is also rethrown, unless it came from the per-attempt timeout or an overall timeout is configured. Everything else loops again.

```ts ! management-http.ts
		} catch (error) {
			const attemptTimedOut =
				attemptTimeoutSignal?.aborted === true && !parentSignal?.aborted && !timeoutSignal?.aborted;
			if (
				parentSignal?.aborted ||
				timeoutSignal?.aborted ||
				(error instanceof Error &&
					error.name === "AbortError" &&
					!attemptTimedOut &&
					timeoutSignal === undefined) ||
				attempt >= maxRetries
			) {
				throw error;
			}
		}
	}
}
```
