Prompt caching makes long conversations cheap, but cache entries expire after minutes of inactivity. If a user pauses and then continues, the whole prompt is billed again at write or input price. `CacheWarmer` avoids that by re-sending the same request shortly before expiry, capped at one output token, so the provider counts it as a cache read and extends the entry.

Warming is not free, so each refresh is an economic decision: pay the small read cost now against the chance of avoiding a large miss later. The class is driven by [agent-session.ts](/docs/src/core/agent-session.ts), which tells it when a request was sent and when the agent settles. It sends requests through [model-runtime.ts](/docs/src/core/model-runtime.ts), records each refresh as a usage entry in [session-manager.ts](/docs/src/core/session-manager.ts), and reads its mode from [settings-manager.ts](/docs/src/core/settings-manager.ts). See also [cache-stats.ts](/docs/src/core/cache-stats.ts).

## !!steps Safety constants

Three limits bound the behavior. Streaming warming stops an hour after the real request. Idle warming stops after 30 minutes, because the continuation estimate gets worse with age. A refresh is sent only if it is expected to save five cents. The idle probability of 0.15 is a measured constant, not a per-session estimate.

```ts ! cache-warmer.ts
/** Streaming warming never continues past this long after the real request that started it. */
const MAX_WARMING_AGE_MS = 60 * 60_000;
/** Idle warming uses a shorter horizon because continuation estimates become less reliable with age. */
const MAX_IDLE_WARMING_AGE_MS = 30 * 60_000;
/** A refresh is sent only when it is expected to save at least this many dollars. */
const CACHE_WARMING_MINIMUM_EXPECTED_SAVINGS = 0.05;
/**
 * Chance that a real request arrives before the cache entry expires while the
 * agent sits idle. Measured from our own usage; per-session estimates were not
 * better than this constant.
 */
const IDLE_CONTINUATION_PROBABILITY = 0.15;
```

## !!steps Timing and TTL

The delay is 90% of the lifetime but never closer than ten seconds to expiry. Lifetimes of ten seconds or less cannot be warmed. The lifetime itself comes from the model's `promptCache` table for the retention tier in use, chosen by the request option or the `PI_CACHE_RETENTION` environment variable.

```ts ! cache-warmer.ts
/** Refresh at 90% of the TTL while preserving at least ten seconds of margin. */
export function getCacheWarmingDelayMs(ttlMs: number): number | undefined {
	if (ttlMs <= 10_000) return undefined;
	return Math.max(1, Math.floor(Math.min(ttlMs * 0.9, ttlMs - 10_000)));
}

// ...
export function getPromptCacheTtlMs(model: Model<Api>, options: SimpleStreamOptions | undefined): number | undefined {
	const retention =
		options?.cacheRetention ??
		(getProviderEnvValue("PI_CACHE_RETENTION", options?.env) === "long" ? "long" : "short");
	if (retention === "none") return undefined;
	const seconds = model.promptCache?.[retention];
	return seconds === undefined ? undefined : seconds * 1000;
}
```

## !!steps When replaying is unsafe

Capping output at one token also changes `max_tokens`. For Anthropic models that use budget-based thinking, the thinking budget derives from `max_tokens`, and the provider keys the message cache on it, so the replay would miss the cache and might still think for thousands of tokens. Only requests without reasoning, on other APIs, or on models forced to adaptive thinking are replayable.

```ts ! cache-warmer.ts
export function isReplayable(model: Model<Api>, options: SimpleStreamOptions | undefined): boolean {
	if (!options?.reasoning || model.api !== "anthropic-messages") return true;
	return (model as Model<"anthropic-messages">).compat?.forceAdaptiveThinking === true;
}

/** Prompt size of the most recent real request on the branch, as reported by the provider. */
function lastPromptTokens(entries: SessionEntry[]): number {
	for (let index = entries.length - 1; index >= 0; index--) {
		const entry = entries[index];
		if (entry.type === "message" && entry.message.role === "assistant") {
			const usage = entry.message.usage;
			return usage.input + usage.cacheRead + usage.cacheWrite;
		}
	}
	return 0;
}
```

## !!steps The decision record

Each decision stores both prices, the probability and the expected savings, so `/session` can explain itself. Extensions get a smaller event with only the inputs and pi's proposed action, and may answer with `warm` or `stop`.

```ts ! cache-warmer.ts
export interface CacheWarmingDecision {
	/** "streaming" while the agent run that sent the request is still active. */
	phase: "streaming" | "idle";
	/** Price of this refresh: a cache read of the prompt plus one output token. */
	warmCost: number;
	/** Extra price of the next real request if the cache entry is lost. */
	missCost: number;
	/** Estimated chance that a real request arrives before the entry expires. */
	continuationProbability: number;
	/** `continuationProbability * missCost - warmCost`. */
	expectedSavings: number;
	/** False when the prompt size or the model's prices are unknown. */
	economicsAvailable: boolean;
	/** Pi's decision: "warm" when `expectedSavings` is at least $0.05. */
	action: CacheWarmingAction;
}
```

## !!steps Run state and the class

One `ActiveRun` holds the original request, a timer, an abort controller and deadlines. `isCurrent` is a callback from the session that turns false when the model or messages no longer match, since replaying a stale request would warm the wrong entry. The class depends only on narrow `Pick` types of its collaborators, which keeps it easy to test.

```ts ! cache-warmer.ts
export class CacheWarmer {
	private run?: ActiveRun;
	private inactive: CacheWarmingStatus;
	private readonly models: Pick<ModelRuntime, "streamSimple">;
	private readonly sessionManager: Pick<SessionManager, "appendUsage" | "getBranch">;
	private readonly getMode: () => CacheWarmingMode;
	/** Lets extensions override `event.action`; failures fall back to pi's decision. */
	private readonly decide: (event: CacheWarmingDecisionEvent) => Promise<CacheWarmingAction>;
	/** Called with the persisted usage entry after each successful refresh. */
	onWarmed?: (entry: UsageEntry) => void;
```

## !!steps Starting a run

`start` first clears any previous run, then walks a series of refusals, each recording a human-readable reason that `status` later shows: mode off, request not replayable, no cache lifetime, no usable delay. Only if all pass is a run created in the `streaming` phase and scheduled.

```ts ! cache-warmer.ts
	start(request: CacheWarmRequest, isCurrent: () => boolean): void {
		this.clearRun();
		const mode = this.getMode();
		if (mode === "off") {
			this.stop("cache warming disabled");
			return;
		}
		if (!isReplayable(request.model, request.options)) {
			this.stop("request cannot be replayed safely");
			return;
		}
		const ttlMs = getPromptCacheTtlMs(request.model, request.options);
```

## !!steps Scheduling and late timers

Each schedule computes the next fire time and a refresh deadline halfway through the remaining margin. A timer that fires after sleep or a blocked event loop could land after expiry, in which case the refresh would be a full-price write, so a missed deadline stops warming instead. The timer is unref'd so it never keeps the process alive.

```ts ! cache-warmer.ts
	private schedule(run: ActiveRun): void {
		run.extensionOverride = false;
		run.nextWarmAt = Date.now() + run.delayMs;
		// A timer can run late after sleep or event-loop blockage. Keep half of
		// the planned pre-expiry margin for that delay and request dispatch; a
		// late refresh is likely a full-price cache write, not a cache warm.
		run.refreshDeadlineAt = run.nextWarmAt + Math.floor((run.ttlMs - run.delayMs) / 2);
		const deadline = run.startedAt + (run.phase === "idle" ? MAX_IDLE_WARMING_AGE_MS : MAX_WARMING_AGE_MS);
		if (run.nextWarmAt > deadline || Date.now() >= deadline) {
			this.stop(run.phase === "idle" ? "30-minute idle safety limit reached" : "one-hour safety limit reached");
			return;
		}
		run.timer = setTimeout(() => void this.refresh(run), Math.max(0, run.nextWarmAt - Date.now()));
		run.timer.unref?.();
	}
```

## !!steps Streaming versus idle

When the agent run settles, mode `streaming` stops warming immediately. Otherwise the run flips to the `idle` phase, which uses the shorter 30-minute horizon and the low continuation probability. The mode setting therefore controls whether warming outlives the agent turn at all.

```ts ! cache-warmer.ts
	onAgentSettled(): void {
		const run = this.run;
		if (!run) return;
		if (this.getMode() === "streaming") {
			this.stop("agent run settled");
			return;
		}
		run.phase = "idle";
		const deadline = run.startedAt + MAX_IDLE_WARMING_AGE_MS;
		if (run.nextWarmAt > deadline || Date.now() >= deadline) {
			this.stop("30-minute idle safety limit reached");
		}
	}
```

## !!steps The refresh path

On timer fire the run is validated, the decision evaluated, and extensions consulted; a thrown extension handler falls back to pi's choice. The request is replayed with `maxTokens: 1` and no retries, under the run's abort signal. Success is persisted as a `cache_warm` usage entry, but errored or aborted replies are not. Any exception is swallowed because warming must never disturb the real agent run, and the next refresh is scheduled only if this run is still the active one.

```ts ! cache-warmer.ts
		run.extensionOverride = extensionOverride;
		try {
			const message = await this.models
				.streamSimple(run.model, run.context, {
					...run.options,
					maxTokens: 1,
					maxRetries: 0,
					signal: run.controller.signal,
				})
				.result();
			if (!this.validateRun(run)) return;
			if (message.stopReason !== "error" && message.stopReason !== "aborted") {
				const entry = this.sessionManager.appendUsage(
					"cache_warm",
					message.provider,
					message.responseModel ?? message.model,
					message.usage,
					extensionOverride ? "extension override" : undefined,
				);
				this.onWarmed?.(entry);
			}
		} catch {
			// Cache warming is best-effort and must not affect the active agent run.
		}
		if (this.run === run) this.schedule(run);
```

## !!steps The economics

A hit costs a cache read of the last prompt. A miss costs a cache write if the model charges for writes, otherwise plain input. The cost of a miss is the difference, so only the avoidable extra counts. Expected savings is probability times that extra, minus the cost of the warm request itself. While the agent is streaming the probability is 1, since a request is in progress; idle uses the 0.15 constant.

```ts ! cache-warmer.ts
	private evaluate(run: ActiveRun): CacheWarmingDecision {
		const model = run.model;
		const promptTokens = lastPromptTokens(this.sessionManager.getBranch());
		const cacheHitCost = price(model, { cacheRead: promptTokens });
		const cacheMissCost = price(
			model,
			model.cost.cacheWrite > 0 ? { cacheWrite: promptTokens } : { input: promptTokens },
		);
		const warmCost = price(model, { cacheRead: promptTokens, output: 1 });
		const missCost = Math.max(0, cacheMissCost - cacheHitCost);
		const continuationProbability = run.phase === "idle" ? IDLE_CONTINUATION_PROBABILITY : 1;
		const economicsAvailable = promptTokens > 0 && (cacheHitCost > 0 || cacheMissCost > 0);
		const expectedSavings = continuationProbability * missCost - warmCost;
```

## !!steps Status text

The formatters at the bottom turn a status into one line for `/session`, such as a countdown to the next decision, or the reason warming stopped. A persisted warm is rendered in the transcript with its cost, trimming trailing zeros from the six-decimal figure.

```ts ! cache-warmer.ts
/** One-line transcript text for persisted cache-warming usage. */
export function formatCacheWarmingUsage(entry: UsageEntry): string {
	const note = entry.note ? ` (${entry.note})` : "";
	const cost = entry.usage.cost.total.toFixed(6).replace(/(\.\d{3}\d*?)0+$/, "$1");
	return `Cache warmed${note}: $${cost}`;
}
```

</Scrollycoding>

The class holds at most one run and every exit goes through `stop`, which clears the timer and aborts any in-flight replay, so state cannot leak between turns. The `MAX_WARMING_AGE_MS` window is measured from the original request, and refreshes never extend it.
