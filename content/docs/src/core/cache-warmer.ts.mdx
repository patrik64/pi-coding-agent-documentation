Prompt caching makes long conversations cheap, but cache entries expire after minutes of inactivity. If a user pauses and then continues, the whole prompt is billed again at write or input price. `CacheWarmer` avoids that by re-sending the same request shortly before expiry, capped at one output token, so the provider counts it as a cache read and extends the entry.

Warming is not free, so each refresh is an economic decision: pay the small read cost now against the chance of avoiding a large miss later. The numbers behind that decision (safety windows, refresh delay, cache lifetime, replay safety, expected savings) now live in pi-ai's `cache-warming` module, so other hosts can warm caches with the same policy. This file keeps the host side: one active run, its timer, the extension hook, status for `/session`, and persisting each refresh.

The class is driven by [agent-session.ts](/docs/src/core/agent-session.ts), which tells it when a request was sent and when the agent settles. It sends requests through [model-runtime.ts](/docs/src/core/model-runtime.ts), records each refresh as a usage entry in [session-manager.ts](/docs/src/core/session-manager.ts), and reads its mode from [settings-manager.ts](/docs/src/core/settings-manager.ts). [interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts) renders the warms in the transcript. See also [cache-stats.ts](/docs/src/core/cache-stats.ts).

## !!steps The policy comes from pi-ai

Everything numeric is imported. The two safety windows are one hour for streaming warming and 30 minutes for idle warming, both measured from the real request. A refresh is sent only if it is expected to save five cents. `getCacheWarmingDelayMs` schedules at 90% of the cache lifetime but never closer than ten seconds to expiry, and `getPromptCacheTtlMs` reads that lifetime from the model's `promptCache` table for the retention tier in use, chosen by the request option or the `PI_CACHE_RETENTION` environment variable.

The decision types are re-exported so existing importers of this module, such as the extension runner, keep working unchanged.

```ts ! cache-warmer.ts
import {
	type Api,
	CACHE_WARMING_MAX_AGE_MS,
	CACHE_WARMING_MAX_IDLE_AGE_MS,
	CACHE_WARMING_MINIMUM_EXPECTED_SAVINGS,
	type CacheWarmingAction,
	type CacheWarmingDecision,
	type Context,
	evaluateCacheWarming,
	getCacheWarmingDelayMs,
	getCacheWarmingRequestOptions,
	getPromptCacheTtlMs,
	isCacheWarmingReplayable,
	type Model,
	type ModelsSimpleStreamOptions,
} from "@earendil-works/pi-ai";
// ...

export type { CacheWarmingAction, CacheWarmingDecision };
```

## !!steps The one input this file supplies

The pi-ai evaluator needs the model, the phase and the prompt size. The prompt size comes from the session: the input, cache-read and cache-write tokens of the most recent assistant message on the branch, as reported by the provider.

With that, pi-ai prices a hit as a cache read of the prompt and a miss as a cache write (or plain input when the model does not charge for writes). The cost of a miss is the difference, so only the avoidable extra counts. Expected savings is the continuation probability times that extra, minus the cost of the warm request itself. While the agent is streaming the probability is 1, since a request is in progress; idle uses a measured constant of 0.15.

```ts ! cache-warmer.ts
/** Prompt size of the most recent real request on the branch, as reported by the provider. */
function lastPromptTokens(entries: SessionEntry[]): number {
	for (let index = entries.length - 1; index >= 0; index--) {
		const entry = entries[index];
		if (entry.type === "message" && entry.message.role === "assistant") {
			const usage = entry.message.usage;
			return usage.input + usage.cacheRead + usage.cacheWrite;
		}
	}
	return 0;
}
// ...
	private evaluate(run: ActiveRun): CacheWarmingDecision {
		return evaluateCacheWarming(run.model, lastPromptTokens(this.sessionManager.getBranch()), run.phase);
	}
```

## !!steps The extension event and the status

A full decision stores both prices, the probability, the expected savings and whether the economics could be computed at all, so `/session` can explain itself. Extensions get a smaller event with only the inputs and pi's proposed action, and may answer with `warm` or `stop`.

The status is what `/session` shows: inactive with a reason, a timer armed, or a refresh in flight. When warming stopped because of a decision, that decision is kept so the reason can include the numbers.

```ts ! cache-warmer.ts
export interface CacheWarmingDecisionEvent
	extends Pick<CacheWarmingDecision, "warmCost" | "missCost" | "continuationProbability" | "action"> {
	type: "cache_warming_decision";
}

export interface CacheWarmingDecisionEventResult {
	/** Override whether this refresh is sent. "stop" ends warming until the next real request. */
	action?: CacheWarmingAction;
}

export interface CacheWarmingStatus {
	/** "scheduled": a refresh timer is armed; "refreshing": a warm request is in flight. */
	state: "inactive" | "scheduled" | "refreshing";
	/** Why nothing is scheduled. */
	reason?: string;
	nextWarmAt?: number;
	/** The pending decision, or the decision that stopped warming. */
	decision?: CacheWarmingDecision;
	/** True when an extension changed `decision.action`. */
	extensionOverride?: boolean;
}
```

## !!steps Run state and the class

One `ActiveRun` holds the original request, a timer, an abort controller and deadlines. `isCurrent` is a callback from the session that turns false when the model or messages no longer match, since replaying a stale request would warm the wrong entry. The class depends only on narrow `Pick` types of its collaborators, which keeps it easy to test.

```ts ! cache-warmer.ts
export class CacheWarmer {
	private run?: ActiveRun;
	private inactive: CacheWarmingStatus;
	private readonly models: Pick<ModelRuntime, "streamSimple">;
	private readonly sessionManager: Pick<SessionManager, "appendUsage" | "getBranch">;
	private readonly getMode: () => CacheWarmingMode;
	/** Lets extensions override `event.action`; failures fall back to pi's decision. */
	private readonly decide: (event: CacheWarmingDecisionEvent) => Promise<CacheWarmingAction>;
	/** Called with the persisted usage entry after each successful refresh. */
	onWarmed?: (entry: UsageEntry) => void;
```

## !!steps Starting a run

`start` first clears any previous run, then walks a series of refusals, each recording a human-readable reason that `status` later shows: mode off, request not replayable, no cache lifetime, no usable delay. Only if all pass is a run created in the `streaming` phase and scheduled.

The replay check matters because capping output at one token also changes `max_tokens`. For Anthropic models with budget-based thinking, the thinking budget derives from `max_tokens` and the provider keys the message cache on it, so the replay would miss the cache and might still think for thousands of tokens. `isCacheWarmingReplayable` therefore accepts only requests without reasoning, on other APIs, or on models forced to adaptive thinking.

```ts ! cache-warmer.ts
	start(request: CacheWarmRequest, isCurrent: () => boolean): void {
		this.clearRun();
		const mode = this.getMode();
		if (mode === "off") {
			this.stop("cache warming disabled");
			return;
		}
		if (!isCacheWarmingReplayable(request.model, request.options)) {
			this.stop("request cannot be replayed safely");
			return;
		}
		const ttlMs = getPromptCacheTtlMs(request.model, request.options);
```

## !!steps Scheduling and late timers

Each schedule computes the next fire time and a refresh deadline halfway through the remaining margin. A timer that fires after sleep or a blocked event loop could land after expiry, in which case the refresh would be a full-price write, so a missed deadline stops warming instead. The timer is unref'd so it never keeps the process alive.

```ts ! cache-warmer.ts
	private schedule(run: ActiveRun): void {
		run.extensionOverride = false;
		run.nextWarmAt = Date.now() + run.delayMs;
		// A timer can run late after sleep or event-loop blockage. Keep half of
		// the planned pre-expiry margin for that delay and request dispatch; a
		// late refresh is likely a full-price cache write, not a cache warm.
		run.refreshDeadlineAt = run.nextWarmAt + Math.floor((run.ttlMs - run.delayMs) / 2);
		const deadline =
			run.startedAt + (run.phase === "idle" ? CACHE_WARMING_MAX_IDLE_AGE_MS : CACHE_WARMING_MAX_AGE_MS);
		if (run.nextWarmAt > deadline || Date.now() >= deadline) {
			this.stop(run.phase === "idle" ? "30-minute idle safety limit reached" : "one-hour safety limit reached");
			return;
		}
		run.timer = setTimeout(() => void this.refresh(run), Math.max(0, run.nextWarmAt - Date.now()));
		run.timer.unref?.();
	}
```

## !!steps Streaming versus idle

When the agent run settles, mode `streaming` stops warming immediately. Otherwise the run flips to the `idle` phase, which uses the shorter 30-minute horizon and the low continuation probability. The mode setting therefore controls whether warming outlives the agent turn at all. A mode change while a run is active goes through the same rules, so switching to `off`, or to `streaming` while idle, stops the run at once.

```ts ! cache-warmer.ts
	onAgentSettled(): void {
		const run = this.run;
		if (!run) return;
		if (this.getMode() === "streaming") {
			this.stop("agent run settled");
			return;
		}
		run.phase = "idle";
		const deadline = run.startedAt + CACHE_WARMING_MAX_IDLE_AGE_MS;
		if (run.nextWarmAt > deadline || Date.now() >= deadline) {
			this.stop("30-minute idle safety limit reached");
		}
	}
```

## !!steps The refresh path

On timer fire the run is validated, the decision evaluated, and extensions consulted; a thrown extension handler falls back to pi's choice. The request is replayed with the options from `getCacheWarmingRequestOptions`: the original options with one output token, no retries, the run's abort signal, and `disableContinuation`. That last flag exists for Anthropic message threads, where the server continues a conversation from the previous reply; a warm request repeats the last request and must not replace the session's thread.

Success is persisted as a `cache_warm` usage entry, but errored or aborted replies are not. Any exception is swallowed because warming must never disturb the real agent run, and the next refresh is scheduled only if this run is still the active one.

```ts ! cache-warmer.ts
		run.extensionOverride = extensionOverride;
		try {
			const message = await this.models
				.streamSimple(run.model, run.context, getCacheWarmingRequestOptions(run.options, run.controller.signal))
				.result();
			if (!this.validateRun(run)) return;
			if (message.stopReason !== "error" && message.stopReason !== "aborted") {
				const entry = this.sessionManager.appendUsage(
					"cache_warm",
					message.provider,
					message.responseModel ?? message.model,
					message.usage,
					extensionOverride ? "extension override" : undefined,
				);
				this.onWarmed?.(entry);
			}
		} catch {
			// Cache warming is best-effort and must not affect the active agent run.
		}
		if (this.run === run) this.schedule(run);
```

## !!steps Status text

The formatters at the bottom turn a status into one line for `/session`, such as a countdown to the next decision, or the reason warming stopped.

The transcript formatter takes a total cost rather than a single usage entry. Interactive mode collapses back-to-back warms with the same note into one line and updates its cumulative cost, while each warm is still persisted as its own usage entry. Trailing zeros are trimmed from the six-decimal figure.

```ts ! cache-warmer.ts
/** One-line transcript text for the total cost of one or more consecutive cache warms. */
export function formatCacheWarmingUsage(totalCost: number, note?: string): string {
	const noteText = note ? ` (${note})` : "";
	const cost = totalCost.toFixed(6).replace(/(\.\d{3}\d*?)0+$/, "$1");
	return `Cache warmed${noteText}: $${cost}`;
}
```

The class holds at most one run and every exit goes through `stop`, which clears the timer and aborts any in-flight replay, so state cannot leak between turns. The safety windows are measured from the original request, and refreshes never extend them.
