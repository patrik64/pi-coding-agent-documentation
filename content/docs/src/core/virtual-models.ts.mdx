A virtual model looks like any other model in the model picker, but it is not backed by an API. Selecting it means "let this router decide which real model answers each request". An extension can register one to implement, say, a cheap-first policy that escalates after failures.

The key invariant is stated in the header comment: everything below the routing step only sees physical models. Providers stream physical models, and assistant messages record physical models. A virtual model never reaches a provider. This file defines the types a router implements, helpers that recover the selection and router state from a session branch, and the wrapper that adds virtual entries to a provider's catalog. Catalog storage is handled by [model-runtime.ts](/docs/src/core/model-runtime.ts) and [model-registry.ts](/docs/src/core/model-registry.ts).

## !!steps Marker constants and persisted state

A virtual model is recognized purely by its `api` value, `pi-virtual`. Router state is persisted as a custom entry in the session, under the type `pi.virtual-model-state`, with the provider, model id and an arbitrary JSON-serializable state. Because it lives on the branch, forking a session forks the router's memory too. See [session-manager.ts](/docs/src/core/session-manager.ts) for the entry types.

```ts ! virtual-models.ts
/** API id of virtual catalog entries. Requests for it fail unless routed first. */
export const VIRTUAL_MODEL_API = "pi-virtual";

/** Custom entry type that stores router state on the session branch. */
export const VIRTUAL_MODEL_STATE_ENTRY = "pi.virtual-model-state";

/** Data of a `pi.virtual-model-state` custom entry. */
export interface VirtualModelStateData<TState = unknown> {
	provider: string;
	modelId: string;
	state: TState;
}
```

## !!steps What a router sees

A `ModelRouteRequest` gives the router the selected virtual model and thinking level, the reason for the request, the model and level of the latest successful response, the previous failure for retries, the saved state and the full message list. The reason distinguishes user turns, continuations after tool results, automatic retries and `direct` calls outside the agent loop, such as compaction summaries.

```ts ! virtual-models.ts
export type ModelRouteReason = "user" | "continuation" | "retry" | "direct";

export interface ModelRouteRequest<TState = unknown> {
	/** The selected virtual model. */
	model: Model<Api>;
	/** The selected thinking level. Its meaning is up to the router. */
	thinkingLevel: ModelThinkingLevel;
	reason: ModelRouteReason;
	/** Physical model and thinking level of the latest successful response in `messages`. */
	previous?: { model: Model<Api>; thinkingLevel?: ModelThinkingLevel };
// ...
	/** Conversation for this request, including system messages. */
	messages: readonly Message[];
	signal?: AbortSignal;
}
```

## !!steps The route result and the definition

A router returns the physical model, thinking level and optionally new state. State is saved on the branch unless it is the request's own state; returning undefined keeps it, and `direct` requests ignore it.

`VirtualModelDefinition` is what an extension registers: provider, id, display name, offered thinking levels (default only `off`), optional limits shown before the first response, accepted inputs and the `route` function, which may be async. The id must not collide with a physical model of the same provider.

```ts ! virtual-models.ts
export interface ModelRoute<TState = unknown> {
	model: Model<Api>;
	thinkingLevel: ModelThinkingLevel;
// ...
	state?: TState;
}

export interface VirtualModelDefinition<TState = unknown> {
	/** Provider the virtual model is listed under. May be a provider with physical models. */
	provider: string;
	/** Model id. Must not be the id of a physical model of `provider`. */
	id: string;
	name: string;
	/** Thinking levels offered for selection. Defaults to `["off"]`. */
// ...
	/** Pick the physical model, which must have credentials, and thinking level for one request. */
	route(request: ModelRouteRequest<TState>): ModelRoute<TState> | Promise<ModelRoute<TState>>;
}
```

## !!steps Finding the latest real answer

`isVirtualModel` is the single check used everywhere. `findLatestResponse` scans messages from the end for an assistant message whose stop reason is neither `error` nor `aborted`. Skipping failures matters because a failed message may still name the virtual model, while a successful one always names the physical model that answered.

```ts ! virtual-models.ts
export function isVirtualModel(model: { api: string }): boolean {
	return model.api === VIRTUAL_MODEL_API;
}

/** Latest successful response. Its model is physical: failed or aborted requests, including failed routing, are skipped. */
export function findLatestResponse(messages: readonly AgentMessage[]): AssistantMessage | undefined {
	for (let i = messages.length - 1; i >= 0; i--) {
		const message = messages[i];
		// !mark
		if (message.role === "assistant" && message.stopReason !== "error" && message.stopReason !== "aborted") {
			return message;
		}
	}
	return undefined;
}
```

## !!steps Recovering the selection from a branch

After a reload the session must know which model is selected. The scan goes backwards. An explicit `model_change` wins immediately. Otherwise the last non-virtual assistant message is a candidate, but if the last `model_change` before it named a registered virtual model, that virtual selection holds, since the response only records the physical model it was routed to.

If the virtual model is no longer registered, the selection falls back to the physical model that answered. Only one catalog lookup is ever made.

```ts ! virtual-models.ts
export function getBranchSelection(
	branch: readonly SessionEntry[],
	getModel: (provider: string, modelId: string) => Model<Api> | undefined,
): { provider: string; modelId: string } | undefined {
	for (let i = branch.length - 1; i >= 0; i--) {
		const entry = branch[i];
		if (entry.type === "model_change") {
			return { provider: entry.provider, modelId: entry.modelId };
		}
		// !mark(1:5)
		if (entry.type === "message" && entry.message.role === "assistant" && !isVirtualModel(entry.message)) {
			const response = { provider: entry.message.provider, modelId: entry.message.model };
			const change = findLastModelChange(branch, i);
			const model = change && getModel(change.provider, change.modelId);
			return change && model && isVirtualModel(model) ? change : response;
		}
	}
	return undefined;
}
```

## !!steps Reading router state and building the catalog entry

`getVirtualModelState` scans backwards for the newest state entry matching the provider and model id. `createVirtualModel` builds the `Model` object: a thinking level map that marks offered levels as themselves and everything else as `null`, `reasoning` true if any level other than `off` is offered, zero cost, an empty base URL, and unknown limits as 0.

```ts ! virtual-models.ts
export function createVirtualModel(definition: Omit<VirtualModelDefinition, "route">): Model<Api> {
	const levels = definition.thinkingLevels ?? ["off"];
	const thinkingLevelMap: ThinkingLevelMap = {};
	// !mark
	for (const level of THINKING_LEVELS) thinkingLevelMap[level] = levels.includes(level) ? level : null;
	return {
		id: definition.id,
		name: definition.name,
		api: VIRTUAL_MODEL_API,
		provider: definition.provider,
		baseUrl: "",
		reasoning: levels.some((level) => level !== "off"),
		thinkingLevelMap,
		input: definition.input ?? ["text", "image"],
		cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
		contextWindow: definition.contextWindow ?? 0,
		maxTokens: definition.maxTokens ?? 0,
	};
}
```

## !!steps Guarding against unrouted streaming

If code ever tries to stream a virtual model directly, `unroutedStream` returns a lazy stream that fails with a clear error naming the model. This is the enforcement of the invariant at the provider boundary.

```ts ! virtual-models.ts
/** Stream for a virtual model that was not routed, e.g. `stream()` with API-specific options. */
function unroutedStream(model: Model<Api>): AssistantMessageEventStream {
	return lazyStream(model, async () => {
		throw new Error(`Virtual model ${model.provider}/${model.id} must be routed before streaming`);
	});
}
```

## !!steps Adding virtual models to a provider

With no existing provider, `withVirtualModels` creates a keyless stand-in that lists only the virtual models and whose streams are the unrouted guard.

With a provider, it removes physical chat models whose ids collide with a virtual model (a catalog refresh can add them later), appends the virtual ones to `getModels` and `getAllModels`, and applies credential filtering only to the physical part. Virtual models bypass `filterModels`, so their availability follows the provider's auth. Streaming for virtual models goes to the guard; physical models go to the original provider.

```ts ! virtual-models.ts
	const ids = new Set(virtualModels.map((model) => model.id));
	const physical = <TModel extends AnyModel>(models: readonly TModel[]) =>
		models.filter((model) => !isVirtualModel(model) && !(isModelType(model, "chat") && ids.has(model.id)));
	const virtual = <TModel extends AnyModel>(models: readonly TModel[]) =>
		models.filter((model) => isVirtualModel(model));
	const { filterModels, filterAllModels } = provider;
	return {
		...provider,
		getModels: () => [...physical(provider.getModels()), ...virtualModels],
		getAllModels: () => [...physical(provider.getAllModels?.() ?? provider.getModels()), ...virtualModels],
		filterModels: (models, credential) => {
			const real = physical(models);
			return [...(filterModels?.(real, credential) ?? real), ...virtual(models)];
		},
```

The module is a pure library: no I/O, with the session branch passed in as data. One structural note: the `physical` filter drops only chat models that share an id with a virtual one, so a non-chat physical model with the same id would remain in the catalog.
