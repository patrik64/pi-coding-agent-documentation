This is the programmatic front door. `createAgentSession` takes a handful of
optional inputs and does everything needed to produce a working
[AgentSession](/docs/src/core/agent-session.ts): it fills in defaults, restores
or chooses a model, decides the thinking level and the initial tool set, builds
the low-level `Agent` from pi-agent-core with all its stream hooks, and wraps
it in the session.

Most of the file is that one function. It is deliberately a long, linear
script: each decision (which model, which thinking level, which tools) is made
in order, with session-restored values taking priority over settings, and
settings over built-in defaults. The CLI reaches it indirectly through
[agent-session-services.ts](/docs/src/core/agent-session-services.ts); SDK
users call it directly.

## !!steps Options and the default stream function

`CreateAgentSessionOptions` is almost entirely optional. The notable pair is
`tools` and `noTools` (`"all"` or `"builtin"`), plus the `excludeTools`
denylist that applies afterward and reaches MCP tools too.

`tools` has two shapes. Plain entries form an allowlist of names or `*`
patterns. A list made only of `+name` and `-name` entries instead edits the
default selection, the same way the `defaultTools` setting does; such entries
take exact names, and mixing the two shapes is an error.

At import time the module also calls `setDefaultStreamFn(streamSimple)`, a
side effect that keeps extensions constructing bare `Agent` instances working
even though agent core does not import the provider layer itself.

```ts ! sdk.ts
// Preserve the pre-0.81 fallback for extensions that construct Agent instances
// or invoke low-level agent loops without supplying streamFn. Agent core remains
// provider-agnostic and does not import pi-ai/compat itself.
// !mark
setDefaultStreamFn(streamSimple);

export interface CreateAgentSessionOptions {
	/** Working directory for project-local discovery. Default: process.cwd() */
	cwd?: string;
	/** Global config directory. Default: ~/.pi/agent */
	agentDir?: string;
// ...
	noTools?: "all" | "builtin";
// ...
	tools?: string[];
	/**
	 * Optional denylist of tool names or patterns to disable. Applies after `tools` when both are
	 * provided, MCP tools included.
	 */
	excludeTools?: string[];
```

## !!steps Defaults for everything the caller omitted

The cwd falls back to the session manager's cwd and only then to
`process.cwd()`. Auth and model files are only given explicit paths when the
caller passed an `agentDir`; otherwise `ModelRuntime.create` uses its own
defaults. Settings and the session manager are created on demand, and a
resource loader is built and reloaded only if none was supplied.

```ts ! sdk.ts
export async function createAgentSession(options: CreateAgentSessionOptions = {}): Promise<CreateAgentSessionResult> {
	// !mark
	const cwd = resolvePath(options.cwd ?? options.sessionManager?.getCwd() ?? process.cwd());
	const agentDir = options.agentDir ? resolvePath(options.agentDir) : getDefaultAgentDir();
	let resourceLoader = options.resourceLoader;

	const authPath = options.agentDir ? join(agentDir, "auth.json") : undefined;
	const modelsPath = options.agentDir ? join(agentDir, "models.json") : undefined;
	const modelRuntime = options.modelRuntime ?? (await ModelRuntime.create({ authPath, modelsPath }));

	const settingsManager = options.settingsManager ?? SettingsManager.create(cwd, agentDir);
	const sessionManager = options.sessionManager ?? SessionManager.create(cwd, getDefaultSessionDir(cwd, agentDir));

	// !mark(1:4)
	if (!resourceLoader) {
		resourceLoader = new DefaultResourceLoader({ cwd, agentDir, settingsManager });
		await resourceLoader.reload();
		time("resourceLoader.reload");
	}
```

## !!steps Choosing the model

If the caller gave no model and the session already has messages, the model
recorded on the branch is restored, but only if it still exists and has
configured auth. The lookup uses `getBranchSelection` from
[virtual-models.ts](/docs/src/core/virtual-models.ts), because assistant
messages name the physical model that answered while a virtual selection only
appears in `model_change` entries.

If that fails, or the session is new, `findInitialModel` in
[model-resolver.ts](/docs/src/core/model-resolver.ts) consults settings and
provider defaults. The failure becomes `modelFallbackMessage`: either "Could
not restore model ..." with the replacement appended, or the
no-models-available text from [auth-guidance.ts](/docs/src/core/auth-guidance.ts).

```ts ! sdk.ts
	// If session has data, try to restore model from it
	if (!model && hasExistingSession && sessionModel) {
		const restoredModel = modelRuntime.getModel(sessionModel.provider, sessionModel.modelId);
		// !mark(1:3)
		if (restoredModel && modelRuntime.hasConfiguredAuth(restoredModel.provider)) {
			model = restoredModel;
		}
		if (!model) {
			modelFallbackMessage = `Could not restore model ${sessionModel.provider}/${sessionModel.modelId}`;
		}
	}

	// If still no model, use findInitialModel (checks settings default, then provider defaults)
	if (!model) {
		const result = await findInitialModel({
			scopedModels: [],
			isContinuing: hasExistingSession,
// ...
		model = result.model;
		if (!model) {
			modelFallbackMessage = formatNoModelsAvailableMessage();
		} else if (modelFallbackMessage) {
			modelFallbackMessage += `. Using ${model.provider}/${model.id}`;
		}
	}
```

## !!steps Resolving the thinking level

Thinking level has a strict precedence ladder. An explicit option wins. For a
restored session, the level stored in the transcript wins, or the settings
default if the session never recorded one. For new sessions, the per-model
override from settings applies, then the global default, then
`DEFAULT_THINKING_LEVEL` from [defaults.ts](/docs/src/core/defaults.ts).

Finally the result is clamped to what the chosen model supports, and forced to
`"off"` when there is no model at all.

```ts ! sdk.ts
	let thinkingLevel = options.thinkingLevel;

	// If session has data, restore thinking level from it
	if (thinkingLevel === undefined && hasExistingSession) {
		thinkingLevel = hasThinkingEntry
			? (existingSession.thinkingLevel as ThinkingLevel)
			: (settingsManager.getDefaultThinkingLevel() ?? DEFAULT_THINKING_LEVEL);
	}

	// Fall back to per-model override, then global default
	if (thinkingLevel === undefined && model) {
		const perModel = settingsManager.getModelThinkingLevel(model.provider, model.id);
		if (perModel) {
			thinkingLevel = perModel;
		}
	}
// ...
	// Clamp to model capabilities
	if (!model) {
		thinkingLevel = "off";
	} else {
		// !mark
		thinkingLevel = clampThinkingLevel(model, thinkingLevel) as ThinkingLevel;
	}
```

## !!steps Initial tool selection

The `tools` list is validated first with `getToolListError` from
[settings-manager.ts](/docs/src/core/settings-manager.ts), which rejects
mixed lists and patterns in `+name`/`-name` entries; the SDK throws rather
than guessing.

`defaultToolNames` is the base selection: nothing if `noTools` is set,
otherwise the `defaultTools` setting or `DEFAULT_TOOL_NAMES`. A modifier list
is applied to that base with `applyToolModifiers`; a plain list replaces it.
The allowlist follows the same split. Modifiers do not restrict which tools
may exist, so they produce no allowlist unless `noTools` is `"all"`, in which
case the edited selection becomes the allowlist. A plain list is the
allowlist itself, and `noTools: "all"` alone gives an empty one.

`excludedToolNames` is compiled into a matcher by `createToolNameMatcher` from
[mcp-servers.ts](/docs/src/core/mcp-servers.ts) and filters the initial active
set last.

```ts ! sdk.ts
	// !mark(1:2)
	const toolListError = options.tools ? getToolListError(options.tools) : undefined;
	if (toolListError) throw new Error(`Invalid tools option: ${toolListError}`);
	const defaultToolNames = options.noTools ? [] : (settingsManager.getDefaultTools() ?? DEFAULT_TOOL_NAMES);
	// A `tools` list of only `+name`/`-name` entries changes the default selection instead of
	// replacing it, like the `defaultTools` setting.
	// !mark(1:2)
	const toolModifiers = options.tools?.some(isToolModifier) ? options.tools : undefined;
	const selectedToolNames = toolModifiers ? applyToolModifiers(defaultToolNames, toolModifiers) : options.tools;
	const allowedToolNames = toolModifiers
		? options.noTools === "all"
			? selectedToolNames
			: undefined
		: (options.tools ?? (options.noTools === "all" ? [] : undefined));
	const excludedToolNames = options.excludeTools;
	const isExcludedTool = excludedToolNames ? createToolNameMatcher(excludedToolNames) : undefined;
	const initialActiveToolNames = (selectedToolNames ?? defaultToolNames).filter((name) => !isExcludedTool?.(name));
```

## !!steps Blocking images, checked on every request

`convertToLlm` from [messages.ts](/docs/src/core/messages.ts) turns session
messages into provider messages. This wrapper adds a second line of defense for
the `blockImages` setting: if it is on, image parts in user and tool-result
messages are replaced by the text "Image reading is disabled.", and
consecutive placeholders are collapsed into one.

The setting is read inside the closure on each call, so toggling it mid-session
takes effect on the next request without rebuilding the agent.

```ts ! sdk.ts
	const convertToLlmWithBlockImages = (messages: AgentMessage[]): Message[] => {
		const converted = convertToLlm(messages);
		// Check setting dynamically so mid-session changes take effect
		// !mark
		if (!settingsManager.getBlockImages()) {
			return converted;
		}
		// Filter out ImageContent from all messages, replacing with text placeholder
		return converted.map((msg) => {
			if (msg.role === "user" || msg.role === "toolResult") {
				const content = msg.content;
				if (Array.isArray(content)) {
					const hasImages = content.some((c) => c.type === "image");
					if (hasImages) {
						const filteredContent = content
							.map((c) =>
								// !mark
								c.type === "image" ? { type: "text" as const, text: "Image reading is disabled." } : c,
							)
```

## !!steps Request options and the late-bound extension runner

`extensionRunnerRef` is a mutable box. The `Agent` is built before the
`AgentSession` exists, but its hooks must call the extension runner that the
session creates later (and replaces on reload). Every hook reads
`extensionRunnerRef.current` at call time, so it always sees the live runner.

`buildRequestOptions` merges per-request options with settings: provider retry
settings and an HTTP idle timeout where `0` means effectively unlimited
(`2147483647` ms).

It also sets the request's `identity` from
[client-identity.ts](/docs/src/core/client-identity.ts). pi-ai turns that
identity into the `User-Agent` and the provider attribution headers, so this
file no longer needs to know the request's model; it used to merge those
headers itself. The identity replaces pi-agent-core's default and is computed
on every request, so turning install telemetry off stops attribution on the
next call. The remaining `transformHeaders` callback hands the request
headers to `before_provider_headers` extension handlers. pi-ai adds the
identity's headers later, beneath the request headers, so handlers no longer
see the attribution headers but can still override or remove them.

```ts ! sdk.ts
	const extensionRunnerRef: { current?: ExtensionRunner } = {};
	const cacheWarmer = new CacheWarmer(
		modelRuntime,
		sessionManager,
		() => settingsManager.getCacheWarmingMode(),
		async (event) => extensionRunnerRef.current?.emitCacheWarmingDecision(event) ?? event.action,
	);
	const buildRequestOptions = (options: ModelsSimpleStreamOptions = {}): ModelsSimpleStreamOptions => {
		const providerRetrySettings = settingsManager.getProviderRetrySettings();
		const httpIdleTimeoutMs = settingsManager.getHttpIdleTimeoutMs();
		// !mark
		const effectiveTimeoutMs = httpIdleTimeoutMs === 0 ? 2147483647 : httpIdleTimeoutMs;
		const headerRunner = extensionRunnerRef.current;
		return {
			...options,
			timeoutMs: options.timeoutMs ?? providerRetrySettings.timeoutMs ?? effectiveTimeoutMs,
// ...
			// Replaces the agent loop's default identity; read per request so telemetry changes apply at once.
			// !mark
			identity: getClientIdentity(settingsManager),
			transformHeaders: async (headers) =>
				headerRunner?.hasHandlers("before_provider_headers")
					? headerRunner.emitBeforeProviderHeaders(headers)
					: headers,
		};
	};
```

## !!steps Cache warming only for stable requests

A [cache-warmer.ts](/docs/src/core/cache-warmer.ts) keeps the provider's
prompt cache alive between turns. `cacheContextIsCurrent` captures the message
array at request time and returns a predicate that stays true only while the
agent's model is unchanged and the captured messages are still a prefix of the
current ones, compared element by element.

The comment explains why identity of the array is not enough: agent state may
shallow-copy the array or refresh the model object without changing the actual
request.

```ts ! sdk.ts
	// Warm only requests for the selected model. Requests a virtual selection routed, or that an
	// extension redirected, may not be repeated by the next request, so warming them could be wasted.
	const cacheContextIsCurrent = (requestModel: Model<any>) => {
		const messages = agent.state.messages;
		return () => {
			const currentModel = agent.state.model;
			const currentMessages = agent.state.messages;
			return (
				// !mark(1:3)
				currentModel.provider === requestModel.provider &&
				currentModel.id === requestModel.id &&
				messages.length <= currentMessages.length &&
				messages.every((message, index) => currentMessages[index] === message)
			);
		};
	};
```

## !!steps Provider event hooks forwarded to extensions

Three small adapters turn low-level provider callbacks into extension events:
`before_provider_request` may replace the payload, `after_provider_response`
reports status and headers, and `provider_stream_event` forwards raw stream
data with the provider, API and model id. Each first checks `hasHandlers`, so
sessions without such extensions pay nothing.

```ts ! sdk.ts
	const transformProviderPayload = async (payload: unknown) => {
		const runner = extensionRunnerRef.current;
		// !mark
		if (!runner?.hasHandlers("before_provider_request")) return payload;
		return runner.emitBeforeProviderRequest(payload);
	};
	const handleProviderResponse: NonNullable<ModelsSimpleStreamOptions["onResponse"]> = async (response) => {
		const runner = extensionRunnerRef.current;
		if (!runner?.hasHandlers("after_provider_response")) return;
		await runner.emit({
			type: "after_provider_response",
			status: response.status,
			headers: response.headers,
		});
	};
```

## !!steps Constructing the Agent

The `Agent` starts with an empty system prompt and no tools; the session fills
both in afterward. Its `streamFn` builds request options, starts cache warming
only when the request's session ID matches the current session (compaction and
summary calls use their own IDs and must not reset warming), and delegates to
`modelRuntime.streamSimple`.

`transformContext` lets extensions rewrite messages through `emitContext`.
Steering and follow-up modes, transport, thinking budgets and retry delay come
from settings.

Right after construction, `markRuntimeStreamFunction` registers this stream
function with [agent-session.ts](/docs/src/core/agent-session.ts) as one that
resolves auth through `modelRuntime`. Compaction and other summaries check that
mark and leave credential resolution to the runtime instead of passing a
pre-resolved token as an explicit API key, which some providers treat
differently from stored OAuth. A caller that swaps `agent.streamFunction` loses
the mark and gets the old pre-resolving behavior.

```ts ! sdk.ts
	const agent = new Agent({
		initialState: {
			systemPrompt: "",
			model,
			thinkingLevel,
			tools: [],
			messages: existingSession.messages,
		},
		convertToLlm: convertToLlmWithBlockImages,
		streamFn: async (model, context, options) => {
			const requestOptions = buildRequestOptions(options);
// ...
			// !mark(1:3)
			if (options?.sessionId === sessionManager.getSessionId()) {
				cacheWarmer.start({ model, context, options: requestOptions }, cacheContextIsCurrent(model));
			}
			return modelRuntime.streamSimple(model, context, requestOptions);
		},
		onPayload: transformProviderPayload,
// ...
	// This stream resolves auth through modelRuntime, so summaries must not pre-resolve it (#11520).
	// !mark
	markRuntimeStreamFunction(agent.streamFunction, modelRuntime);
```

## !!steps Persisting metadata and creating the session

Older sessions may lack a thinking-level entry, so one is appended. For a new
session, the initial model and thinking level are written to the transcript so
a later resume restores them. Then the `AgentSession` is constructed with all
the resolved pieces.

`usesDefaultTools` is true when `noTools` was not passed and `tools` was
either omitted or a modifier list. It tells the session that the initial tools
came from the defaults, so a resumed session may replace them with the loadout
its transcript records and a settings reload may activate newly added default
tools. `defaultToolModifiers` hands over the modifier list so both paths apply
it again, keeping a `-name` tool removed. The result carries the extensions
result for UI setup and the fallback message.

```ts ! sdk.ts
	// Restore missing settings metadata for older sessions.
	if (hasExistingSession) {
		if (!hasThinkingEntry) {
			sessionManager.appendThinkingLevelChange(thinkingLevel);
		}
	} else {
		// Save initial model and thinking level for new sessions so they can be restored on resume
		// !mark(1:3)
		if (model) {
			sessionManager.appendModelChange(model.provider, model.id);
		}
		sessionManager.appendThinkingLevelChange(thinkingLevel);
	}

	const session = new AgentSession({
		agent,
		sessionManager,
		settingsManager,
		cwd,
// ...
		// !mark(1:2)
		usesDefaultTools: (options.tools === undefined || toolModifiers !== undefined) && !options.noTools,
		defaultToolModifiers: toolModifiers,
		allowedToolNames,
```

</Scrollycoding>

Everything above feeds one object: [agent-session.ts](/docs/src/core/agent-session.ts),
whose constructor installs further hooks on the `Agent` that this file built.
The middle of the file also re-exports the tool factories (`createReadTool`,
`createCodingTools` and friends from
[tools/index.ts](/docs/src/core/tools/index.ts)) and
[agent-session-runtime.ts](/docs/src/core/agent-session-runtime.ts) wholesale,
which is how the public [index.ts](/docs/src/index.ts) gets its SDK surface.

Structurally, the function depends on the order of declarations: `agent` is
referenced inside `cacheContextIsCurrent` before it is assigned, which works
only because the closure runs later.
