A provider the user sees is rarely just one thing. Pi ships built-in providers, users edit models.json to add models, override fields or change base URLs, and extensions can register or replace providers at runtime. `composeModelProvider` merges these three layers into one `Provider` object with models, auth methods and streaming.

The file is deliberately free of credential I/O: it builds closures that resolve keys and headers later, when auth is actually requested. [model-runtime.ts](/docs/src/core/model-runtime.ts) is the main caller, [model-registry.ts](/docs/src/core/model-registry.ts) re-exports its types, the shape of models.json is defined in [model-config.ts](/docs/src/core/model-config.ts), and value syntax such as environment references is handled by [resolve-config-value.ts](/docs/src/core/resolve-config-value.ts).

## !!steps What extensions can register

`ProviderConfigInput` is what an extension passes to registerProvider (the extension API is typed in [types.ts](/docs/src/core/extensions/types.ts)). Besides names, URLs and headers it can supply a custom `streamSimple`, image and classifier implementations keyed by API, an OAuth config, a fixed model list, or a `refreshModels` callback for dynamic lists.

The OAuth config is the older extension shape. Its `usesCallbackServer` field is marked deprecated and ignored.

```ts ! provider-composer.ts
export interface ExtensionOAuthConfig {
	name: string;
	/** Whether access through this auth method is backed by a provider subscription. */
	isSubscription?: boolean;
	/** @deprecated Retained for extension source compatibility; ignored by canonical auth flows. */
	usesCallbackServer?: boolean;
	login(callbacks: OAuthLoginCallbacks): Promise<OAuthCredentials>;
	refreshToken(credentials: OAuthCredentials, signal: AbortSignal): Promise<OAuthCredentials>;
	getApiKey(credentials: OAuthCredentials): string;
	modifyModels?(models: Model<Api>[], credentials: OAuthCredentials): Model<Api>[];
}
// ...
/** Input type for the extension registerProvider API. */
// !mark
export interface ProviderConfigInput {
	name?: string;
	baseUrl?: string;
	apiKey?: string;
	api?: Api;
// !mark(1:5)
	streamSimple?: (
		model: Model<Api>,
		context: TranscriptContext,
		options?: SimpleStreamOptions,
	) => AssistantMessageEventStream;
	images?: Partial<Record<ImageApi, ProviderImages>>;
	classifiers?: Partial<Record<ClassifierApi, ProviderClassifier>>;
	headers?: Record<string, string>;
	authHeader?: boolean;
// !mark
	oauth?: ExtensionOAuthConfig;
	models?: ProviderModelConfig[];
	refreshModels?(context: RefreshModelsContext): Promise<ProviderModelConfig[]>;
}
```

## !!steps Model definitions come in three kinds

Models are chat, image or classifier. They share a base (id, name, input kinds, cost, headers) and extend it with the fields each operation needs: chat models have reasoning, context window and token limits; image models declare their outputs; classifiers have a context window. The discriminant is `type`, which defaults to chat when omitted.

```ts ! provider-composer.ts
interface ProviderModelConfigBase {
	id: string;
	name: string;
	api?: string;
	baseUrl?: string;
	input: ("text" | "image")[];
	inputLimits?: AnyModel["inputLimits"];
	cost: AnyModel["cost"];
	headers?: Record<string, string>;
}

// !mark
export interface ProviderChatModelConfig extends ProviderModelConfigBase {
	type?: "chat";
	api?: Api;
	reasoning: boolean;
	thinkingLevelMap?: Model<Api>["thinkingLevelMap"];
	promptCache?: Model<Api>["promptCache"];
	contextWindow: number;
	maxTokens: number;
	samplingParams?: Model<Api>["samplingParams"];
	samplingParamsByThinkingLevel?: Model<Api>["samplingParamsByThinkingLevel"];
	compat?: Model<Api>["compat"];
}

// !mark
export interface ProviderImageModelConfig extends ProviderModelConfigBase {
	type: "image";
	api?: ImageApi;
	output: ("text" | "image")[];
}

// !mark
export interface ProviderClassifierModelConfig extends ProviderModelConfigBase {
	type: "classifier";
	api?: ClassifierApi;
	contextWindow: number;
}

export type ProviderModelConfig = ProviderChatModelConfig | ProviderImageModelConfig | ProviderClassifierModelConfig;
```

## !!steps Merging nested overrides

`mergeCompat` is a shallow merge with one refinement: four named keys (OpenRouter and Vercel gateway routing, and two chat template argument maps) are merged one level deeper, so overriding one routing field does not erase its siblings.

The same one-level-deeper pattern appears for input limits, where image resize settings merge separately from the rest, and for sampling parameters per thinking level.

```ts ! provider-composer.ts
function mergeCompat(
	base: Model<Api>["compat"],
	override: Model<Api>["compat"] | ModelsJsonModelOverride["compat"],
): Model<Api>["compat"] {
	if (!override) return base;
	const merged = { ...base, ...override } as NonNullable<Model<Api>["compat"]>;
	const baseNested = base as Record<string, unknown> | undefined;
	const overrideNested = override as Record<string, unknown>;
	const mergedNested = merged as Record<string, unknown>;
// !mark
	for (const key of ["openRouterRouting", "vercelGatewayRouting", "chatTemplateKwargs", "chatTemplateArgs"] as const) {
		const baseValue = baseNested?.[key];
		const overrideValue = overrideNested[key];
		if (
			(typeof baseValue === "object" && baseValue !== null) ||
			(typeof overrideValue === "object" && overrideValue !== null)
		) {
			mergedNested[key] = { ...(baseValue as object | undefined), ...(overrideValue as object | undefined) };
		}
	}
	return merged;
}
```

## !!steps Applying a model override

`applyModelOverride` is how `modelOverrides` in models.json patch an existing model. Scalars use nullish fallbacks, so an unset field keeps the original. Cost is merged field by field. Thinking level maps, prompt cache settings and sampling params are spread over the originals.

Overrides are chat only.

```ts ! provider-composer.ts
function applyModelOverride(model: Model<Api>, override: ModelsJsonModelOverride): Model<Api> {
	return {
		...model,
// !mark
		name: override.name ?? model.name,
		reasoning: override.reasoning ?? model.reasoning,
		thinkingLevelMap: override.thinkingLevelMap
			? { ...model.thinkingLevelMap, ...override.thinkingLevelMap }
			: model.thinkingLevelMap,
		input: (override.input as ("text" | "image")[] | undefined) ?? model.input,
		inputLimits: mergeInputLimits(model.inputLimits, override.inputLimits),
// !mark(1:8)
		cost: override.cost
			? {
					input: override.cost.input ?? model.cost.input,
					output: override.cost.output ?? model.cost.output,
					cacheRead: override.cost.cacheRead ?? model.cost.cacheRead,
					cacheWrite: override.cost.cacheWrite ?? model.cost.cacheWrite,
					tiers: override.cost.tiers ?? model.cost.tiers,
				}
			: model.cost,
		promptCache: override.promptCache ? { ...model.promptCache, ...override.promptCache } : model.promptCache,
		contextWindow: override.contextWindow ?? model.contextWindow,
		maxTokens: override.maxTokens ?? model.maxTokens,
		samplingParams: override.samplingParams
			? { ...model.samplingParams, ...override.samplingParams }
			: model.samplingParams,
		samplingParamsByThinkingLevel: mergeSamplingParamsByThinkingLevel(
			model.samplingParamsByThinkingLevel,
			override.samplingParamsByThinkingLevel,
		),
// !mark
		compat: mergeCompat(model.compat, override.compat),
	};
}
```

## !!steps Building models from models.json

`modelFromJson` creates a complete chat model from a user definition. The API and base URL are resolved from the definition, then the provider entry, then defaults taken from an existing model; if neither exists it throws a configuration error naming the provider and model. Non-positive context windows or token limits are rejected.

Unspecified fields fall back to a zero cost, a 128000 token context window, 16384 max tokens, and text-only input.

```ts ! provider-composer.ts
function modelFromJson(
	providerId: string,
	definition: ModelsJsonModel,
	providerConfig: ModelsJsonProvider,
	defaults: Model<Api> | undefined,
): Model<Api> {
// !mark(1:5)
	const api = definition.api ?? providerConfig.api ?? defaults?.api;
	if (!api) {
		throw new Error(
			`Provider ${providerId}, model ${definition.id}: no "api" specified. Set at provider or model level.`,
		);
	}
// !mark(1:2)
	const baseUrl = definition.baseUrl ?? providerConfig.baseUrl ?? defaults?.baseUrl;
	if (!baseUrl) throw new Error(`Provider ${providerId}: "baseUrl" is required when defining custom models.`);
// !mark(1:6)
	if (definition.contextWindow !== undefined && definition.contextWindow <= 0) {
		throw new Error(`Provider ${providerId}, model ${definition.id}: invalid contextWindow`);
	}
	if (definition.maxTokens !== undefined && definition.maxTokens <= 0) {
		throw new Error(`Provider ${providerId}, model ${definition.id}: invalid maxTokens`);
	}
	return {
		id: definition.id,
		name: definition.name ?? definition.id,
		api: api as Api,
		provider: providerId,
		baseUrl,
		reasoning: definition.reasoning ?? false,
		thinkingLevelMap: definition.thinkingLevelMap,
		input: (definition.input ?? ["text"]) as ("text" | "image")[],
		inputLimits: definition.inputLimits,
		cost: definition.cost ?? { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
		promptCache: definition.promptCache,
// !mark(1:2)
		contextWindow: definition.contextWindow ?? 128000,
		maxTokens: definition.maxTokens ?? 16384,
		samplingParams: definition.samplingParams,
		samplingParamsByThinkingLevel: definition.samplingParamsByThinkingLevel,
		headers: undefined,
		compat: mergeCompat(providerConfig.compat, definition.compat),
	};
}
```

## !!steps Picking defaults to inherit from

When a custom model does not name an API, it borrows from a similar model: one with the same id, then one with the requested API, then any model speaking the OpenAI completions API, then simply the first. The extension variant does the same but filters candidates by model type first and only uses the completions fallback for chat.

```ts ! provider-composer.ts
function findModelDefaults(models: readonly AnyModel[], modelId: string, api?: Api): Model<Api> | undefined {
	const chatModels = models.filter((model) => isModelType(model, "chat"));
	return (
// !mark(1:5)
		chatModels.find((model) => model.id === modelId) ??
		(api ? chatModels.find((model) => model.api === api) : undefined) ??
		chatModels.find((model) => model.api === "openai-completions") ??
		chatModels[0]
	);
}

function findExtensionModelDefaults(
	models: readonly AnyModel[],
	definition: ProviderModelConfig,
): AnyModel | undefined {
	const type = definition.type ?? "chat";
	const candidates = models.filter((model) => isModelType(model, type));
// !mark(1:5)
	return (
		candidates.find((model) => model.id === definition.id) ??
		(definition.api ? candidates.find((model) => model.api === definition.api) : undefined) ??
		(type === "chat" ? candidates.find((model) => model.api === "openai-completions") : undefined) ??
		candidates[0]
	);
}
```

## !!steps Applying models.json to the base list

`applyModelsJson` validates the entry first: setting oauth requires a base URL, and an entry with no effect at all is an error listing what was expected. Existing models get the provider's base URL and compat merged in. Radius OAuth providers keep their own base URL.

Custom models then replace an existing model with the same id or are appended.

```ts ! provider-composer.ts
function applyModelsJson(
	providerId: string,
	baseModels: readonly AnyModel[],
	config: ModelsJsonProvider | undefined,
): AnyModel[] {
	if (!config) return [...baseModels];
// !mark(1:2)
	if (config.oauth && !config.baseUrl) {
		throw new Error(`Provider ${providerId}: "baseUrl" is required when "oauth" is set.`);
	}
// !mark(1:12)
	const hasOverrides = config.modelOverrides && Object.keys(config.modelOverrides).length > 0;
	if (
		!config.models?.length &&
		!config.baseUrl &&
		!config.headers &&
		!config.compat &&
		!hasOverrides &&
		!config.apiKey &&
		!config.oauth &&
		config.authHeader === undefined
	) {
		throw new Error(
			`Provider ${providerId}: must specify "baseUrl", "headers", "compat", "modelOverrides", or "models".`,
		);
	}

	const models: AnyModel[] = baseModels.map((model) => {
// !mark
		const baseUrl = config.oauth === "radius" ? model.baseUrl : (config.baseUrl ?? model.baseUrl);
		return isModelType(model, "chat")
			? { ...model, baseUrl, compat: mergeCompat(model.compat, config.compat) }
			: { ...model, baseUrl };
	});
	for (const definition of config.models ?? []) {
		const existingIndex = models.findIndex((model) => isModelType(model, "chat") && model.id === definition.id);
		const defaults = findModelDefaults(models, definition.id, definition.api ?? config.api);
		const model = modelFromJson(providerId, definition, config, defaults);
		if (existingIndex >= 0) models[existingIndex] = model;
		else models.push(model);
	}
	return models;
}
```

## !!steps Applying the extension layer

An extension with no model list only retargets the base URL. An extension with a model list replaces the models entirely, rather than merging, with each definition filled in by `extensionModelFromDefinition`, which resolves api and baseUrl similarly and clears per-model headers into the raw field for later resolution.

```ts ! provider-composer.ts
function applyExtension(
	providerId: string,
	models: readonly AnyModel[],
	config: ProviderConfigInput | undefined,
): AnyModel[] {
	if (!config) return [...models];
// !mark(1:3)
	if (!config.models) {
		return config.baseUrl ? models.map((model) => ({ ...model, baseUrl: config.baseUrl! })) : [...models];
	}
// !mark
	return config.models.map((definition) => extensionModelFromDefinition(providerId, models, config, definition));
}
```

## !!steps Adapting extension OAuth

`adaptOAuth` translates the legacy callback-based extension login into the notify/prompt interaction model: auth URLs, device codes, progress, manual code input and selection each map to an event or a prompt. The credentials are tagged with `type: "oauth"`.

`withConfiguredAuth` merges configured headers into whatever auth produced, and when `authHeader` is set it adds a bearer Authorization header from the resolved key, throwing if there is none.

```ts ! provider-composer.ts
function adaptOAuth(config: ExtensionOAuthConfig): OAuthAuth {
	return {
		name: config.name,
		isSubscription: config.isSubscription,
// !mark(1:2)
		login: async (callbacks) => {
			const credential = await config.login({
				onAuth: (info) => callbacks.notify({ type: "auth_url", ...info }),
				onDeviceCode: (info) => callbacks.notify({ type: "device_code", ...info }),
				onPrompt: (prompt) => callbacks.prompt({ type: "text", ...prompt }),
				onProgress: (message) => callbacks.notify({ type: "progress", message }),
				onManualCodeInput: () => callbacks.prompt({ type: "manual_code", message: "Paste the authorization code" }),
				onSelect: (prompt) => callbacks.prompt({ type: "select", ...prompt }),
				signal: callbacks.signal,
			});
			return { ...credential, type: "oauth" };
		},
// !mark(1:2)
		refresh: async (credential, signal) => ({ ...(await config.refreshToken(credential, signal)), type: "oauth" }),
		toAuth: async (credential) => ({ apiKey: config.getApiKey(credential) }),
	};
}

function withConfiguredAuth(
	auth: ModelAuth,
	headers: Record<string, string> | undefined,
	authHeader: boolean,
): ModelAuth {
	let mergedHeaders: ProviderHeaders | undefined =
		auth.headers || headers ? { ...auth.headers, ...headers } : undefined;
// !mark(1:6)
	if (authHeader) {
		if (!auth.apiKey) throw new Error("authHeader requires a resolved API key");
		mergedHeaders = { ...mergedHeaders, Authorization: `Bearer ${auth.apiKey}` };
	}
	return { ...auth, headers: mergedHeaders };
}
```

## !!steps Composing API-key auth

The API-key method inherits name and login from the base provider when one exists. An OAuth-only provider with no key configured gets no API-key method at all, so no fake login option appears.

`check` answers whether a credential could be resolved without resolving it, in priority order: a stored credential, a configured key (command values are assumed present; environment values must exist), then the base provider's own check.

```ts ! provider-composer.ts
function composeApiKeyAuth(
	providerId: string,
	base: Provider | undefined,
	config: ModelsJsonProvider | undefined,
	extension: ProviderConfigInput | undefined,
): ApiKeyAuth | undefined {
	const inherited = base?.auth.apiKey;
	const rawKey = configuredApiKey(config, extension);
	const oauth = extension?.oauth ?? base?.auth.oauth;
	// OAuth-only providers get no fabricated API-key login method.
// !mark
	if (!inherited && rawKey === undefined && oauth) return undefined;
	const rawHeaders = configuredHeaders(config, extension);
	const authHeader = extension?.authHeader ?? config?.authHeader ?? false;
	return {
		name: inherited?.name ?? "API key",
		login:
			inherited?.login ??
			(async (interaction: AuthInteraction) => ({
				type: "api_key",
				key: await interaction.prompt({ type: "secret", message: "Enter API key" }),
			})),
		// ...
		check: async (input) => {
			if (input.credential) {
				if (inherited?.check) return inherited.check(input);
				if (input.credential.key) return { type: "api_key", source: "stored credential" };
				const resolved = await inherited?.resolve(input);
				return resolved ? { type: "api_key", source: resolved.source } : undefined;
			}
// !mark(1:2)
			if (rawKey !== undefined) {
				if (isCommandConfigValue(rawKey)) return { type: "api_key", source: "configured API key" };
				const envNames = getConfigValueEnvVarNames(rawKey);
				for (const name of envNames) {
					if ((await input.ctx.env(name)) === undefined) return undefined;
				}
				return { type: "api_key", source: "configured API key" };
			}
// !mark(1:3)
			if (inherited?.check) return inherited.check(input);
			const resolved = await inherited?.resolve(input);
			return resolved ? { type: "api_key", source: resolved.source } : undefined;
		},
```

## !!steps Resolving the key and headers

`resolve` uses the stored credential if given, else resolves the configured key from the models.json or extension value, throwing a descriptive error on failure, else defers to the base. If the base provider exists, it receives the resolved key as a credential, so provider-specific logic such as extra headers still runs.

Headers are resolved afterward using environment values from the credential and from the auth context, and merged into the auth result.

```ts ! provider-composer.ts
		resolve: async (input) => {
			let result: AuthResult | undefined;
// !mark(1:3)
			if (input.credential) {
				result = inherited
					? await inherited.resolve(input)
					: input.credential.key
						? { auth: { apiKey: input.credential.key }, env: input.credential.env, source: "stored credential" }
						: undefined;
// !mark(1:6)
			} else if (rawKey !== undefined) {
				const env = await configContextEnv([rawKey], input.ctx);
				const key = resolveConfigValueOrThrow(rawKey, `API key for provider "${providerId}"`, env);
				result = inherited
					? await inherited.resolve({ ...input, credential: { type: "api_key", key } })
					: { auth: { apiKey: key }, source: "configured API key" };
			} else {
				result = await inherited?.resolve(input);
			}
			if (!result) return undefined;
			const explicitEnv = { ...(input.credential?.env ?? {}), ...(result.env ?? {}) };
// !mark(1:2)
			const headerEnv = await configContextEnv(Object.values(rawHeaders ?? {}), input.ctx, explicitEnv);
			const headers = resolveHeadersOrThrow(rawHeaders, `provider "${providerId}"`, headerEnv);
			return { ...result, auth: withConfiguredAuth(result.auth, headers, authHeader) };
		},
	};
```

## !!steps Composing OAuth auth and per-model headers

OAuth auth wraps the underlying method so that `toAuth` still runs first and the configured headers are merged afterward. An extension's OAuth replaces the base one.

For headers on a single model, three sources merge with increasing priority: models.json override, models.json definition, then the extension's definition, which is matched by type and id so models of different types sharing an id do not leak headers.

```ts ! provider-composer.ts
function composeOAuthAuth(
	providerId: string,
	base: Provider | undefined,
	config: ModelsJsonProvider | undefined,
	extension: ProviderConfigInput | undefined,
): OAuthAuth | undefined {
// !mark
	const oauth = extension?.oauth ? adaptOAuth(extension.oauth) : base?.auth.oauth;
	if (!oauth) return undefined;
	const rawHeaders = configuredHeaders(config, extension);
	const authHeader = extension?.authHeader ?? config?.authHeader ?? false;
	return {
		...oauth,
// !mark(1:3)
		toAuth: async (credential) => {
			const auth = await oauth.toAuth(credential);
			const env = credential.env;
			const headers = resolveHeadersOrThrow(
				rawHeaders,
				`provider "${providerId}"`,
				typeof env === "object" && env !== null ? (env as Record<string, string>) : undefined,
			);
			return withConfiguredAuth(auth, headers, authHeader);
		},
	};
}
// ...
function rawModelHeaders(
	model: AnyModel,
	config: ModelsJsonProvider | undefined,
	extension: ProviderConfigInput | undefined,
): Record<string, string> | undefined {
	// models.json definitions and overrides are chat-only. Extension definitions
	// are matched by operation and id so colliding models cannot share headers.
// !mark(1:3)
	const chatDefinition = isModelType(model, "chat")
		? config?.models?.find((entry) => entry.id === model.id)
		: undefined;
	const extensionModel = extension?.models?.find(
		(entry) => (entry.type ?? "chat") === (model.type ?? "chat") && entry.id === model.id,
	);
// !mark(1:5)
	const headers = {
		...(isModelType(model, "chat") ? config?.modelOverrides?.[model.id]?.headers : undefined),
		...chatDefinition?.headers,
		...extensionModel?.headers,
	};
	return Object.keys(headers).length > 0 ? headers : undefined;
}
```

## !!steps Validation and the eager check

`validateExtensionProvider` dry-runs the layering so registration errors are reported immediately. `composeModelProvider` does the same by calling `getAllModels` once up front, and throws if the combination has no auth method at all.

```ts ! provider-composer.ts
export function validateExtensionProvider(
	providerId: string,
	base: Provider | undefined,
	modelsConfig: ModelsJsonProvider | undefined,
	extension: ProviderConfigInput,
): void {
// !mark(1:3)
	if (extension.streamSimple && !extension.api) {
		throw new Error(`Provider ${providerId}: "api" is required when registering streamSimple.`);
	}
	applyExtension(providerId, applyModelsJson(providerId, getAllProviderModels(base), modelsConfig), extension);
}
	// ...
	// Validate eagerly so registration/reload reports structural errors immediately.
// !mark
	getAllModels();
	const apiKey = composeApiKeyAuth(providerId, base, config, extension);
	const oauth = composeOAuthAuth(providerId, base, config, extension);
// !mark
	if (!apiKey && !oauth) throw new Error(`Provider ${providerId}: no authentication method configured.`);
```

## !!steps The model getter and refresh state

`getAllModels` is recomputed on each call from the layers: models.json, then extension, then an OAuth `modifyModels` hook that sees only chat models, and finally `modelOverrides`. Because overrides are applied last, user configuration always has the final say. Two closure variables, the OAuth credential and models refreshed by the extension, make this dynamic.

```ts ! provider-composer.ts
	const config = modelConfig.getProvider(providerId);
	let extensionOAuthCredential: OAuthCredentials | undefined;
	let refreshedExtensionModels: ProviderConfigInput["models"];
	const currentExtension = (): ProviderConfigInput | undefined =>
		extension && refreshedExtensionModels ? { ...extension, models: refreshedExtensionModels } : extension;
// !mark(1:2)
	// models.json modelOverrides are the topmost user-config layer: they apply once,
	// after custom-model upserts, extension model replacement, and legacy OAuth projection.
	const getAllModels = (): AnyModel[] => {
		let models = applyExtension(
			providerId,
			applyModelsJson(providerId, getAllProviderModels(base), config),
			currentExtension(),
		);
// !mark(1:10)
		if (extensionOAuthCredential && extension?.oauth?.modifyModels) {
			// The extension hook is chat-only; other model types pass through untouched.
			models = [
				...extension.oauth.modifyModels(
					models.filter((model) => isModelType(model, "chat")),
					extensionOAuthCredential,
				),
				...models.filter((model) => !isModelType(model, "chat")),
			];
		}
// !mark(1:4)
		return models.map((model) => {
			const override = config?.modelOverrides?.[model.id];
			return override && isModelType(model, "chat") ? applyModelOverride(model, override) : model;
		});
	};
```

## !!steps Streaming dispatch

`streamWith` wraps the call in `lazyStream`. The order of preference is the extension's `streamSimple` (when the model's API matches), then the base provider if it supports that API, then a globally registered API provider. If nothing handles the API, it throws.

```ts ! provider-composer.ts
	const supportsBaseApi = (model: Model<Api>) => base?.getModels().some((entry) => entry.api === model.api) ?? false;
	const streamWith = (
		model: Model<Api>,
		context: TranscriptContext,
		options: StreamOptions | undefined,
		simple: boolean,
	): AssistantMessageEventStream =>
		lazyStream(model, async () => {
// !mark(1:3)
			if (extension?.streamSimple && model.api === extension.api) {
				return extension.streamSimple(model, context, options as SimpleStreamOptions);
			}
// !mark(1:6)
			if (base && supportsBaseApi(model)) {
				return simple
					? base.streamSimple(model, context, options as SimpleStreamOptions)
					: base.stream(model, context, options);
			}
// !mark(1:2)
			const api = getApiProvider(model.api);
			if (!api) throw new Error(`No API provider registered for api: ${model.api}`);
			return simple
				? api.streamSimple(model, context, options as SimpleStreamOptions)
				: api.stream(model, context, options);
		});
```

## !!steps The assembled Provider

The name falls back through extension, models.json, base, OAuth name and finally the id. Chat-only and all-model getters are provided. `refreshModels` exists only if something can refresh: it runs the base refresh, then the extension's, and publishes validated results together with the OAuth credential, so the synchronous getter never sees invalid lists. Model filters are passed through from the base.

```ts ! provider-composer.ts
	const provider: Provider = {
		id: providerId,
// !mark
		name: extension?.name ?? config?.name ?? base?.name ?? extension?.oauth?.name ?? providerId,
		baseUrl: extension?.baseUrl ?? config?.baseUrl ?? base?.baseUrl,
		headers: base?.headers,
		auth: { ...(apiKey ? { apiKey } : {}), ...(oauth ? { oauth } : {}) },
// !mark(1:2)
		getModels: () => getAllModels().filter((model) => isModelType(model, "chat")),
		getAllModels,
// !mark(1:3)
		refreshModels:
			base?.refreshModels || extension?.refreshModels || extension?.oauth?.modifyModels
				? async (context) => {
						await base?.refreshModels?.(context);
						let refreshed: NonNullable<ProviderConfigInput["models"]> | undefined;
						if (extension?.refreshModels) refreshed = await extension.refreshModels(context);
						if (context.signal.aborted) return;
						const oauthCredential = context.credential?.type === "oauth" ? context.credential : undefined;
						await context.publish({
							update: () => {
								if (refreshed) {
									// Validate before publishing the new synchronous list.
									applyExtension(providerId, applyModelsJson(providerId, getAllProviderModels(base), config), {
										...extension,
										models: refreshed,
									});
									refreshedExtensionModels = refreshed;
								}
								extensionOAuthCredential = oauthCredential;
							},
						});
					}
				: undefined,
// !mark(1:6)
		filterModels: base?.filterModels
			? (models, credential: Credential | undefined) => base.filterModels!(models, credential)
			: undefined,
		filterAllModels: base?.filterAllModels
			? (models, credential: Credential | undefined) => base.filterAllModels!(models, credential)
			: undefined,
		stream: (model, context, options) => streamWith(model, context, options, false),
		streamSimple: (model, context, options) => streamWith(model, context, options, true),
	};
```

## !!steps Images, classifiers, and status helpers

Image and classifier operations are added only if the base or extension supplies them; the extension's per-API implementation wins, then the base, and otherwise an error result is returned rather than throwing.

The remaining exports resolve per-model headers and request config for compatibility call paths, and `configuredRequestAuthStatus` computes the auth status label shown in the UI without resolving secrets: a command, an environment variable set or missing, or a literal key from models.json or an extension fallback.

The output is one object that behaves as if it had always been a single provider. Layer order is the key invariant: built-in models first, then models.json, then extension replacement, then OAuth hooks, then user overrides last. Two things to be aware of: `clearApiKeyCache` is simply an alias of the config value cache clear, and `headers` on the composed provider come from the base only, not from models.json or the extension.
