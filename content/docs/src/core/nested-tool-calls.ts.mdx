Normally the model issues a tool call and the agent loop runs it. Some tools, such as codemode scripts, want to call other tools while they run. This file is the machinery for that: a recorder that summarizes the nested calls, and a runner that executes them through the same tool pipeline with hooks, events and ordering rules intact.

The agent loop never sees nested calls. The session supplies a host object, and the runner uses it to resolve tools, run each call, and emit `tool_execution_*` events tagged with `parentToolCallId`. When the outer call finishes, [agent-session.ts](/docs/src/core/agent-session.ts) takes the record and attaches it, with the summed usage, to the model-issued call's tool result message.

Nothing here runs unless a tool actually calls `ctx.executeTool()`.

## !!steps Hard limits on what gets recorded

The record that rides on a tool result message has to stay small, since it is persisted with the session by [session-manager.ts](/docs/src/core/session-manager.ts). These limits cap the number of calls, the size of each call's arguments, the total argument size and the length of stored error text.

Exceeding a limit never fails the call. The record just becomes incomplete, which the summary reports through a `complete` flag.

```ts ! nested-tool-calls.ts
/**
 * Limits of the nested-call record on a tool result: arguments
 * over the per-call or total size are omitted, calls beyond the count are dropped, and the record
 * is marked incomplete when any of that happens.
 */
// !mark(1:5)
export const NESTED_CALL_LIMITS = {
	maxCalls: 256,
	maxArgumentBytesPerCall: 8 * 1024,
	maxArgumentBytesTotal: 32 * 1024,
	maxErrorChars: 500,
} as const;

const encoder = new TextEncoder();
```

## !!steps Recording a call as it starts

`start` creates the record with status `unfinished`. If the count limit is hit, the call is dropped from the record entirely, but it will still run.

Arguments are serialized once to measure bytes. Too big for one call or for the running total means only `argumentsBytes` is stored and the record is flagged incomplete. Otherwise the JSON is parsed back, so the record holds a detached copy of the arguments rather than a live reference. Start time is kept in a side map for the duration calculation.

```ts ! nested-tool-calls.ts
export class NestedCallRecorder {
	private readonly calls: NestedToolCallRecord[] = [];
	private readonly startedAt = new Map<NestedToolCallRecord, number>();
	private complete = true;
	private argumentBytes = 0;
	/** Summed usage of every nested result, including calls dropped from the record. */
	private usage: Usage | undefined;

	/** Record a call as it starts. Returns undefined when the call is dropped. */
	start(toolCall: AgentToolCall): NestedToolCallRecord | undefined {
// !mark(1:4)
		if (this.calls.length >= NESTED_CALL_LIMITS.maxCalls) {
			this.complete = false;
			return undefined;
		}
		const record: NestedToolCallRecord = { id: toolCall.id, name: toolCall.name, status: "unfinished" };
		const json = JSON.stringify(toolCall.arguments ?? {});
		const bytes = encoder.encode(json).length;
// !mark(1:5)
		if (
			bytes > NESTED_CALL_LIMITS.maxArgumentBytesPerCall ||
			this.argumentBytes + bytes > NESTED_CALL_LIMITS.maxArgumentBytesTotal
		) {
			record.argumentsBytes = bytes;
			this.complete = false;
		} else {
			record.arguments = JSON.parse(json) as JsonObject;
			this.argumentBytes += bytes;
		}
		this.calls.push(record);
		this.startedAt.set(record, performance.now());
		return record;
	}
```

## !!steps Finishing, usage, and snapshots

`finish` turns the status into `ok` or `error`, rounds the duration, and truncates error text. A `record` of undefined (a dropped call) is silently ignored.

Usage is accumulated separately from the record with `combineUsage` from [usage-totals.ts](/docs/src/core/usage-totals.ts), so calls dropped by the count limit still contribute their cost.

`snapshot` copies the calls, and reports `complete` only if nothing was dropped and no call is still unfinished. It returns undefined when no nested call happened at all, so ordinary tool results stay unchanged.

```ts ! nested-tool-calls.ts
	finish(record: NestedToolCallRecord | undefined, isError: boolean, errorText: string): void {
		if (!record) return;
// !mark(1:2)
		record.status = isError ? "error" : "ok";
		record.durationMs = Math.round(performance.now() - (this.startedAt.get(record) ?? performance.now()));
		this.startedAt.delete(record);
		if (isError && errorText) record.error = errorText.slice(0, NESTED_CALL_LIMITS.maxErrorChars);
	}

	addUsage(usage: Usage): void {
		this.usage = this.usage ? combineUsage(this.usage, usage) : usage;
	}

	get totalUsage(): Usage | undefined {
		return this.usage;
	}

	/** Copy of the record so far, or undefined when no nested call was made. */
	snapshot(): NestedToolCalls | undefined {
// !mark
		if (this.calls.length === 0 && this.complete) return undefined;
		const calls = this.calls.map((call) => ({ ...call }));
		return { calls, complete: this.complete && calls.every((call) => call.status !== "unfinished") };
	}
```

## !!steps The host contract and event shapes

The runner is deliberately ignorant of the agent. `NestedToolCallHost` is everything it needs: the current tool list, whether the agent runs tools sequentially, a way to run one call through the pipeline with a parent id, and an event sink.

The three event variants mirror the normal `tool_execution_*` events plus `parentToolCallId`, which is how UIs in [interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts) and the JSON modes can nest them under the call that caused them.

```ts ! nested-tool-calls.ts
/** `tool_execution_*` events of nested calls. */
export type NestedToolExecutionEvent =
	| { type: "tool_execution_start"; toolCallId: string; toolName: string; args: unknown; parentToolCallId: string }
	| {
			type: "tool_execution_update";
			toolCallId: string;
			toolName: string;
			args: unknown;
			partialResult: AgentToolResult<unknown>;
			parentToolCallId: string;
	  }
	| {
			type: "tool_execution_end";
			toolCallId: string;
			toolName: string;
			result: AgentToolResult<unknown>;
			isError: boolean;
			parentToolCallId: string;
	  };

// !mark(1:4)
export interface NestedToolCallHost {
	/** Tools nested calls resolve against. */
	getTools(): readonly AgentTool[];
	/** Whether every nested call runs exclusively, as when the agent executes tool calls sequentially. */
	isSequential(): boolean;
	/** Run the call through the tool pipeline, with hooks that report `parentToolCallId`. */
	runToolCall(
		toolCall: AgentToolCall,
		parentToolCallId: string,
		signal: AbortSignal | undefined,
		onUpdate: (partialResult: AgentToolResult<unknown>) => Promise<void>,
	): Promise<AgentToolCallOutcome>;
	emit(event: NestedToolExecutionEvent): Promise<void>;
}
```

## !!steps Scopes and call ids

A `CallScope` ties every call beneath one model-issued call to a single recorder. Scopes are keyed by the id of the calling tool call. A model call gets a scope lazily on its first nested call.

Nested ids are `callerId/n`, numbered per caller. Because the nested call itself gets a scope (see below), a nested tool that makes its own nested calls produces ids like `a/1/1`, all feeding the same top-level recorder.

```ts ! nested-tool-calls.ts
/** Calls below one model-issued call share its recorder. */
interface CallScope {
	recorder: NestedCallRecorder;
	nextId: number;
	/** Set inside a call that holds the exclusive queue, so its own nested calls do not wait on it. */
	holdsQueue: boolean;
}
// ...
export class NestedToolCallRunner {
	private readonly host: NestedToolCallHost;
	/** Scopes by the id of the calling tool call. */
	private readonly scopes = new Map<string, CallScope>();
	/** Serializes nested calls that must not run concurrently. */
	private queueTail: Promise<void> = Promise.resolve();

	constructor(host: NestedToolCallHost) {
		this.host = host;
	}
		// ...
		let scope = this.scopes.get(callerId);
		if (!scope) {
			scope = { recorder: new NestedCallRecorder(), nextId: 1, holdsQueue: false };
			this.scopes.set(callerId, scope);
		}
		const toolCall: AgentToolCall = {
			type: "toolCall",
// !mark
			id: `${callerId}/${scope.nextId++}`,
			name,
			arguments: (args ?? {}) as AgentToolCall["arguments"],
		};
		const record = scope.recorder.start(toolCall);
		await this.host.emit({
			type: "tool_execution_start",
			toolCallId: toolCall.id,
			toolName: name,
			args: toolCall.arguments,
			parentToolCallId: callerId,
		});
```

## !!steps Serializing sequential tools

A call is exclusive when the agent runs tools sequentially, or when the target tool declares `executionMode` as sequential. Exclusive calls chain onto `queueTail`: each waits for the previous exclusive call and publishes its own release promise.

`holdsQueue` prevents deadlock. A call running inside an exclusive call inherits the flag, so its own nested calls skip the queue instead of waiting on the call that is waiting on them. Non-exclusive calls run concurrently.

```ts ! nested-tool-calls.ts
// !mark(1:4)
		const exclusive =
			!scope.holdsQueue &&
			(this.host.isSequential() ||
				this.host.getTools().find((tool) => tool.name === name)?.executionMode === "sequential");
		let release: (() => void) | undefined;
		if (exclusive) {
// !mark(1:5)
			const previous = this.queueTail;
			this.queueTail = new Promise((resolve) => {
				release = resolve;
			});
			await previous;
		}
		this.scopes.set(toolCall.id, {
			recorder: scope.recorder,
			nextId: 1,
			holdsQueue: scope.holdsQueue || exclusive,
		});
```

## !!steps Running, cleanup and the end event

The call goes through `host.runToolCall`, which applies the session's hooks. Partial results are forwarded to the caller's `onUpdate` and also emitted as update events.

The `finally` block always deletes the call's scope and releases the queue, even if the pipeline throws. After the call, the record is finished and usage is added. The comment explains why usage is tracked here: nested results are never persisted themselves, so the recorder is the only place their cost survives.

```ts ! nested-tool-calls.ts
		let outcome: AgentToolCallOutcome;
		try {
			outcome = await this.host.runToolCall(toolCall, callerId, options.signal, async (partialResult) => {
				options.onUpdate?.(partialResult);
				await this.host.emit({
					type: "tool_execution_update",
					toolCallId: toolCall.id,
					toolName: name,
					args: toolCall.arguments,
					partialResult,
					parentToolCallId: callerId,
				});
			});
// !mark(1:3)
		} finally {
			this.scopes.delete(toolCall.id);
			release?.();
		}

		scope.recorder.finish(record, outcome.isError, textOf(outcome.result));
// !mark
		// Nested results are not persisted, so their usage is only counted through the recorder.
		if (outcome.result.usage) scope.recorder.addUsage(outcome.result.usage);
		await this.host.emit({
			type: "tool_execution_end",
			toolCallId: toolCall.id,
			toolName: name,
			result: outcome.result,
			isError: outcome.isError,
			parentToolCallId: callerId,
		});
		return outcome;
	}
```

## !!steps Handing the record to the outer call

When a model-issued call completes, the session calls `takeRecord` with its id. That removes the scope and returns the snapshot plus total usage, which become `nestedCalls` and an addition to the message's `usage`. The session does this when the tool result message starts, and calls `clear` on `agent_end` to drop leftover scopes.

```ts ! nested-tool-calls.ts
	/** Remove and return the record of the nested calls a model-issued call made. */
// !mark(1:6)
	takeRecord(toolCallId: string): NestedCallSummary | undefined {
		const scope = this.scopes.get(toolCallId);
		this.scopes.delete(toolCallId);
		if (!scope) return undefined;
		return { calls: scope.recorder.snapshot(), usage: scope.recorder.totalUsage };
	}

	clear(): void {
		this.scopes.clear();
	}
}
```

The file is consumed by [agent-session.ts](/docs/src/core/agent-session.ts), which implements the host and calls `execute` when a tool invokes `ctx.executeTool()`. Structurally it is two independent halves: a pure recorder with no I/O, and a runner that owns concurrency.
