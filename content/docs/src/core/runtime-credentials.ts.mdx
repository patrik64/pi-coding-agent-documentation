Some API keys should not be persisted: ones passed on the command line, or injected by an SDK caller. `RuntimeCredentials` implements the `CredentialStore` interface from pi-ai by wrapping a real store and adding an in-memory override map keyed by provider id. It also keeps track of writes still in flight, so the process can wait for an OAuth refresh to be saved before it exits.

It is created by [model-runtime.ts](/docs/src/core/model-runtime.ts), which hands it to the provider machinery, and the underlying persistent store is the one managed through [auth-storage.ts](/docs/src/core/auth-storage.ts).

<Scrollycoding>

## !!steps The overlay and its setters

Overrides are just a map of provider id to key. Setting, removing and testing are synchronous and never touch the wrapped store.

```ts ! runtime-credentials.ts
/** Async credential store overlay for non-persistent runtime API keys. */
export class RuntimeCredentials implements CredentialStore {
	private readonly store: CredentialStore;
// !mark(1:2)
	private readonly overrides = new Map<string, string>();

	constructor(store: CredentialStore) {
		this.store = store;
	}

	setRuntimeApiKey(providerId: string, apiKey: string): void {
		this.overrides.set(providerId, apiKey);
	}

	removeRuntimeApiKey(providerId: string): void {
		this.overrides.delete(providerId);
	}

	hasRuntimeApiKey(providerId: string): boolean {
		return this.overrides.has(providerId);
	}
```

## !!steps Reads and lists see the overrides

`read` returns a synthetic api_key credential when an override exists, and otherwise delegates. Both methods check the abort signal first. `list` merges the store's entries with the overrides, which replace a stored entry of the same provider, so the UI shows the key as configured.

```ts ! runtime-credentials.ts
	async read(providerId: string, options?: AuthOperationOptions): Promise<Credential | undefined> {
		options?.signal?.throwIfAborted();
		const override = this.overrides.get(providerId);
// !mark
		return override ? { type: "api_key", key: override } : this.store.read(providerId, options);
	}

	async list(options?: AuthOperationOptions): Promise<readonly CredentialInfo[]> {
		const entries = new Map((await this.store.list(options)).map((entry) => [entry.providerId, entry]));
		options?.signal?.throwIfAborted();
// !mark(1:3)
		for (const providerId of this.overrides.keys()) {
			entries.set(providerId, { providerId, type: "api_key" });
		}
		return [...entries.values()];
	}
```

## !!steps Writes go to the store, and are tracked

`modify` bypasses the overrides entirely, so a refresh or login writes to the persistent store while the override still wins on read. `delete` removes from the store first, then drops the override, so logging out also clears a runtime key.

Each `modify` is also recorded in `pendingModifications` until it is written or fails. The tracked promise swallows the outcome, so it never rejects; the caller still gets the original promise and sees the real error.

```ts ! runtime-credentials.ts
	/** Modifications not yet written or failed, for example an OAuth refresh. */
	private readonly pendingModifications = new Set<Promise<void>>();
// ...
// !mark(1:6)
	modify(
		providerId: string,
		fn: (current: Credential | undefined) => Promise<Credential | undefined>,
		options?: AuthOperationOptions,
	): Promise<Credential | undefined> {
		const modification = this.store.modify(providerId, fn, options);
		const pending = modification.then(
			() => undefined,
			() => undefined,
		);
		this.pendingModifications.add(pending);
		void pending.finally(() => this.pendingModifications.delete(pending));
		return modification;
	}
```

## !!steps Waiting for writes before exit

An OAuth refresh spends the single-use refresh token as soon as the token request reaches the provider. If pi exited after that but before the new token was written, `auth.json` would keep only the spent token and the next request would fail. This happened in RPC mode, where a background catalog refresh could renew an expired token while the client sent SIGTERM.

`settled` waits for every modification started so far. [model-runtime.ts](/docs/src/core/model-runtime.ts) exposes it as `settleCredentialWrites`, and `dispose` in [agent-session-runtime.ts](/docs/src/core/agent-session-runtime.ts) awaits it, so every mode waits on its way out. There is no extra timeout because the refresh and the 30 second lock wait are already bounded.

```ts ! runtime-credentials.ts
	/**
	 * Resolves when every modification started so far is written or failed. An OAuth refresh may
	 * already have spent the single-use refresh token, so exiting before its result is written would
	 * leave only the spent token in auth.json.
	 */
	async settled(): Promise<void> {
		await Promise.all(this.pendingModifications);
	}

	async delete(providerId: string, options?: AuthOperationOptions): Promise<void> {
		options?.signal?.throwIfAborted();
// !mark(1:2)
		await this.store.delete(providerId, options);
		this.overrides.delete(providerId);
	}
}
```

</Scrollycoding>

The overlay is the reason a runtime key beats a stored OAuth token for the same provider. It does not support listing credential details beyond the type.
