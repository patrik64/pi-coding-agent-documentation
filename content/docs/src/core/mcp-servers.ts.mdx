pi supports MCP servers either from `mcp.json` or registered at runtime by extensions through `pi.registerMcpServer()`. The core deliberately does very little with them: this file defines the config shapes, validates raw entries, answers questions about tool names and exposure, and stores registrations. Actually connecting is left to the MCP extension under [extensions/mcp](/docs/src/extensions/mcp/index.ts) or any extension that listens for `mcp_servers_change`.

The standard `mcpServers` shape (stdio and HTTP fields, `oauth`, `enabled`, `description`, `timeout`) and its validation moved into the `@earendil-works/pi-mcp` package, together with the namespace and tool-name helpers. What stays here is what only pi has: the exposure model, which decides whether a server's tools are shown to the model directly, deferred behind a search tool, hidden, or reachable only from codemode scripts; the `auth.provider` field; and the rule for which OAuth callbacks pi's Client ID Metadata Documents cover.

Validation is used by [config.ts](/docs/src/extensions/mcp/config.ts), [cli.ts](/docs/src/extensions/mcp/cli.ts) and the extension [loader.ts](/docs/src/core/extensions/loader.ts); the tool-name helpers by [agent-session.ts](/docs/src/core/agent-session.ts) and [sdk.ts](/docs/src/core/sdk.ts); and [radius-mcp.ts](/docs/src/core/radius-mcp.ts) builds an `McpHttpServerConfig`. The registry connects to the extension runner in [runner.ts](/docs/src/core/extensions/runner.ts).

## !!steps Matching tool names with wildcards

`toolPatternRegExp` escapes every regex metacharacter in each piece between `*` characters, and then joins the pieces with `.*`. That makes `*` the only wildcard, anchored to the whole name.

`createToolNameMatcher` splits entries into an exact-name set and a pattern list, so the common exact case stays a set lookup.

```ts ! mcp-servers.ts
function toolPatternRegExp(pattern: string): RegExp {
	const source = pattern
		.split("*")
		// !mark(1:3)
		.map((part) => part.replace(/[.+?^${}()|[\]\\]/g, "\\$&"))
		.join(".*");
	return new RegExp(`^${source}$`);
}

/** Whether a tool name matches any of the entries, each an exact name or a pattern. */
export function createToolNameMatcher(entries: readonly string[]): (name: string) => boolean {
	// !mark(1:3)
	const names = new Set(entries.filter((entry) => !entry.includes("*")));
	const patterns = entries.filter((entry) => entry.includes("*")).map(toolPatternRegExp);
	return (name) => names.has(name) || patterns.some((pattern) => pattern.test(name));
}
```

## !!steps Recognising MCP tools

Server tools are named `mcp__<server>__<tool>`. The three resource tools have fixed names and span all servers, so they are recognised from a small set. `isMcpToolName` answers whether a tool name came from MCP.

```ts ! mcp-servers.ts
/** MCP resource tools, which reach every server with resources. */
export const LIST_MCP_RESOURCES_TOOL = "list_mcp_resources";
export const LIST_MCP_RESOURCE_TEMPLATES_TOOL = "list_mcp_resource_templates";
export const READ_MCP_RESOURCE_TOOL = "read_mcp_resource";

const MCP_RESOURCE_TOOLS: ReadonlySet<string> = new Set([
	LIST_MCP_RESOURCES_TOOL,
	LIST_MCP_RESOURCE_TEMPLATES_TOOL,
	READ_MCP_RESOURCE_TOOL,
]);

/** Whether a tool comes from MCP: a server tool (`mcp__<server>__<tool>`) or a resource tool. */
// !mark(1:2)
export function isMcpToolName(name: string): boolean {
	return name.startsWith("mcp__") || MCP_RESOURCE_TOOLS.has(name);
}
```

## !!steps Exposure levels and aliases

Four exposures control visibility. `direct` declares tools to the model as usual. `deferred` hides them until the `tool_search` tool loads them. `codemode` makes them callable only from codemode scripts, found with `searchTools()`. `hidden` registers them but makes them unreachable.

The default is `codemode`. An older spelling, `codemode-deferred`, is accepted and rewritten to `codemode` during validation.

```ts ! mcp-servers.ts
/**
 * - `codemode`: tools are callable from codemode scripts but neither declared to the model nor
 *   listed in the codemode description, which lists only the server's namespace. Scripts find them
 *   with `searchTools()`. `codemode-deferred` is accepted as an alias.
 * - `deferred`: not declared to the model until the `tool_search` tool loads them; the model then
 *   calls them directly. Does not need codemode.
 * - `direct`: tools are declared to the model like any other tool (and callable from codemode).
 * - `hidden`: tools are registered but unreachable.
 */
// !mark
export type McpExposure = "codemode" | "deferred" | "direct" | "hidden";

const MCP_EXPOSURES: readonly string[] = ["codemode", "deferred", "direct", "hidden"] satisfies McpExposure[];

/** Older exposure names, accepted in configs and replaced by their current name when validated. */
// !mark
const MCP_EXPOSURE_ALIASES: Readonly<Record<string, McpExposure>> = { "codemode-deferred": "codemode" };
```

## !!steps pi's fields on top of pi-mcp's

The `mcpServers` shape itself now belongs to the `@earendil-works/pi-mcp` package, so other applications read the same entries the same way. pi imports its types and validator under `...Fields` aliases and adds only what is pi-specific.

`McpServerConfigBase` holds those additions: the exposure, per-tool overrides, and two shared fields (`description`, `timeout`) declared again so pi's generated documentation can describe how pi uses them. `toolExposure` resolution is documented in the comment: an exact name beats patterns, and among patterns the first in object order wins. Setting the server to `hidden` and then overriding a few tools is the way to expose only those. `enabled` is no longer listed here because it is one of pi-mcp's shared fields.

```ts ! mcp-servers.ts
import {
	type McpHttpServerConfig as McpHttpServerFields,
	type McpOAuthConfig as McpOAuthFields,
	type McpStdioServerConfig as McpStdioServerFields,
	validateMcpServerConfig as validateMcpServerFields,
} from "@earendil-works/pi-mcp";
// ...
/**
 * pi's fields of every server entry, beside the shared `mcpServers` fields of pi-mcp. `description`
 * and `timeout` are shared fields, declared again for pi's documentation.
 */
interface McpServerConfigBase {
	/** Default: `codemode`. */
	// !mark
	exposure?: McpExposure;
	/**
	 * What the server offers, in a sentence. The `mcp_servers` system prompt section lists the server
	 * with it, tool search ranks the server's tools by it, and codemode's `describeNamespace()` returns it.
	 */
	description?: string;
	/**
	 * Exposure of single tools, overriding `exposure`. Keys are tool names as the server offers them,
	 * or patterns where `*` matches any characters. An exact name wins over patterns; among patterns
	 * the first match in the object wins. `hidden` removes tools, so `"exposure": "hidden"` with
	 * overrides for a few tools exposes only those.
	 */
	// !mark
	toolExposure?: Record<string, McpExposure>;
	/** Per-request timeout in seconds. Progress notifications from the server reset it. Default: 60. */
	timeout?: number;
}
```

## !!steps Stdio and HTTP server shapes

Each server type extends both pi-mcp's fields (`command` and `args`, or `url`) and pi's base. The redeclared `env`, `cwd` and `headers` fields add pi's notes: values may be `${NAME}` references or `!cmd` commands, and a relative `cwd` resolves against the session directory. `oauth` is narrowed to pi's documented `McpOAuthConfig`.

`auth` is pi's own field and a security rule: it sends a pi provider's credential to the URL, so it is forbidden in project `mcp.json` files and requires https unless the host is loopback.

```ts ! mcp-servers.ts
// !mark
export interface McpStdioServerConfig extends McpStdioServerFields, McpServerConfigBase {
	// Shared fields, declared again for pi's documentation.
	/** Values may reference environment variables (`${NAME}`) or commands (`!cmd`). */
	env?: Record<string, string>;
	/** Relative paths resolve against the session working directory. */
	cwd?: string;
}
// ...
// !mark
export interface McpHttpServerConfig extends McpHttpServerFields, McpServerConfigBase {
	// `headers` is shared, declared again for pi's documentation; `oauth` narrows to pi's documented type.
	/** Values may reference environment variables (`${NAME}`) or commands (`!cmd`). */
	headers?: Record<string, string>;
	oauth?: McpOAuthConfig;
	/**
	 * Send the token of a pi provider (`/login <provider>`) instead of using OAuth. Not allowed in project
	 * `mcp.json` files, and requires https except on loopback hosts, since it sends the credential to `url`.
	 */
	// !mark
	auth?: { provider: string };
}

export type McpServerConfig = McpStdioServerConfig | McpHttpServerConfig;
```

## !!steps OAuth client settings and pi's metadata documents

`McpOAuthConfig` keeps the shared fields from pi-mcp (`clientId`, `callbackPort`, `callbackUrl`, `scope`, `authServerMetadataUrl`) and redeclares the three whose documentation is pi-specific.

`clientRegistration` now defaults to `auto`: pi identifies itself with its Client ID Metadata Document on pi.dev when the authorization server supports that for public clients, and falls back to dynamic client registration otherwise. A custom `clientName` or a callback the documents do not list forces dynamic registration.

`isClientMetadataDocumentCallback` encodes which callbacks the documents on pi.dev list: path `/callback` on localhost or 127.0.0.1, on any port. Validation below uses it, and [oauth.ts](/docs/src/extensions/mcp/oauth.ts) hands it to pi-mcp as the documents' `listsRedirectUrl` check.

```ts ! mcp-servers.ts
/** OAuth client settings for servers that do not support dynamic client registration. */
export interface McpOAuthConfig extends McpOAuthFields {
	// Shared fields, declared again for pi's documentation.
	/** May reference environment variables (`${NAME}`) or commands (`!cmd`). */
	clientSecret?: string;
	/**
	 * `client_name` sent with dynamic client registration, for servers that only accept known clients.
	 * Default: `pi`.
	 */
	clientName?: string;
	/**
	 * How pi identifies itself without `clientId`. `auto` (default): pi's Client ID Metadata Document on
	 * pi.dev when the authorization server supports it for public clients, otherwise dynamic client
	 * registration; with `clientName` or a `callbackUrl` other than `/callback` on localhost or 127.0.0.1,
	 * always dynamic client registration. `cimd`: always the document, and sign-in fails without support.
	 * `dcr`: always dynamic client registration.
	 */
	// !mark
	clientRegistration?: "auto" | "dcr" | "cimd";
}

/**
 * Whether pi's Client ID Metadata Documents list a redirect URI for the loopback `callbackUrl`: they list
 * `/callback` on localhost and 127.0.0.1, on any port. Without `callbackUrl`, pi uses such a URI.
 */
export function isClientMetadataDocumentCallback(callbackUrl: string | undefined): boolean {
	if (callbackUrl === undefined) return true;
	const url = new URL(callbackUrl);
	// !mark
	return url.hostname !== "[::1]" && url.pathname === "/callback";
}
```

## !!steps Resolving the effective exposure

`getMcpToolExposure` applies the documented precedence: exact override, then the first matching pattern in insertion order, then the server's own exposure, then `codemode`.

```ts ! mcp-servers.ts
/** Exposure of one tool of a server: its `toolExposure` entry, else the server's `exposure`. */
export function getMcpToolExposure(config: McpServerConfig, toolName: string): McpExposure {
	const overrides = config.toolExposure ?? {};
	// !mark(1:6)
	const exact = overrides[toolName];
	if (exact !== undefined) return exact;
	for (const [pattern, exposure] of Object.entries(overrides)) {
		if (pattern.includes("*") && toolPatternRegExp(pattern).test(toolName)) return exposure;
	}
	return config.exposure ?? "codemode";
}
```

## !!steps Validating a server entry

`validateMcpServerConfig` returns either a config or an error string, never throwing. It first resolves exposure aliases on a copy, then hands the entry to pi-mcp, which checks the server name, the shared fields, the stdio or HTTP shape and the `oauth` block, and tags the result with its kind. pi-mcp refuses `clientRegistration: "cimd"` unless the application supplies `checkMetadataDocumentCallback`, so pi passes one built on `isClientMetadataDocumentCallback`.

pi-mcp keeps fields it does not know, so pi then checks its own: `checkExposures` validates `exposure` and every `toolExposure` value, and for HTTP servers `checkAuth` enforces the https-or-loopback rule for `auth`. The final cast is safe because those checks just ran.

```ts ! mcp-servers.ts
/** Checks `exposure` and `toolExposure`, after aliases were resolved. Returns an error message. */
function checkExposures(entry: Record<string, unknown>): string | undefined {
	const { exposure, toolExposure } = entry;
	const exposures = MCP_EXPOSURES.map((value) => `"${value}"`).join(", ");
	if (exposure !== undefined && !isExposure(exposure)) return `exposure must be one of ${exposures}`;
	if (toolExposure !== undefined) {
		if (!isRecord(toolExposure)) return "toolExposure must map tool names to exposures";
		for (const [tool, value] of Object.entries(toolExposure)) {
			if (!isExposure(value)) return `toolExposure "${tool}" must be one of ${exposures}`;
		}
	}
	return undefined;
}

const LOOPBACK_HOSTS = ["localhost", "127.0.0.1", "[::1]"];

/** Checks `auth` of an HTTP server, which sends a provider's credential to `url`. Returns an error message. */
function checkAuth(auth: unknown, url: string): string | undefined {
	if (auth === undefined) return undefined;
	if (!isRecord(auth) || typeof auth.provider !== "string" || !auth.provider) {
		return "auth.provider must be a provider name";
	}
	const parsed = new URL(url);
	// !mark(1:3)
	if (parsed.protocol !== "https:" && !LOOPBACK_HOSTS.includes(parsed.hostname)) {
		return "auth requires an https URL, or http on localhost, 127.0.0.1, or [::1]";
	}
	return undefined;
}
// ...
export function validateMcpServerConfig(name: string, raw: unknown): McpServerConfig | string {
	// !mark(1:6)
	const result = validateMcpServerFields(name, isRecord(raw) ? resolveExposureAliases(raw) : raw, {
		checkMetadataDocumentCallback: (callbackUrl) =>
			isClientMetadataDocumentCallback(callbackUrl)
				? undefined
				: 'oauth.clientRegistration "cimd" requires oauth.callbackUrl on localhost or 127.0.0.1 with path /callback',
	});
	if (result.kind === "invalid") return result.error;
	const error =
		checkExposures(result.config) ??
		(result.kind === "http" ? checkAuth(result.config.auth, result.config.url) : undefined);
	if (error) return `server "${name}": ${error}`;
	// The cast holds because pi's fields were checked above, which the types cannot express.
	return result.config as McpServerConfig;
}
```

## !!steps The registry for extension-registered servers

`McpServerRegistry` stores registrations in a map, keyed by server name, and calls a single change listener after each change. The runner sets that listener when it binds, in order to emit `mcp_servers_change`.

`unregister` checks `extensionPath` first, so one extension cannot remove another's server. `register` has no such check; its comment says the caller verifies ownership. `list` returns copies, with the config cloned.

```ts ! mcp-servers.ts
/** Servers registered by the extensions of one runtime. */
export class McpServerRegistry {
	private readonly servers = new Map<string, RegisteredMcpServer>();
	private changeListener: (() => void) | undefined;

	/** Register or replace a server. The caller checks ownership. */
	// !mark(1:3)
	register(server: RegisteredMcpServer): void {
		this.servers.set(server.name, server);
		this.changeListener?.();
	}

	/** Remove a server registered by `extensionPath`. Servers of other extensions are left alone. */
	unregister(name: string, extensionPath: string): void {
		// !mark
		if (this.servers.get(name)?.extensionPath !== extensionPath) return;
		this.servers.delete(name);
		this.changeListener?.();
	}

	get(name: string): RegisteredMcpServer | undefined {
		return this.servers.get(name);
	}

	/** Copies of the registered servers, in registration order. */
	list(): RegisteredMcpServer[] {
		// !mark
		return [...this.servers.values()].map((server) => ({ ...server, config: structuredClone(server.config) }));
	}

	/** Called after every change. The runner sets it when it binds, to emit `mcp_servers_change`. */
	setChangeListener(listener: (() => void) | undefined): void {
		this.changeListener = listener;
	}
}
```

Config files and extension registrations both pass through the validation function, so the same rules apply to either source, and the shared part of those rules is the same in every application built on pi-mcp. One structural note: exposure aliases are resolved only inside validation, so code that reads a raw config without validating it can still see the old spelling.
