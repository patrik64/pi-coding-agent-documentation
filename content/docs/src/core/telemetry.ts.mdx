A single decision function: is install telemetry enabled? The answer comes from
the `PI_TELEMETRY` environment variable when it is set, and from the saved
setting otherwise. The file only decides; it does not send anything.

<Scrollycoding>

## !!steps What counts as true

An unset or empty value is false. Otherwise the accepted spellings are `1`,
`true` and `yes`, with the words matched case-insensitively. Anything else, such
as `0`, `off` or garbage, is false.

```ts ! telemetry.ts
function isTruthyEnvFlag(value: string | undefined): boolean {
	if (!value) return false;
	return value === "1" || value.toLowerCase() === "true" || value.toLowerCase() === "yes";
}
```

## !!steps The environment wins when it is defined

The check is `!== undefined`, not truthiness, so `PI_TELEMETRY=` (empty) or
`PI_TELEMETRY=0` explicitly disables telemetry even if the setting says
enabled. Only when the variable is absent does the code read
`getEnableInstallTelemetry()` from
[settings-manager.ts](/docs/src/core/settings-manager.ts). The env value is a
default parameter, which lets tests pass a value without touching `process.env`.

```ts ! telemetry.ts
export function isInstallTelemetryEnabled(
	settingsManager: SettingsManager,
	telemetryEnv: string | undefined = process.env.PI_TELEMETRY,
): boolean {
	// !mark
	return telemetryEnv !== undefined ? isTruthyEnvFlag(telemetryEnv) : settingsManager.getEnableInstallTelemetry();
}
```

</Scrollycoding>

Two callers consult it. `reportInstallTelemetry` in
[interactive-mode.ts](/docs/src/modes/interactive/interactive-mode.ts) sends the
one install ping to `pi.dev` only when it returns true (and `PI_OFFLINE` is
unset). [client-identity.ts](/docs/src/core/client-identity.ts) uses the same
answer to decide whether provider requests carry pi's attribution. The setting
it reads is defined by
[settings-manager.ts](/docs/src/core/settings-manager.ts). Keeping the opt-out
rule here means `PI_TELEMETRY` switches off both the ping and the attribution.
