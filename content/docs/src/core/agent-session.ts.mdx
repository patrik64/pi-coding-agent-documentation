The `Agent` from pi-agent-core knows how to run a loop of model calls and tool
calls. It knows nothing about session files, extensions, context windows or
which tools the user enabled. `AgentSession` is everything around that loop.
Interactive, print and RPC modes all hold one and add only their own I/O on top.

At 4,000+ lines it is the largest file in the package, but it is organized in
labelled sections: event handling and persistence, prompting, model and
thinking management, compaction, extension binding, retry, bash, tree
navigation and stats. The constructor installs a set of hooks on the `Agent`
(tool calls, request preparation, turn boundaries, context transforms), and
nearly everything interesting happens inside those hooks or in the
`prompt()` path that feeds the loop.

It is created by [sdk.ts](/docs/src/core/sdk.ts), replaced as a whole by
[agent-session-runtime.ts](/docs/src/core/agent-session-runtime.ts), persists
through [session-manager.ts](/docs/src/core/session-manager.ts) and talks to
extensions through [runner.ts](/docs/src/core/extensions/runner.ts).

## !!steps The event stream modes subscribe to

`AgentSessionEvent` extends the core `AgentEvent` rather than replacing it. Two
changes: `agent_end` gains `willRetry` (so a UI can keep its spinner while the
session retries or compacts), and a set of session-level events is added for
queue changes, compaction, auto-retry, appended entries and bash output.

`agent_settled` carries `aborted`, so a host can tell a cancelled run from one
that finished. Interactive mode uses it to report the terminal's program status
as idle rather than done after an abort (see
[program-status-reporter.ts](/docs/src/modes/interactive/program-status-reporter.ts)).

Tool execution events can carry a `parentToolCallId` when a tool made the call
through `ctx.executeTool()`. `parseSkillBlock` above it is the inverse of the
skill expansion done in `_expandSkillCommand`, used by UIs to render a skill
invocation as a collapsed block.

## !!steps State and the constructor

The field list shows what the class juggles: steering and follow-up queues
(kept as plain strings for UI display), compaction and retry abort
controllers, a pending list of custom messages, and many extension-binding
fields. Most mutable flags exist to answer one question precisely: is the
session idle?

The constructor subscribes to the agent, installs six hooks and builds the
runtime (tools, extension runner). When the initial tools come from the
`defaultTools` setting rather than an explicit `--tools` list, it then replaces
them with the loadout the transcript records, so a resumed session gets back
the tools it had. `--tools` entries of the form `+name` or `-name` modify the
setting instead of replacing it, so they are kept as `_defaultToolModifiers`
and applied on top of the restored loadout.

```ts ! agent-session.ts
	constructor(config: AgentSessionConfig) {
```

## !!steps Persistence happens in the event handler

`_handleAgentEvent` is the heart of the class. On every event it forwards to
extensions first, then to public listeners, then persists. Persistence is
keyed on `message_end`: custom messages become `CustomMessageEntry`, and
system, user, assistant and tool-result messages become regular message
entries. The returned entry ID is remembered in a `WeakMap` so later hooks can
map a message object back to its entry.

Other message kinds (bash executions, compaction summaries, branch summaries)
are persisted by their own code paths, as the comment says.

## !!steps Queued messages are fixed up on delivery

Before any of that, a user `message_start` is matched against the steering and
follow-up queues kept for display, so the UI sees the updated queue in the
same event. An image-only message has empty text, and its queue entry is the
empty string, so the match now runs even when there is no text. A guard on
the text used to skip such messages, leaving them in the displayed queue after
they were delivered.

Images in idle prompts are resized to the model's limits, but steering and
follow-up messages used to be sent and saved at full size. `_queueSteer` and
`_queueFollowUp` now mark messages that carry images in a `WeakSet`, and on
delivery the images are normalized in place, with resize hints appended to the
text, before extensions, listeners and persistence see the message. Doing it
at delivery rather than when queuing keeps queuing synchronous, so a slow
resize cannot leave a message stranded after the run ends, and it uses the
model that is current when the message is actually sent.

```ts ! agent-session.ts
		if (event.type === "message_start" && event.message.role === "user") {
```

## !!steps Extensions can rewrite a message before it is saved

For `message_end`, `_emitExtensionEvent` asks the runner for a replacement
message. Because persistence runs afterward using the same `event.message`
object, the replacement is applied by mutating that object in place: all its
keys are deleted and the replacement's are assigned. That keeps agent state,
later turn events, listeners and the saved entry consistent without any of
them needing to know a replacement happened.

Handlers are untyped at runtime, so a replacement with null content is
normalized to an empty array before it can reach history.

```ts ! agent-session.ts
		} else if (event.type === "message_end") {

			if (replacement) {

				// normalize so it never enters agent state or session history.
				const normalized =
					(replacement.role === "user" ||
						replacement.role === "assistant" ||
						replacement.role === "toolResult" ||
						replacement.role === "custom") &&
```

## !!steps Tool hooks replace per-tool wrappers

`beforeToolCall` and `afterToolCall` are installed once on the agent. They
read `this._extensionRunner` at call time, so reloading extensions swaps the
runner without reinstalling hooks. `_beforeToolCall` emits `tool_call` and
lets a handler block execution; a non-Error throw is wrapped so the failure
always blocks.

`_afterToolCall` emits `tool_result`, which may replace content, details,
`isError` or usage, then runs image normalization after the hook so images
injected by extensions are resized too, using the limits of the current model.
If nothing changed it returns `undefined` and the original result stands.
(The `tool_execution_end` event forwarded to extensions also carries the
tool's `durationMs` when the agent measured it.)

```ts ! agent-session.ts
		const content = hookResult?.content ?? result.content ?? [];
		// Runs after the extension hook so images injected or replaced by extensions are normalized too.
		const resizeOptions = this._limitsModel()?.inputLimits?.images?.resize;
		const normalizedContent = await normalizeToolResultImages(content, {
			autoResizeImages: this.settingsManager.getImageAutoResize(),
			...(resizeOptions ? { resizeOptions } : {}),
		});

		// !mark(1:3)
		if (!hookResult && normalizedContent === content) {
			return undefined;
		}

		// The hook result already dropped structured content that replaced content no longer matches.
		return {
			content: normalizedContent,
			details: hookResult?.details,
			structuredContent: hookResult ? hookResult.structuredContent : result.structuredContent,
			isError: hookResult?.isError ?? isError,
			usage: hookResult?.usage,
		};
```

## !!steps What prompt does before the model is called

`prompt()` is a long gate. Slash commands from extensions run immediately,
even while streaming. A prompt is refused while a manual compaction or a tree
navigation's branch summary is in progress (the error message mentions only
compaction). Everything after that runs in
`_preparePrompt`: the `input` extension event can swallow or transform the
text, skill and template expansion follow, and if a run is active the message
is queued as a steer or follow-up (a missing `streamingBehavior` throws).
Otherwise it requires a model and usable auth and returns a trigger describing
the run to start.

Input hooks and the auth check are asynchronous, so `_promptPreflightCount`
is raised around them. `navigateTree` refuses while it is non-zero; before
this, a navigation could switch the branch underneath a prompt that had not
started yet. There is no gap afterwards because `_startRun` marks the run
active synchronously.

```ts ! agent-session.ts
		if (this._compactionAbortController !== undefined || this._branchSummaryAbortController !== undefined) {
```

## !!steps Starting a run

Every run starts in `_startRun`, whether it comes from `prompt()` or from a
custom message sent with `triggerTurn`. The session counts as busy from the
first line, before `before_agent_start` handlers run. A message sent while
they run is therefore queued into this run instead of starting a second one,
and an abort requested meanwhile is honored as soon as the run exists:
`_handleAgentEvent` calls `agent.abort()` on `agent_start` when the abort flag
is set.

If preparation throws, the busy flag is cleared and idle waiters are released.
Bash and custom messages held back while the run was starting are flushed
before its first request, which places them ahead of the starting message just
as they would have been while idle. Then the live model and thinking level are
recorded on the branch, and pending tool names are dropped because the run
records the loadout in the transcript.

```ts ! agent-session.ts
	private async _startRun(trigger: BeforeAgentStartTrigger, onStarted?: () => void): Promise<void> {
		// !mark
		this._isAgentRunActive = true;
		this._agentRunAbortRequested = false;
		let messages: AgentMessage[];
		try {
			messages = await this._prepareRun(trigger);
		} catch (error) {
			this._isAgentRunActive = false;
			this._flushPendingBashMessages();
			this._flushPendingCustomMessages();
			this._resolveIdleWaitIfIdle();
			throw error;
		}
		// Messages held while the run was starting go before its starting messages, as they would
		// have while idle. No run exists yet, so they cannot split a tool call from its result.
		this._flushPendingBashMessages();
		this._flushPendingCustomMessages();
		onStarted?.();

		// Compaction before the prompt may have scheduled a retry; the new prompt replaces it.
		this._failedResponse = undefined;
		this._recordSelection();
		// The run records the loadout in the transcript; restored tools that did not register by now
		// are dropped, so a tool that never registers does not stay pending.
		this._pendingToolNames.clear();
```

## !!steps Building the starting messages

`_prepareRun` checks compaction against the last assistant message, then
emits `before_agent_start` with the trigger. The event is a union on
`messageType`: `"user"` carries the prompt text and images, `"custom"` carries
the starting custom message. Custom-message runs used to skip the event, and
after their first tool call the next-turn refresh patched away the prompt
sections handlers had added, changing the system prompt mid-run and breaking
the provider's prompt cache.

The comments explain the order: images are normalized after the event so an
extension that switches model changes the resize profile. The starting message
is followed by pending `nextTurn` messages and the handlers' messages, and a
system patch goes first when the prompt changed.

```ts ! agent-session.ts
	private async _prepareRun(trigger: BeforeAgentStartTrigger): Promise<AgentMessage[]> {

			messages.push(trigger.message);
		} else {

			// determines the resize profile used for the request and history.
			const normalized = await this._normalizePromptImages(trigger.images);
```

## !!steps The run loop after the agent returns

After preparation, `_startRun` calls `agent.prompt` and then loops. After each agent run,
`_handlePostAgentRun` decides whether to continue: a retryable error with
budget left (`_prepareRetry` sleeps with backoff, and the failed response is
remembered so routing knows it is a retry), a compaction that wants a retry,
or queued messages. If nothing continues, the `agent_before_settle` boundary
gives extensions one last chance to keep the run going.

The `finally` block always clears transient state, flushes pending bash and
custom messages, and emits `agent_settled` (with `aborted` set from the abort
flag), which is what resolves `waitForIdle`. A user abort sets a flag checked
between each step so the loop exits promptly.

```ts ! agent-session.ts
		try {
			await this.agent.prompt(messages);
			// !mark
			while (!this._agentRunAbortRequested) {
				if (await this._handlePostAgentRun()) {
					if (this._agentRunAbortRequested) break;
					await this.agent.continue();
					continue;
				}
				if (this._agentRunAbortRequested || !(await this._runBeforeSettleBoundary())) break;
				if (this._agentRunAbortRequested) break;
				await this.agent.continue();
			}
		} finally {
			if (this._agentRunAbortRequested) this._finishCancelledRetry();
			this._failedResponse = undefined;
			this._runSystemPromptOptions = undefined;
			this._flushPendingBashMessages();
			this._flushPendingCustomMessages();
			// !mark
			await this._emitAgentSettled();
		}
```

## !!steps Overflow recovery and threshold compaction

`_checkCompaction` handles three cases. A context-overflow error (or a
truncated response that ended under the model's output limit) triggers
compaction and a retry, but only once: `_overflowRecoveryAttempted` turns a
second failure into a `compaction_end` event with an error message. A response
that completed but overflowed is compacted without retry, because
`agent.continue()` cannot resume from a finished assistant message. Otherwise
usage is compared against the threshold.

Two guards prevent false triggers: a message from a different model than the
current one never counts as overflow, and any message older than the latest
compaction entry is ignored. Before the retry, the failed attempt is durably
omitted from the projection with context-edit entries, together with its tool
results. `_omitRecoveryAttempt` finds those results in the projected context
(matching by entry id too, since an earlier edit may have replaced the
projected copy), so the pair stays together whether the attempt came from this
run or a resumed session. An unpaired tool result would fail the next request.

```ts ! agent-session.ts
		if (contextOverflow || recoverableLength) {

			// agent.continue() cannot continue from a completed assistant response.
			if (!willRetry) {
				return await this._runAutoCompaction("overflow", false);
			}

			// !mark
			if (this._overflowRecoveryAttempted) {
// ...
			// Persistently omit the selected final attempt before post-run recovery compaction.
			// !mark(1:4)
			this._overflowRecoveryAttempted = true;
			this._omitRecoveryAttempt(assistantMessage);
```

## !!steps Which tools exist, and which are declared

Tool visibility is layered. `_isAllowedTool` applies `--tools` and
`--exclude-tools` to decide whether a tool is registered at all, with the rule
that MCP tools stay registered for codemode and tool search unless the
allowlist names an MCP tool or is empty. `_isActivatable` decides whether it
may be declared to the model: an MCP tool kept only for tool search can be
active only if it is not `direct` and `tool_search` is registered.

Exposure levels (`direct`, `model-only`, `codemode`, `deferred`, `hidden`)
decide the rest: only `direct` tools that are active, plus every `codemode` or
`deferred` tool, are callable through `ctx.executeTool()`. See
[mcp-servers.ts](/docs/src/core/mcp-servers.ts) for the name matcher.

```ts ! agent-session.ts
	private _isAllowedTool(name: string): boolean {
		if (this._excludedTools?.(name)) return false;
		if (!this._allowedTools || this._allowedTools(name)) return true;
		// !mark
		return !this._allowlistFiltersMcp && isMcpToolName(name);
	}
// ...
	private _isActivatable(name: string): boolean {
		if (!this._allowedTools || this._allowedTools(name) || !isMcpToolName(name)) return true;
		return this._getToolExposure(name) !== "direct" && this._toolRegistry.has("tool_search");
	}
// ...
	private _getCallableTools(active: ReadonlySet<string> = new Set(this.getActiveToolNames())): AgentTool[] {
		return [...this._toolRegistry.values()].filter((tool) => {
			const exposure = this._getToolExposure(tool.name);
			// !mark
			return exposure === "codemode" || exposure === "deferred" || (exposure === "direct" && active.has(tool.name));
		});
	}
```

## !!steps Restoring the loadout from the transcript

`_restoreToolsFromTranscript` runs at construction (when tools come from
`defaultTools`) and after tree navigation. It replays every system message on
the branch, including those before a compaction, because compaction snapshots
are derived from them. A branch with no system message keeps the current
tools. Tools the branch removed stay off.

Extension tools the branch never mentioned were registered after it recorded
its loadout, so they are activated as newly registered tools would be;
built-in tools follow `defaultTools` instead. The `--tools` modifiers apply
last. Names not registered yet, such as tools of MCP servers still
connecting, stay pending and activate when they register.

Setting the loadout is order-stable: `_applyToolLoadout` keeps tools that stay
active in their current order and appends new ones, so passing the same names
in a different order does not change the prompt.

```ts ! agent-session.ts
	private _restoreToolsFromTranscript(modifiers: readonly string[] = []): void {
		this._pendingToolNames.clear();
		// All system messages on the branch, including those before a compaction. Compaction snapshots
		// are derived from these, so replaying them gives the current loadout.
		const systemMessages = this.sessionManager
			.getBranch()
			.flatMap((entry) => (entry.type === "message" && entry.message.role === "system" ? [entry.message] : []));
		// No recorded loadout: keep the current tools.
		if (systemMessages.length === 0) return;
// ...
		// Extension tools the branch never mentioned were registered after it recorded its loadout, so
		// they are activated like newly registered tools. Built-in tools follow `defaultTools` instead.
		const newTools = [...this._toolRegistry.keys()].filter(
			(name) =>
				!mentioned.has(name) && !this._baseToolDefinitions.has(name) && this._isActivatedOnRegistration(name),
		);
		// The recorded loadout plus the new tools, with `--tools +name`/`-name` applied.
		// !mark(1:4)
		const names = applyToolModifiers(
			[...getCurrentTools(systemMessages).map((tool) => tool.name), ...newTools],
			modifiers,
		);
```

## !!steps System prompt as diffs in the transcript

The system prompt is not sent as one fixed string. `_preparePromptAndToolLoadout`
builds structured sections, diffs them against the sections the model last
saw (replayed from the transcript with `getCurrentSystemMessage`), and returns a
`system` message containing only the changes. That message is prepended to the
turn and persisted, so resuming a session reproduces the exact prompt the
model had.

A forced prompt from a `before_agent_start` handler is the exception: it is
projected onto the request head at send time instead of being recorded.
Prompt building itself lives in
[system-prompt.ts](/docs/src/core/system-prompt.ts).

```ts ! agent-session.ts
	private _preparePromptAndToolLoadout(
		options: NormalizedBuildSystemPromptOptions,
		messages: AgentMessage[] = this.agent.state.messages,
	): SystemMessage | undefined {
		options.selectedTools = this._applyToolLoadout(options.selectedTools).map((tool) => tool.name);
		// The tool list and rules must match the declarations the request carries.
		options.hiddenTools = [...this._hiddenDeclarations];
		// !mark(1:4)
		const sections = diffSystemPromptSections(
			getCurrentSystemMessage(messages)?.sections ?? {},
			buildSystemPromptSections(options),
		);
		return sections ? { role: "system", content: "", sections, timestamp: Date.now() } : undefined;
	}
```

## !!steps Changing model and thinking level

`setModel` checks auth, switches `agent.state.model`, and records a
`model_change` entry so resume restores it. Persisting to global defaults only
happens with `persist: true`; otherwise the change is session-only. The
thinking level for the new model comes from `_getThinkingLevelForModelSwitch`
(explicit, then per-model setting, then default), and `setThinkingLevel` clamps
it to what the model supports and appends a transcript entry only if the
level actually changed.

`cycleModel` uses the scoped models list if present, else all available
models. `getNextCycleIndex` handles a current model that is not in the list:
forward picks the first entry and backward the last, so a scope of one model
still switches to it instead of reporting that there is nothing to cycle to.

```ts ! agent-session.ts
	async setModel(model: Model<any>, options: ModelMutationOptions = {}): Promise<void> {
		if (!(await this._modelRuntime.checkAuth(model.provider))) {
			throw new Error(`No API key for ${model.provider}/${model.id}`);
		}

		const previousModel = this.model;
		const thinkingLevel = this._getThinkingLevelForModelSwitch(model);
		// !mark(1:2)
		this.agent.state.model = model;
		this.sessionManager.appendModelChange(model.provider, model.id);
		if (options.persist) {
			this.settingsManager.setDefaultModelAndProvider(model.provider, model.id);
			this._addPersistedDefaultToNonEmptyScope(model);
		}
// ...
		this.setThinkingLevel(thinkingLevel);

		await this._emitModelSelect(model, previousModel, "set");
	}
```

## !!steps Recording the selection on the branch

Tree navigation can leave the latest `model_change` or
`thinking_level_change` on another branch, so a resume would restore a stale
selection. `_recordSelection` runs at the start of every run and appends the
live model and thinking level to the current branch when the branch implies
something else.

The thinking-level check compares after clamping to the current model. A
level that was clamped on resume, such as `xhigh` running as `high`, therefore
does not overwrite the level the user asked for.

```ts ! agent-session.ts
	private _recordSelection(): void {
		const branch = this.sessionManager.getBranch();
		this._recordModelSelection(branch);
		this._recordThinkingLevel(branch);
	}
// ...
	private _recordThinkingLevel(branch: SessionEntry[]): void {
		const recorded = branch.findLast((entry) => entry.type === "thinking_level_change");
		if (!recorded) return;
		const recordedLevel = recorded.thinkingLevel as ThinkingLevel;
		const availableLevels = this.getAvailableThinkingLevels();
		// !mark(1:3)
		const effective = availableLevels.includes(recordedLevel)
			? recordedLevel
			: this._clampThinkingLevel(recordedLevel, availableLevels);
		if (effective === this.thinkingLevel) return;
		this.sessionManager.appendThinkingLevelChange(this.thinkingLevel);
	}
```

## !!steps Reloading extensions and settings in place

`reload` first refuses while a run or compaction is in progress. Invalidating
the runner under a running extension tool would make its next context access
throw a stale-context error, and that failed tool result would be saved in the
session. The guard does not cover a prompt still in preflight.

It then emits `session_shutdown` with reason `reload` on the old runner,
invalidates it, reloads settings and the resource loader, and builds a new
runtime. Flag values are carried over. Tools newly added to `defaultTools`
are activated, with the `--tools` modifiers applied to both the old and new
setting so a tool removed on the command line stays removed. The tools that
were active become pending names, so tools registered later by the new
extensions (MCP servers still connecting) are activated when they appear.

The `session_start` event with reason `reload` is emitted only when a host has
bound UI, commands, a shutdown handler or an error listener; a headless
session skips it.

```ts ! agent-session.ts
	async reload(options?: { beforeSessionStart?: () => void | Promise<void> }): Promise<void> {
		// !mark(1:6)
		if (this.isStreaming) {
			throw new Error("Wait for the current response to finish before reloading.");
		}
		if (this.isCompacting) {
			throw new Error("Wait for compaction to finish before reloading.");
		}

		const oldRunner = this._extensionRunner;
		const previousFlagValues = oldRunner.getFlagValues();
		await emitSessionShutdownEvent(oldRunner, { type: "session_shutdown", reason: "reload" });
		oldRunner.invalidate();
// ...
		// Tools the new extensions register later, such as MCP tools, are pending until then.
		// !mark
		for (const name of this.getActiveToolNames()) this._pendingToolNames.add(name);
		this._buildRuntime({
			activeToolNames: [...this.getActiveToolNames(), ...addedDefaultTools],
			flagValues: previousFlagValues,
			includeAllExtensionTools: true,
		});
```

## !!steps Navigating the session tree

`navigateTree` moves the leaf within the same file (unlike fork, which makes
a new file). It refuses while streaming, while a prompt is in preflight, and
while compacting or another navigation is summarizing. It treats navigation to
the current leaf as a no-op and collects the entries on the abandoned branch
for an optional summary. Extensions can cancel, supply the summary, or
override instructions and label through `session_before_tree`.

The summary request uses the session's thinking level. When the stream
function was created by [sdk.ts](/docs/src/core/sdk.ts), which marks it with
`markRuntimeStreamFunction`, no credentials are resolved up front: that stream
resolves auth itself, and a pre-resolved OAuth token would be taken as an
explicit API key. The same applies to compaction summaries.

Where the leaf lands depends on the target: for a user or custom message the
leaf is its parent and the text goes back to the editor, so the user can edit
and resubmit; any other entry becomes the leaf itself. A summary, if made, is
attached at the new leaf, then the transcript is refreshed and the tool
loadout is restored from it. The branch-summary controller is released before
`session_tree` is emitted, so handlers may prompt or navigate again; the
`finally` block clears it only if no such nested navigation has taken it over.

```ts ! agent-session.ts
			if (targetEntry.type === "message" && targetEntry.message.role === "user") {
				// User message: leaf = parent (null if root), text goes to editor
				newLeafId = targetEntry.parentId;
				editorText = contentText(targetEntry.message.content, "");
			} else if (targetEntry.type === "custom_message") {
				// Custom message: leaf = parent (null if root), text goes to editor
				newLeafId = targetEntry.parentId;
				editorText = contentText(targetEntry.content, "");
			} else {
				// Non-user message: leaf = selected node
				newLeafId = targetId;
			}
// ...
			// Update finalized context from the canonical session projection.
			this._refreshFinalizedContext();
			// !mark
			this._restoreToolsFromTranscript();

			// The selected context is installed; session_tree handlers may now prompt or navigate again.
			this._branchSummaryAbortController = undefined;
```

## !!steps Disposing safely

`dispose` is built to always succeed. It aborts retry, compaction, branch
summary, bash and the agent inside a try block whose errors are swallowed,
then invalidates the extension runner with a long message explaining that old
contexts are stale after session replacement, drops listeners, cancels the
cache warmer and cleans up provider session resources.

`abort` is the graceful variant: it sets the abort flag only if a run is
active, aborts everything, and waits for idle.

```ts ! agent-session.ts
	dispose(): void {
		try {
			this.abortRetry();
			this.abortCompaction();
			this.abortBranchSummary();
			this.abortBash();
			this.agent.abort();
		} catch {
			// Dispose must succeed even if an abort hook throws.
		}
// ...
		this._disconnectFromAgent();
		this._eventListeners = [];
		if (this._cacheWarmer) {
			this._cacheWarmer.onWarmed = undefined;
			this._cacheWarmer.cancel();
		}
		cleanupSessionResources(this.sessionId);
	}
```

The pieces connect through three channels. Agent hooks (`prepareRequest`,
`transformContext`, `finishTurn`, tool hooks) shape what the model sees;
`_handleAgentEvent` persists and relays what it does; and the post-run loop
decides whether to run again. The compaction mechanics themselves live in
[compaction.ts](/docs/src/core/compaction/compaction.ts) and
[branch-summarization.ts](/docs/src/core/compaction/branch-summarization.ts),
and nested tool calls are run by
[nested-tool-calls.ts](/docs/src/core/nested-tool-calls.ts).

Consumers are the three modes under [modes/index.ts](/docs/src/modes/index.ts),
the SDK and extension contexts. Structurally the file is one class with a
large private surface: public methods are thin and the numbered concerns above
are held together by a handful of boolean and controller fields rather than a
state machine.
