Users customize providers and models in `models.json`: custom endpoints, per-model costs, compatibility flags, thinking-level maps and so on. This file defines the schema for that file and loads it into a `ModelConfig`, a frozen snapshot that other code reads.

The header says the snapshot is credential-blind: it holds the configuration but does not resolve API keys, which happens elsewhere, for example in [model-runtime.ts](/docs/src/core/model-runtime.ts) and [resolve-config-value.ts](/docs/src/core/resolve-config-value.ts). Provider assembly lives in [provider-composer.ts](/docs/src/core/provider-composer.ts).

The schema is also a published artifact. [generate-schemas.ts](/docs/scripts/generate-schemas.ts) writes it out as `schemas/models.schema.json` for editors, and [generate-references.ts](/docs/scripts/generate-references.ts) renders the field tables of the models.json reference from it, which is why most fields carry a `description`. Pieces that describe pi-ai's own data, such as costs, OpenRouter routing preferences and compat flags, are not defined here; they come from pi-ai through [pi-ai-schemas.ts](/docs/src/core/pi-ai-schemas.ts).

## !!steps Schemas pi-ai owns come from pi-ai

Model costs, input limits, input modalities, prompt-cache lifetimes, thinking-level maps and the compat flags all describe types that pi-ai defines. Keeping one copy in pi-ai means `models.json` accepts exactly what pi-ai's models can express.

pi-ai now builds these schemas with pi-schema, so they arrive through [pi-ai-schemas.ts](/docs/src/core/pi-ai-schemas.ts), which re-types them for TypeBox. The rest of this file is still TypeBox. `ProviderCompatSchema` is not a union of per-API shapes: pi-ai merges the compat properties of every API into one open object, so unknown compat keys pass validation too.

```ts ! model-config.ts
import { type Static, Type } from "typebox";
import { Compile } from "typebox/compile";
import type { TLocalizedValidationError } from "typebox/error";
// ...
// !mark(1:9)
import {
	ModelCostSchema,
	ModelInputLimitsSchema,
	ModelInputModalitySchema,
	ModelPromptCacheSchema,
	PartialModelCostSchema,
	ProviderCompatSchema,
	ThinkingLevelMapSchema,
} from "./pi-ai-schemas.ts";
```

## !!steps Sampling parameters and headers

Sampling parameters are coding-agent territory: an open record of extra request-body fields, which only OpenAI-compatible APIs send, plus a per-thinking-level variant merged on top. Headers are a string record whose values resolve like `apiKey` (literal, `$NAME` or `!command`), handled at request time by [resolve-config-value.ts](/docs/src/core/resolve-config-value.ts).

These are named constants because both model definitions and overrides reuse them.

```ts ! model-config.ts
const SamplingParamsSchema = Type.Record(Type.String(), Type.Unknown());
const SamplingParamsByThinkingLevelSchema = Type.Object(
	{
		off: Type.Optional(SamplingParamsSchema),
		minimal: Type.Optional(SamplingParamsSchema),
// ...
		max: Type.Optional(SamplingParamsSchema),
	},
	{ description: "samplingParams per thinking level, merged over samplingParams." },
);

// !mark(1:3)
const SamplingParamsFieldSchema = Type.Record(Type.String(), Type.Unknown(), {
	description: "Fields merged into every request body. Applies only to OpenAI-compatible APIs.",
});
const HeadersSchema = Type.Record(Type.String(), Type.String(), {
	description: "Request headers. Values resolve like apiKey.",
});
```

## !!steps Model definitions versus overrides

`ModelDefinitionSchema` requires an `id` and describes a custom model. `ModelOverrideSchema` has no id, no `api` and no `baseUrl`, because it patches a built-in model, and its cost uses `PartialModelCostSchema` so a single rate can be changed.

The two share descriptions through `ModelFieldDescriptions` but differ in defaults. Only definitions declare them (`reasoning` false, `input` text only, a 128000-token context window, 16384 output tokens), because an override that leaves a field out keeps the built-in value. The defaults are documentation: TypeBox's `Check` does not fill them in. [provider-composer.ts](/docs/src/core/provider-composer.ts) applies the same numbers when it builds a model from a definition.

```ts ! model-config.ts
/** Model fields shared by models entries and modelOverrides entries. Defaults apply only to models entries. */
const ModelFieldDescriptions = {
	name: "Display name, also matched by --model patterns.",
	reasoning: "Whether the model supports thinking.",
	contextWindow: "Context window in tokens.",
	maxTokens: "Maximum output tokens.",
} as const;

const ModelDefinitionSchema = Type.Object({
	// !mark
	id: Type.String({ minLength: 1, description: "Model ID sent to the API." }),
	name: Type.Optional(Type.String({ minLength: 1, description: ModelFieldDescriptions.name })),
	api: Type.Optional(Type.String({ minLength: 1, description: "Overrides the provider api." })),
	baseUrl: Type.Optional(Type.String({ minLength: 1, description: "Overrides the provider baseUrl." })),
	reasoning: Type.Optional(Type.Boolean({ default: false, description: ModelFieldDescriptions.reasoning })),
// ...
	contextWindow: Type.Optional(
		// !mark
		Type.Number({ exclusiveMinimum: 0, default: 128000, description: ModelFieldDescriptions.contextWindow }),
	),
// ...
});

const ModelOverrideSchema = Type.Object({
	name: Type.Optional(Type.String({ minLength: 1, description: ModelFieldDescriptions.name })),
	reasoning: Type.Optional(Type.Boolean({ description: ModelFieldDescriptions.reasoning })),
// ...
	// !mark
	cost: Type.Optional(PartialModelCostSchema),
	promptCache: Type.Optional(ModelPromptCacheSchema),
	contextWindow: Type.Optional(
		Type.Number({ exclusiveMinimum: 0, description: ModelFieldDescriptions.contextWindow }),
	),
```

## !!steps The provider schema

A provider can set a base URL, an API key reference, an API type, headers, compat flags, a custom model list, and `modelOverrides` keyed by model id. A `baseUrl` here also applies to the provider's built-in models, which is how users point a built-in provider at a proxy.

The only `oauth` value allowed is the literal `radius`, used for the Radius login flow ([radius.ts](/docs/src/core/radius.ts)); it needs a `baseUrl`. `authHeader` asks for the resolved key to be sent as a bearer token.

```ts ! model-config.ts
const ProviderConfigSchema = Type.Object({
	name: Type.Optional(Type.String({ minLength: 1, description: "Display name." })),
	baseUrl: Type.Optional(
		// !mark
		Type.String({ minLength: 1, description: "API base URL. Also applies to the provider's built-in models." }),
	),
	apiKey: Type.Optional(
		Type.String({
			minLength: 1,
			description: 'Literal key, "$NAME" environment interpolation, or "!command" output.',
		}),
	),
// ...
	// !mark
	oauth: Type.Optional(Type.Literal("radius", { description: "OAuth login flow. Requires baseUrl." })),
	headers: Type.Optional(HeadersSchema),
	compat: Type.Optional(ProviderCompatSchema),
	authHeader: Type.Optional(
		Type.Boolean({ default: false, description: "Whether to send the resolved API key as Authorization: Bearer." }),
	),
	// !mark(1:2)
	models: Type.Optional(Type.Array(ModelDefinitionSchema)),
	modelOverrides: Type.Optional(Type.Record(Type.String(), ModelOverrideSchema)),
});
```

## !!steps The file schema and its exports

The file is a record of providers by id. It also accepts an optional `$schema` string, so a `models.json` can point at the published schema for editor completion without failing validation.

Two things are exported for the generator scripts: `ModelsConfigSchema`, the whole file, and `ModelsJsonSchemas`, the three entry schemas the reference renders as separate tables. The schema is compiled once at module load into a validator, and the exported types come from `Static`.

```ts ! model-config.ts
const ModelsConfigProperties = {
	providers: Type.Record(Type.String(), ProviderConfigSchema),
};

// !mark(1:4)
export const ModelsConfigSchema = Type.Object({
	$schema: Type.Optional(Type.String()),
	...ModelsConfigProperties,
});

/** Entry schemas rendered into docs/models-configuration.md. */
export const ModelsJsonSchemas = {
	provider: ProviderConfigSchema,
	model: ModelDefinitionSchema,
	modelOverride: ModelOverrideSchema,
};

// !mark
const validateModelsConfig = Compile(ModelsConfigSchema);

export type ModelsJsonModel = Static<typeof ModelDefinitionSchema>;
export type ModelsJsonModelOverride = Static<typeof ModelOverrideSchema>;
export type ModelsJsonProvider = Static<typeof ProviderConfigSchema>;
```

## !!steps Readable validation paths and freezing

TypeBox errors give JSON pointers. `formatValidationPath` turns them into dotted paths, and for `required` errors it appends the missing property name, so the message points at what is absent. An empty path becomes `root`.

`deepFreeze` freezes recursively and skips values that are already frozen.

```ts ! model-config.ts
function formatValidationPath(error: TLocalizedValidationError): string {
	// !mark(1:7)
	if (error.keyword === "required") {
		const requiredProperties = (error.params as { requiredProperties?: string[] }).requiredProperties;
		const requiredProperty = requiredProperties?.[0];
		if (requiredProperty) {
			const basePath = error.instancePath.replace(/^\//, "").replace(/\//g, ".");
			return basePath ? `${basePath}.${requiredProperty}` : requiredProperty;
		}
	}
	// !mark(1:2)
	const path = error.instancePath.replace(/^\//, "").replace(/\//g, ".");
	return path || "root";
}

function deepFreeze<T>(value: T): T {
	// !mark(1:3)
	if (typeof value !== "object" || value === null || Object.isFrozen(value)) return value;
	for (const child of Object.values(value)) deepFreeze(child);
	return Object.freeze(value);
}
```

## !!steps Loading never throws

`ModelConfig.load` has four outcomes besides success. No path or a missing file gives an empty config with no error. Any other read error, a parse failure or a schema failure gives an empty config with a message that includes the file path. Comments and a BOM are stripped before parsing, so `models.json` may contain comments.

The schema failure message lists every violation on its own line. A successful `Check` is also a type guard, so after it `parsed` is typed as the file schema and its `providers` can be read without a cast.

```ts ! model-config.ts
	static async load(modelsJsonPath: string | undefined): Promise<ModelConfig> {
		// !mark(1:2)
		if (!modelsJsonPath) return new ModelConfig(new Map());
		const path = normalizePath(modelsJsonPath);
		let content: string;
		try {
			content = await readFile(path, "utf-8");
		// !mark(1:3)
		} catch (error) {
			if ((error as NodeJS.ErrnoException).code === "ENOENT") return new ModelConfig(new Map());
			return new ModelConfig(
				new Map(),
				`Failed to load models.json: ${error instanceof Error ? error.message : error}\n\nFile: ${path}`,
			);
		}

		let parsed: unknown;
		try {
			// !mark
			parsed = JSON.parse(stripJsonComments(stripBom(content)));
		} catch (error) {
			return new ModelConfig(
				new Map(),
				`Failed to parse models.json: ${error instanceof Error ? error.message : error}\n\nFile: ${path}`,
			);
		}

		// !mark(1:7)
		if (!validateModelsConfig.Check(parsed)) {
			const errors =
				validateModelsConfig
					.Errors(parsed)
					.map((error) => `  - ${formatValidationPath(error)}: ${error.message}`)
					.join("\n") || "Unknown schema error";
			return new ModelConfig(new Map(), `Invalid models.json schema:\n${errors}\n\nFile: ${path}`);
		}

		const providers = new Map<string, ModelsJsonProvider>();
		for (const [providerId, provider] of Object.entries(parsed.providers)) {
			providers.set(providerId, deepFreeze(structuredClone(provider)));
		}
		return new ModelConfig(providers);
	}
```

## !!steps Frozen providers and accessors

On success, each provider is cloned with `structuredClone` and deep-frozen, so nothing can mutate the snapshot or share structure with the parsed JSON. The private constructor forces all creation through `load`.

Accessors expose a provider by id, all provider ids, and the error string. Callers must check `getError()` themselves, because a failed load looks like an empty config.

```ts ! model-config.ts
export class ModelConfig {
	private readonly providers: ReadonlyMap<string, ModelsJsonProvider>;
	private readonly error: string | undefined;

	// !mark
	private constructor(providers: ReadonlyMap<string, ModelsJsonProvider>, error?: string) {
		this.providers = providers;
		this.error = error;
	}

// ...
		const providers = new Map<string, ModelsJsonProvider>();
		for (const [providerId, provider] of Object.entries(parsed.providers)) {
			// !mark
			providers.set(providerId, deepFreeze(structuredClone(provider)));
		}
		return new ModelConfig(providers);
	}

	getProvider(providerId: string): ModelsJsonProvider | undefined {
		return this.providers.get(providerId);
	}

	getProviderIds(): readonly string[] {
		return [...this.providers.keys()];
	}

	// !mark(1:3)
	getError(): string | undefined {
		return this.error;
	}
}
```

</Scrollycoding>

A failed load being an empty config, rather than an exception, lets [model-runtime.ts](/docs/src/core/model-runtime.ts) carry on with built-in models and surface the message through its own `getError()`. The schemas here, together with the pi-ai pieces they embed, are the only definition of the file format: the published JSON Schema and the reference tables are generated from them, so adding a field to models.json means editing this file (or pi-ai's schema) and regenerating. Related catalog caching is handled by [models-store.ts](/docs/src/core/models-store.ts).
