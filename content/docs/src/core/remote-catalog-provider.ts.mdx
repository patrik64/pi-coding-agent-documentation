Built-in providers ship with a static model list generated at build time, which goes stale as providers add models. `withRemoteCatalog` decorates a provider so that newer models can be fetched from the pi.dev catalog, stored, and merged over the baseline without a release.

The refresh protocol is careful about three things: offline operation (restore what was stored), network politeness (at most once per interval, with conditional requests), and never letting a bad response wipe a good cache. [model-runtime.ts](/docs/src/core/model-runtime.ts) applies the wrapper to every built-in provider except Radius, and the persisted entries live in [models-store.ts](/docs/src/core/models-store.ts).

OpenRouter gets a second wrapper, `withPersonalizedCatalog`. An OpenRouter key may only be allowed a subset of the catalog, at its own limits and prices, so on each refresh the combined catalog is handed to a personalization function (pi-ai's `personalizeOpenRouterCatalog`, which asks OpenRouter which models the key may use) and the result replaces the provider's model list outright.

## !!steps Constants and supported model types

A request has a four second timeout per attempt, and the overlay is considered fresh for four hours. The client advertises the model types it understands (chat, image, classifier) through a `types` query parameter, so the server can return a richer shard. Models of unknown types are filtered out, and models with no type are treated as chat.

```ts ! remote-catalog-provider.ts
const DEFAULT_CATALOG_BASE_URL = "https://pi.dev";
// !mark(1:2)
const REMOTE_CATALOG_ATTEMPT_TIMEOUT_MS = 4_000;
export const REMOTE_CATALOG_REFRESH_INTERVAL_MS = 4 * 60 * 60 * 1000;
/**
 * Model types this client can consume. Sent as `?types=` so the catalog server
 * returns the full-type shard instead of the chat-only one served to clients
 * that predate model types. A server that ignores the parameter still returns
 * the chat-only shard, which this client handles unchanged.
 */
// !mark
export const REMOTE_CATALOG_MODEL_TYPES: readonly ModelType[] = ["chat", "image", "classifier"];

function isSupportedModelType(model: { type?: unknown }): boolean {
	return (
		model.type === undefined ||
		(typeof model.type === "string" && REMOTE_CATALOG_MODEL_TYPES.includes(model.type as ModelType))
	);
}
```

## !!steps Merging baseline and dynamic models

Models are keyed by type and id, separated by a NUL character. Dynamic entries are placed after the baseline, so on collision the remote definition wins, while models only in the baseline are kept.

```ts ! remote-catalog-provider.ts
function mergeModels<TModel extends AnyModel>(baseline: readonly TModel[], dynamic: readonly TModel[]): TModel[] {
	const merged = new Map<string, TModel>();
// !mark
	for (const model of [...baseline, ...dynamic]) merged.set(`${getModelType(model)}\0${model.id}`, model);
	return [...merged.values()];
}
```

## !!steps Tolerant catalog parsing

The server response can be an array, an object with a `models` array, or a map of id to model. All three are accepted. Entries must be objects with an id and a supported type, and the provider field is overwritten with the local provider id, so a catalog cannot attribute models to another provider.

```ts ! remote-catalog-provider.ts
function parseCatalog(providerId: string, value: unknown): AnyModel[] {
// !mark(1:8)
	const entries = Array.isArray(value)
		? value
		: typeof value === "object" && value !== null && "models" in value && Array.isArray(value.models)
			? value.models
			: typeof value === "object" && value !== null
				? Object.values(value)
				: undefined;
	if (!entries) throw new Error(`Invalid model catalog for provider "${providerId}"`);
// !mark(1:4)
	return entries
		.filter((entry): entry is Record<string, unknown> => typeof entry === "object" && entry !== null && "id" in entry)
		.filter(isSupportedModelType)
		.map((model) => ({ ...model, provider: providerId }) as AnyModel);
}
```

## !!steps Ignoring a catalog older than the build

`localGeneratedAt` is when the built-in list was generated. `isNewer` accepts a catalog only if its last-modified time is later than that, or if the build time is unknown. A stored overlay that fails the test is discarded, since the baseline already includes it, which prevents an old cache from shadowing a newer release. An entry with no `lastModified` at all never passes when a build time is known.

`readCatalog` turns a successful response into the parsed models plus the server's Last-Modified (zero when missing or unparsable) and ETag. Both wrappers use it.

```ts ! remote-catalog-provider.ts
/** Read a successful pi.dev catalog response. A missing or invalid Last-Modified header is 0. */
async function readCatalog(
	providerId: string,
	response: Response,
): Promise<{ models: AnyModel[]; lastModified: number; etag: string | undefined }> {
	const lastModified = Date.parse(response.headers.get("last-modified") ?? "");
	return {
		models: parseCatalog(providerId, await response.json()),
		// !mark
		lastModified: Number.isNaN(lastModified) ? 0 : lastModified,
		etag: response.headers.get("etag") ?? undefined,
	};
}

/** Whether a pi.dev catalog is newer than the model data shipped with pi. */
function isNewer(lastModified: number | undefined, localGeneratedAt: number | undefined): boolean {
	// !mark
	return localGeneratedAt === undefined || (lastModified !== undefined && lastModified > localGeneratedAt);
}

function remoteModels(entry: ModelsStoreEntry | undefined, localGeneratedAt: number | undefined): readonly AnyModel[] {
	return entry && isNewer(entry.lastModified, localGeneratedAt) ? entry.models : [];
}
```

## !!steps One request shape

`requestCatalog` builds the catalog URL with the provider id encoded and the supported types in the query, and fetches it with `fetchWithRetry` from [management-http.ts](/docs/src/utils/management-http.ts) and a user agent from [pi-user-agent.ts](/docs/src/utils/pi-user-agent.ts). An optional validator becomes `if-none-match` for a conditional request.

```ts ! remote-catalog-provider.ts
function requestCatalog(
	providerId: string,
	catalogBaseUrl: string,
	signal: AbortSignal,
	validator?: string,
): Promise<Response> {
	const url = new URL(`/api/models/providers/${encodeURIComponent(providerId)}`, catalogBaseUrl);
	// !mark
	url.searchParams.set("types", REMOTE_CATALOG_MODEL_TYPES.join(","));
	return fetchWithRetry(
		url,
		{
			headers: {
				accept: "application/json",
				"User-Agent": getPiUserAgent(VERSION),
				// !mark
				...(validator ? { "if-none-match": validator } : {}),
			},
			signal,
		},
		{ attemptTimeoutMs: REMOTE_CATALOG_ATTEMPT_TIMEOUT_MS },
	);
}
```

## !!steps The decorated provider

The returned provider spreads the original and overrides the getters. `getModels` returns only chat models, merged. `getAllModels` includes every type. Both read the closure variable `dynamicModels`, which is empty until refresh publishes something.

```ts ! remote-catalog-provider.ts
/** Add a persisted pi.dev catalog overlay to a static built-in provider. */
export function withRemoteCatalog(
	provider: Provider,
	catalogBaseUrl: string = DEFAULT_CATALOG_BASE_URL,
	localGeneratedAt?: number,
): Provider {
	let dynamicModels: readonly AnyModel[] = [];

	return {
		...provider,
// !mark(1:6)
		getModels: () =>
			mergeModels(
				provider.getModels(),
				dynamicModels.filter((model) => isModelType(model, "chat")),
			),
// !mark
		getAllModels: () => mergeModels(provider.getAllModels?.() ?? provider.getModels(), dynamicModels),
```

## !!steps Restoring first, then deciding whether to fetch

Refresh begins by publishing the stored overlay through `context.publish`, which applies the update only if the context is still current; a false return aborts. After that, the network is skipped if it is disallowed, aborted, or the stored entry was checked within the interval, unless a refresh is forced.

The interval only applies to entries that have a `lastModified`. One without it, saved by an older pi or after a failed first request, is ignored by `remoteModels`, so waiting out the interval would leave the overlay empty for hours; it is refetched instead.

```ts ! remote-catalog-provider.ts
		refreshModels: async (context) => {
			const stored = context.stored;
// !mark(1:2)
			const restored = remoteModels(stored, localGeneratedAt).filter((model) => model.provider === provider.id);
// !mark(1:7)
			if (
				!(await context.publish({
					update: () => {
						dynamicModels = restored;
					},
				}))
			) {
				return;
			}
// !mark
			if (!context.allowNetwork || context.signal.aborted) return;
			// Skip the request if pi.dev was checked less than REMOTE_CATALOG_REFRESH_INTERVAL_MS ago.
			// An entry without lastModified (saved by an older pi, or after a failed first request) is
			// always refetched: remoteModels() ignores it, so waiting would leave the overlay empty.
// !mark(1:6)
			if (
				!context.force &&
				stored?.checkedAt !== undefined &&
				stored.lastModified !== undefined &&
				Date.now() - stored.checkedAt < REMOTE_CATALOG_REFRESH_INTERVAL_MS
			) {
				return;
			}
```

## !!steps A conditional request

The ETag is sent as a validator only when a cached body backs it, so a 304 can never leave the overlay empty.

```ts ! remote-catalog-provider.ts
			// Only revalidate when a cached body backs the validator, so a 304 can never
			// leave the overlay empty.
// !mark
			const validator = stored && stored.models.length > 0 ? stored.etag : undefined;
			const response = await requestCatalog(provider.id, catalogBaseUrl, context.signal, validator);
```

## !!steps Handling each outcome

A 304 only advances `checkedAt`. A 404 or 501 means the server has no catalog for this provider: the entry is persisted with `lastModified` of zero and no etag, which makes it older than any build, so the overlay is empty whenever a build time is known, and the next attempt waits for the interval. Other failures keep the cached body and etag, record the check time, then throw so the caller sees the error.

```ts ! remote-catalog-provider.ts
			if (context.signal.aborted) return;
			const checkedAt = Date.now();
			// Unchanged: dynamicModels already holds the stored overlay, so only the
			// freshness window moves.
// !mark(1:4)
			if (response.status === 304 && stored) {
				await context.publish({ persist: { ...stored, checkedAt } });
				return;
			}
// !mark(1:9)
			if (response.status === 404 || response.status === 501) {
				await context.publish({
					persist: {
						...(stored ?? { models: [] }),
						checkedAt,
						lastModified: 0,
						etag: undefined,
					},
				});
				return;
			}
// !mark(1:5)
			if (!response.ok) {
				// Transient failure: the cached body and its validator stay valid, so keep the
				// etag and let the next refresh revalidate instead of downloading the catalog.
				await context.publish({ persist: { ...(stored ?? { models: [] }), checkedAt } });
				throw new Error(`Model catalog request failed for ${provider.id}: ${response.status}`);
			}
```

## !!steps Publishing a fresh catalog

A successful response goes through `readCatalog`, gets its check time, and is filtered through the generation-time rule. The entry is then persisted and swapped into the live list in a single `publish` call, so the stored and in-memory states cannot diverge.

```ts ! remote-catalog-provider.ts
// !mark
			const catalog = await readCatalog(provider.id, response);
			if (context.signal.aborted) return;
			const entry: ModelsStoreEntry = { ...catalog, checkedAt };
// !mark
			const published = remoteModels(entry, localGeneratedAt);
			await context.publish({
				persist: entry,
				update: () => {
					dynamicModels = published;
				},
			});
		},
	};
}
```

## !!steps A personalized catalog replaces the list

`PersonalizeCatalog` receives the catalog and the refresh context, which carries the provider's credential and configured base URL, and returns the models this user should see.

`withPersonalizedCatalog` keeps the personalized list in `personalModels`. Unlike the overlay, it is not merged with the built-in models: when it is non-empty it is the provider's whole list, so models the key may not use disappear. An empty list, meaning nothing saved yet or an empty catalog saved by an older pi, falls back to the built-in models.

```ts ! remote-catalog-provider.ts
/** Replaces the catalog with a credential-specific model list. */
export type PersonalizeCatalog = (
	catalog: readonly AnyModel[],
	context: RefreshModelsContext,
) => Promise<readonly AnyModel[]>;
// ...
export function withPersonalizedCatalog(
	provider: Provider,
	personalize: PersonalizeCatalog,
	catalogBaseUrl: string = DEFAULT_CATALOG_BASE_URL,
	localGeneratedAt?: number,
): Provider {
	let personalModels: readonly AnyModel[] = [];
	const builtinModels = (): readonly AnyModel[] => provider.getAllModels?.() ?? provider.getModels();
	// !mark
	const getAllModels = (): readonly AnyModel[] => (personalModels.length > 0 ? personalModels : builtinModels());

	return {
		...provider,
		getModels: () => getAllModels().filter((model) => isModelType(model, "chat")),
		getAllModels,
```

## !!steps Refreshing a personalized catalog

The saved personalized list is restored first, so the narrowed list also applies offline. With network allowed, every refresh fetches pi.dev without a validator and without the interval check, because the result depends on the credential as well as the catalog. A 404 or 501 just means no pi.dev catalog, other failures throw, and a catalog only counts if it is newer than the build.

The built-in models merged with that catalog go through `personalize`, and the result is persisted and published together. The saved entry holds only models and a check time: it is the personalized list, not the pi.dev catalog, so there is nothing to revalidate.

```ts ! remote-catalog-provider.ts
		refreshModels: async (context) => {
			// !mark
			const restored = (context.stored?.models ?? []).filter((model) => model.provider === provider.id);
// ...
			if (!context.allowNetwork || context.signal.aborted) return;

			const response = await requestCatalog(provider.id, catalogBaseUrl, context.signal);
			if (context.signal.aborted) return;
			let remote: readonly AnyModel[] = [];
			if (response.status !== 404 && response.status !== 501) {
				if (!response.ok) throw new Error(`Model catalog request failed for ${provider.id}: ${response.status}`);
				const catalog = await readCatalog(provider.id, response);
				if (isNewer(catalog.lastModified, localGeneratedAt)) remote = catalog.models;
			}
			// !mark
			const personalized = await personalize(mergeModels(builtinModels(), remote), context);
			if (context.signal.aborted) return;
			await context.publish({
				// !mark
				persist: { models: personalized, checkedAt: Date.now() },
				update: () => {
					personalModels = personalized;
				},
			});
		},
	};
}
```

</Scrollycoding>

Neither wrapper changes authentication or streaming. They only override the model lists and `refreshModels`, which is why they compose cleanly with [provider-composer.ts](/docs/src/core/provider-composer.ts), which layers user configuration on top. What a personalization actually does with the credential is pi-ai's business; for OpenRouter it keeps only the chat models the key may use, takes their context size, output limit and prices from OpenRouter's answer, keeps image and classifier models, and returns the catalog unchanged when there is no key or the key is rejected.
