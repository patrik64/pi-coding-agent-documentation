A system prompt for a coding agent is assembled from many sources: the base persona, the tool list, rules contributed by tools, project instruction files, skills, and the working directory. This file builds it, but not as one string. It builds an ordered record of named sections, each wrapped in an XML-style tag, so that a later change (a tool added, a context file edited) can be expressed as a patch to one section.

The same file also handles the opposite extreme: a `forceSystemPrompt` from an extension replaces everything with one opaque string. The result is consumed by [agent-session.ts](/docs/src/core/agent-session.ts), which writes it into the transcript through [session-manager.ts](/docs/src/core/session-manager.ts).

## !!steps What the builder accepts

`BuildSystemPromptOptions` lists every input. `customPrompt` replaces only the opening persona and also suppresses the tools, rules and docs sections. `forceSystemPrompt` replaces the entire prompt. `selectedTools` defaults to read, bash, edit and write, `hiddenTools` are selected tools whose declarations are withheld from requests (reachable only through another tool), and `sections` lets callers add their own tagged sections.

The remaining fields supply tool snippets and guidelines, appended text, project context files, skills and the working directory.

```ts ! system-prompt.ts
export interface BuildSystemPromptOptions {
	/** Custom system prompt (replaces the default prefix). */
// !mark
	customPrompt?: string;
	/** Exact full prompt replacement set by a before_agent_start handler. */
// !mark
	forceSystemPrompt?: string;
	/** Tools to include in prompt. Default: [read, bash, edit, write]. */
	selectedTools?: string[];
	/**
	 * Selected tools whose declarations requests leave out (`prepareLoadout` hidden declarations).
	 * They are reachable only through another tool, so the tool list and rules leave them out too.
	 */
	hiddenTools?: string[];
	/** Optional one-line tool snippets keyed by tool name. */
	toolSnippets?: Record<string, string>;
	/** Guideline bullets contributed by each tool, keyed by tool name. */
	toolGuidelines?: Record<string, string[]>;
	/** Additional guideline bullets appended to the default system prompt rules. */
	promptGuidelines?: string[];
	/** Text appended from user configuration before project context, skills, and cwd. */
	appendSystemPrompt?: string;
	/** Additional XML-wrapped prompt sections keyed by tag name. */
	sections?: Record<string, string>;
	/** Working directory. */
	cwd: string;
	/** Pre-loaded context files. */
	contextFiles?: Array<{ path: string; content: string }>;
	/** Pre-loaded skills. */
	skills?: Skill[];
}
```

## !!steps Normalizing into a defensive copy

`normalizeBuildSystemPromptOptions` fills every default and copies every array, record and object, so that extension handlers receiving the normalized shape can mutate it without touching the caller's data. The returned type makes the collection fields non-optional.

Section names must match a lowercase identifier pattern, defined just above, because they become tag names.

```ts ! system-prompt.ts
const SYSTEM_PROMPT_SECTION_NAME = /^[a-z][a-z0-9_-]*$/;
/** Normalize prompt input into the mutable, collection-complete shape exposed to extensions. */
export function normalizeBuildSystemPromptOptions(input: BuildSystemPromptOptions): NormalizedBuildSystemPromptOptions {
	return {
		customPrompt: input.customPrompt,
		forceSystemPrompt: input.forceSystemPrompt,
		selectedTools: [...(input.selectedTools ?? ["read", "bash", "edit", "write"])],
		hiddenTools: [...(input.hiddenTools ?? [])],
		toolSnippets: { ...(input.toolSnippets ?? {}) },
		toolGuidelines: Object.fromEntries(
			Object.entries(input.toolGuidelines ?? {}).map(([name, guidelines]) => [name, [...guidelines]]),
		),
		promptGuidelines: [...(input.promptGuidelines ?? [])],
		appendSystemPrompt: input.appendSystemPrompt ?? "",
		sections: { ...(input.sections ?? {}) },
		cwd: input.cwd,
		contextFiles: (input.contextFiles ?? []).map((file) => ({ ...file })),
		skills: (input.skills ?? []).map((skill) => ({ ...skill })),
	};
}
```

## !!steps Rules are deduplicated and ordered

`buildRules` collects bullet points through `addRule`, which trims each rule and skips empty or repeated ones. The order is fixed: a hint to use bash or PowerShell for file operations (only when one of them is present and none of grep, find or ls is), then each selected tool's own guidelines, then the extra prompt guidelines, then two always-on rules about conciseness and file paths.

Because of the dedupe set, two tools that contribute the same sentence yield one bullet.

```ts ! system-prompt.ts
	const rules: string[] = [];
	const seen = new Set<string>();
	const addRule = (rule: string): void => {
		const normalized = rule.trim();
		if (!normalized || seen.has(normalized)) return;
		seen.add(normalized);
		rules.push(normalized);
	};
// ...
	if ((hasBash || hasPowerShell) && !hasGrep && !hasFind && !hasLs) {
		if (hasBash && hasPowerShell) {
			addRule("Use bash or PowerShell for file operations like listing, searching, and finding files");
		} else if (hasPowerShell) {
			addRule("Use PowerShell for file operations like listing, searching, and finding files");
		} else {
			addRule("Use bash for file operations like ls, rg, find");
		}
	}

	for (const name of selectedTools) {
		for (const rule of toolGuidelines[name] ?? []) addRule(rule);
	}
	for (const rule of promptGuidelines) addRule(rule);
	addRule("Be concise in your responses");
	addRule("Show file paths clearly when working with files");
	return rules.map((rule) => `- ${rule}`).join("\n");
}
```

## !!steps Validation, the persona and the default sections

`buildSystemPromptSections` first rejects any custom section whose name is invalid or equals `preamble`, which is reserved. Then it decides between two shapes. With a custom prompt, the preamble is that prompt and nothing else is generated. Otherwise it writes the default persona, a tools section listing only tools that are declared and have a snippet (or `(none)`), a rules section, and a docs section pointing at pi's own documentation.

Hidden tools are removed from `declaredTools` first, so they appear in neither the tool list nor the rule logic.

```ts ! system-prompt.ts
	for (const name of Object.keys(customSections)) {
		if (!SYSTEM_PROMPT_SECTION_NAME.test(name) || name === "preamble") {
			throw new Error(`Invalid system prompt section name: ${name}`);
		}
	}
// ...
	const declaredTools = selectedTools.filter((name) => !hiddenTools.includes(name));
	const promptSections: Record<string, string> = {};
	if (customPrompt) {
		promptSections.preamble = customPrompt;
	} else {
		promptSections.preamble =
			"You are an expert coding assistant operating inside pi, a coding agent harness. You help users by reading files, executing commands, editing code, and writing new files.";
		const visibleTools = declaredTools.filter((name) => !!toolSnippets[name]);
		const tools =
			visibleTools.length > 0 ? visibleTools.map((name) => `- ${name}: ${toolSnippets[name]}`).join("\n") : "(none)";
		promptSections.tools = `${tools}\n\nIn addition to the tools above, you may have access to other custom tools depending on the project.`;
		promptSections.rules = buildRules(declaredTools, toolGuidelines, promptGuidelines);
```

## !!steps Optional sections, skills and the working directory

Next come the optional parts: the appended text becomes `addendum`, and any context files become `project_context`. Skills are included only if there is a way for the model to read their files. The code looks for `read` and then `bash` among declared tools; if neither is declared but one is selected (hidden), it passes `indirect` so the skills text names no tool. See [skills.ts](/docs/src/core/skills.ts) for `formatSkillsForPrompt`.

The working directory has backslashes turned into forward slashes, and caller-supplied sections are added last, skipping empty ones.

```ts ! system-prompt.ts
	if (appendSystemPrompt) promptSections.addendum = appendSystemPrompt;
	if (contextFiles.length > 0) promptSections.project_context = renderProjectContext(contextFiles);
	// A hidden reader is still reachable through another tool, so skills stay but the hint names no tool.
	const readers = ["read", "bash"] as const;
	const skillFileReadTool =
		readers.find((tool) => declaredTools.includes(tool)) ??
		(readers.some((tool) => selectedTools.includes(tool)) ? "indirect" : undefined);
	if (skillFileReadTool && skills.length > 0) {
		const skillsPrompt = formatSkillsForPrompt(skills, skillFileReadTool).trim();
		if (skillsPrompt) promptSections.skills = skillsPrompt;
	}
	promptSections.cwd = cwd.replace(/\\/g, "/");
	for (const [name, content] of Object.entries(customSections)) {
		if (content) promptSections[name] = content;
	}
```

## !!steps Wrapping and the two prompt states

Every section except `preamble` is wrapped in a tag named after itself. The preamble stays bare, so the first lines of the prompt read naturally.

`buildSystemPromptState` returns one of two shapes: forced prompt text in `content` with no sections, or an empty `content` with the structured sections. A forced prompt wins even over a custom prompt, since it is checked first.

```ts ! system-prompt.ts
	const sections: SystemPromptSections = { preamble: promptSections.preamble };
	for (const [name, content] of Object.entries(promptSections)) {
		if (name !== "preamble") sections[name] = `<${name}>\n${content}\n</${name}>`;
	}
	return sections;
}
// ...
export function buildSystemPromptState(input: BuildSystemPromptOptions): {
	content: string;
	sections?: SystemPromptSections;
} {
	if (input.forceSystemPrompt !== undefined) return { content: input.forceSystemPrompt };
	return { content: "", sections: buildSystemPromptSections(input) };
}

/** Build the system prompt text, rendered exactly as the transcript's system message replays it. */
export function buildSystemPrompt(input: BuildSystemPromptOptions): string {
	return getSystemMessageText({ role: "system", ...buildSystemPromptState(input), timestamp: 0 });
}
```

## !!steps Diffing sections between turns

`diffSystemPromptSections` compares what the model currently has, replayed from the transcript, with the freshly built sections. Changed or new sections go in the patch with their new text, and sections that disappeared are set to `null`. When nothing changed it returns `undefined`, so no new system message needs to be written.

This is what keeps prompt-cache prefixes stable: an unchanged prompt costs no transcript entry, and a changed tool list only touches one tagged block.

```ts ! system-prompt.ts
export function diffSystemPromptSections(
	previous: Record<string, string | null>,
	current: SystemPromptSections,
): Record<string, string | null> | undefined {
	const patch: Record<string, string | null> = {};
	for (const [name, text] of Object.entries(current)) {
		if (previous[name] !== text) patch[name] = text;
	}
	for (const name of Object.keys(previous)) {
		if (current[name] === undefined) patch[name] = null;
	}
	return Object.keys(patch).length > 0 ? patch : undefined;
}
```

</Scrollycoding>

The pieces connect as a pipeline: options are normalized, sections are built and wrapped, then either rendered whole by `buildSystemPrompt` or diffed against the transcript. Inputs come from [resource-loader.ts](/docs/src/core/resource-loader.ts) (context files and skills) and from the tool definitions under [tools](/docs/src/core/tools/index.ts). The file is a flat set of functions with no state.
