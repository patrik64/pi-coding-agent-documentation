This file holds the pure logic of the edit tool. Given LF-normalized file content and a list of `oldText`/`newText` pairs, it finds each `oldText`, checks that the edits are unambiguous and disjoint, and returns the new content together with the list of replacements it applied. [edit.ts](/docs/src/core/tools/edit.ts) uses that list twice: to diff only the regions around the changes, and to splice the changes into the original text so that untouched lines keep their exact bytes, line endings included. The TUI preview in [edit.ts](/docs/src/core/tools/renderers/edit.ts) uses `computeEditsDiff` to show a diff before the tool runs.

The central design choice is tolerance with safety. Models routinely reproduce text with smart quotes, odd dashes or trailing spaces. When an exact match fails, the code retries in a normalized space, but it still demands exactly one match and then rewrites only the lines it touched, so the rest of the file is not silently normalized.

## !!steps Matching on LF-only text

Matching always runs on text where CRLF and lone CR have become LF, so a model's `oldText` matches whatever line endings the file uses. The file used to be written back with one line ending detected from its first line break, which converted every line of a mixed file. Now the original text is kept and only the replaced ranges change, which is what the next function does.

```ts ! edit-diff.ts
export function normalizeToLF(text: string): string {
	return text.replace(/\r\n/g, "\n").replace(/\r/g, "\n");
}
```

## !!steps Splicing replacements into the original

`applyReplacementsToOriginal` takes replacements whose offsets refer to the normalized text and applies them to the original. Only CRLF changes length when normalizing, so an original offset is the normalized offset plus the number of CRLFs before it; `toOriginal` counts them with a cursor that only moves forward, since the replacements are sorted. A range that covers a normalized LF therefore covers the whole CRLF. Line breaks in the new text get the line ending of the line where the replacement starts.

`push` handles one corner case. If a kept piece ends with a lone CR and the next piece starts with LF, the two would merge into one CRLF and the file would gain a different line structure from the one the diff shows. Adding an LF at the seam gives the CR a line break of its own, so the written file normalizes to exactly the content that was diffed.

```ts ! edit-diff.ts
export function applyReplacementsToOriginal(originalContent: string, replacements: TextReplacement[]): string {
	// Only CRLF changes length when normalizing: the LF of the n-th CRLF (at original offset p) is at
	// p - n in the normalized text. Adding the number of CRLFs before a normalized offset gives the
	// original offset, and a range that covers that LF covers the whole CRLF.
	let crlfBefore = 0;
	let nextCrlf = originalContent.indexOf("\r\n");
	const toOriginal = (offset: number): number => {
		while (nextCrlf !== -1 && nextCrlf - crlfBefore < offset) {
			crlfBefore++;
			nextCrlf = originalContent.indexOf("\r\n", nextCrlf + 2);
		}
		return offset + crlfBefore;
	};

	const parts: string[] = [];
	let endsWithCr = false;
	const push = (part: string): void => {
		if (part.length === 0) return;
		// A CR before a seam and an LF after it would merge into one CRLF line break, for example a kept
		// lone CR followed by inserted text that starts with LF, or both sides of a deleted range. Adding
		// an LF turns the CR into a CRLF of its own, so the written file has the line breaks the diff shows.
		if (endsWithCr && part[0] === "\n") parts.push("\n");
		parts.push(part);
		endsWithCr = part[part.length - 1] === "\r";
	};
	let position = 0;
	for (const replacement of replacements) {
		const start = toOriginal(replacement.matchIndex);
		push(originalContent.slice(position, start));
		const ending = getLineEndingAt(originalContent, start);
		push(ending === "\n" ? replacement.newText : replacement.newText.replaceAll("\n", ending));
		position = toOriginal(replacement.matchIndex + replacement.matchLength);
	}
	push(originalContent.slice(position));
	return parts.join("");
}
```

## !!steps Choosing a line ending for new lines

The line ending for inserted lines comes from the line that contains the replacement start, or from the line before when that line is the unterminated last one. A lone CR counts as a line ending only in files with no LF at all, the classic Mac format; anywhere else it is more likely a control character inside a line, such as a progress-bar redraw.

```ts ! edit-diff.ts
function getLineEndingAt(content: string, offset: number): "\r\n" | "\n" | "\r" {
	let lineFeed = content.indexOf("\n", offset);
	if (lineFeed === -1) lineFeed = content.lastIndexOf("\n", offset);
	if (lineFeed === -1) return content.includes("\r") ? "\r" : "\n";
	return content[lineFeed - 1] === "\r" ? "\r\n" : "\n";
}
```

## !!steps Fuzzy normalization

The normalizer is applied to both the file content and the model's `oldText`. It uses NFKC, strips trailing whitespace on each line, and maps smart quotes, assorted dashes and unusual space characters to ASCII.

NFKC is the broadest step: it also folds compatibility forms such as full-width letters and ligatures, so the fuzzy space is more permissive than the comments listing four transformations suggest.

```ts ! edit-diff.ts
export function normalizeForFuzzyMatch(text: string): string {
	return (
		text
			.normalize("NFKC")
			// Strip trailing whitespace per line
			.split("\n")
			.map((line) => line.trimEnd())
			.join("\n")
			// Smart single quotes → '
			// !mark
			.replace(/[\u2018\u2019\u201A\u201B]/g, "'")
// ...
			// !mark
			.replace(/[\u2010\u2011\u2012\u2013\u2014\u2015\u2212]/g, "-")
			// !mark(1:2)
			.replace(/[\u00A0\u2002-\u200A\u202F\u205F\u3000]/g, " ")
	);
```

## !!steps Exact first, then fuzzy

`fuzzyFindText` tries `indexOf` on the raw content first. Only if that fails does it normalize both strings and search again. In the fuzzy case the returned index refers to the normalized content, and `contentForReplacement` is that normalized content, so callers must apply the replacement there.

```ts ! edit-diff.ts
	// Try fuzzy match - work entirely in normalized space
	const fuzzyContent = normalizeForFuzzyMatch(content);
	const fuzzyOldText = normalizeForFuzzyMatch(oldText);
	const fuzzyIndex = fuzzyContent.indexOf(fuzzyOldText);

	if (fuzzyIndex === -1) {
		return {
			found: false,
			index: -1,
			matchLength: 0,
			usedFuzzyMatch: false,
			contentForReplacement: content,
		};
	}

	// When fuzzy matching, return offsets in normalized space. Callers can use
	// the normalized content to compute replacements, then decide how much of
	// that normalized output should be written back.
	return {
		found: true,
		index: fuzzyIndex,
		matchLength: fuzzyOldText.length,
		usedFuzzyMatch: true,
		contentForReplacement: fuzzyContent,
	};
}
```

## !!steps Uniqueness and error messages

`countOccurrences` always normalizes both sides before counting, even when the match was exact. A separate family of small functions builds error messages that differ for single-edit and multi-edit calls, naming `edits[i]` only when there are several so the model knows which entry to fix.

```ts ! edit-diff.ts
function countOccurrences(content: string, oldText: string): number {
	const fuzzyContent = normalizeForFuzzyMatch(content);
	const fuzzyOldText = normalizeForFuzzyMatch(oldText);
	return fuzzyContent.split(fuzzyOldText).length - 1;
}

	}
	return new Error(
		`Could not find edits[${editIndex}] in ${path}. The oldText must match exactly including all whitespace and newlines.`,

}
```

## !!steps Matching every edit against the same content

`applyEditsToNormalizedContent` first normalizes line endings in the edits and rejects empty `oldText`. It then does a trial pass to see whether any edit needs fuzzy matching. If one does, the whole call is switched to normalized space, so all edits are located in the same coordinate system.

Each edit is then matched again in the chosen content, must be found, and must occur once. Because all matches are against the original, edits cannot depend on each other.

```ts ! edit-diff.ts
	const normalizedEdits = edits.map((edit) => ({
```

## !!steps Overlap check, replacements and the no-op guard

Matches are sorted by position and neighbours are compared: if one starts before the previous ends, the call fails with a message telling the model to merge them. Disjointness is what makes it safe to apply them in any order.

An exact-only call uses the matched edits as its replacements. A fuzzy call first widens them to whole lines of the LF-normalized content. Either way the result is a sorted list of replacements of `baseContent`, which is returned alongside the new content so callers can diff and splice without searching again. If the result equals the input, the function throws rather than reporting a successful no-op.

```ts ! edit-diff.ts
		matchedEdits.push({
			editIndex: i,
			matchIndex: matchResult.index,
			matchLength: matchResult.matchLength,
			newText: edit.newText,
		});
	}

	matchedEdits.sort((a, b) => a.matchIndex - b.matchIndex);
	for (let i = 1; i < matchedEdits.length; i++) {
		const previous = matchedEdits[i - 1];
		const current = matchedEdits[i];
		if (previous.matchIndex + previous.matchLength > current.matchIndex) {
			throw new Error(
				`edits[${previous.editIndex}] and edits[${current.editIndex}] overlap in ${path}. Merge them into one edit or target disjoint regions.`,
			);
		}
	}

	const baseContent = normalizedContent;
	const replacements = usedFuzzyMatch
		? widenReplacementsToLines(normalizedContent, replacementBaseContent, matchedEdits)
		: matchedEdits;
	const newContent = applyReplacements(baseContent, replacements);

	if (baseContent === newContent) {
		throw getNoChangeError(path, normalizedEdits.length);
	}

	return { baseContent, newContent, replacements };
}
```

## !!steps Applying replacements from the end

Replacements are applied from the last to the first, so the earlier offsets stay valid while the string changes length. The `offset` parameter lets the same function work on a slice of the content, which the widening step uses.

```ts ! edit-diff.ts
function applyReplacements(content: string, replacements: TextReplacement[], offset = 0): string {
	let result = content;
	for (let i = replacements.length - 1; i >= 0; i--) {
		const replacement = replacements[i];
		const matchIndex = replacement.matchIndex - offset;
		result =
			result.substring(0, matchIndex) + replacement.newText + result.substring(matchIndex + replacement.matchLength);
	}
	return result;
}
```

## !!steps Widening a replacement to whole lines

To keep untouched lines byte-identical after a fuzzy match, each replacement is mapped to the lines it touches. `getLineSpans` gives character offsets per line, and `getReplacementLineRange` finds the first line containing the match start and the last line whose end reaches the match end.

```ts ! edit-diff.ts
function getReplacementLineRange(lines: LineSpan[], replacement: TextReplacement) {
	const replacementStart = replacement.matchIndex;
	const replacementEnd = replacement.matchIndex + replacement.matchLength;

	let startLine = -1;
	for (let i = 0; i < lines.length; i++) {
		const line = lines[i];
		if (replacementStart >= line.start && replacementStart < line.end) {
			startLine = i;
			break;
		}
	}
	if (startLine === -1) {
		throw new Error("Replacement range is outside the base content.");
	}

	let endLine = startLine;
	while (endLine < lines.length && lines[endLine].end < replacementEnd) {
		endLine++;
	}
	if (endLine >= lines.length) {
		throw new Error("Replacement range is outside the base content.");
	}

	return { startLine, endLine: endLine + 1 };
}
```

## !!steps Turning fuzzy matches into line replacements

`widenReplacementsToLines` takes the LF-normalized text, the fuzzy-normalized base the matches were found in, and the matched edits. It requires equal line counts, groups edits whose line ranges overlap or touch, and rewrites each group's lines from the fuzzy base. The output is one replacement per group, expressed in offsets of the LF-normalized text, so every line outside a group is left alone. Earlier versions rebuilt the whole file here; returning replacements lets the splice step keep the original line endings outside the touched lines as well.

The comment notes why the replacement ranges, not a line-by-line diff, drive this: duplicate normalized lines could otherwise be aligned to the wrong occurrence.

```ts ! edit-diff.ts
function widenReplacementsToLines(
	originalContent: string,
	baseContent: string,
	replacements: TextReplacement[],
): TextReplacement[] {
	const originalLines = getLineSpans(originalContent);
	const baseLines = getLineSpans(baseContent);
	if (originalLines.length !== baseLines.length) {
		throw new Error("Cannot preserve unchanged lines because the base content has a different line count.");
	}

	const groups: Array<{ startLine: number; endLine: number; replacements: TextReplacement[] }> = [];
	const sortedReplacements = [...replacements].sort((a, b) => a.matchIndex - b.matchIndex);
	for (const replacement of sortedReplacements) {
		const range = getReplacementLineRange(baseLines, replacement);
		const current = groups[groups.length - 1];
		if (current && range.startLine < current.endLine) {
			current.endLine = Math.max(current.endLine, range.endLine);
			current.replacements.push(replacement);
			continue;
		}
		groups.push({ ...range, replacements: [replacement] });
	}

	return groups.map((group) => {
		const groupStartOffset = baseLines[group.startLine].start;
		const groupEndOffset = baseLines[group.endLine - 1].end;
		const originalStart = originalLines[group.startLine].start;
		return {
			matchIndex: originalStart,
			matchLength: originalLines[group.endLine - 1].end - originalStart,
			newText: applyReplacements(
				baseContent.slice(groupStartOffset, groupEndOffset),
				group.replacements,
				groupStartOffset,
			),
		};
	});
}
```

## !!steps Diffing only around the changes

`generateEditDiff` is what the edit tool and the preview call. Because the replacement positions are already known, it diffs only a window around each one: the replaced lines plus 32 unchanged lines on each side, far more than the four shown, so jsdiff aligns a change inside its window the way it would over the whole file. Each window is formatted with file line numbers, and its patch hunks are shifted by the window's first line and written with `formatPatch`. The result has the same format as the whole-file functions; only runs of repeated lines can be aligned differently. Two windows on either side of a long unchanged run would each print a skip marker, so a duplicate is dropped. Lines are pushed in a loop because spreading a very large replacement into `push` would overflow the call stack.

```ts ! edit-diff.ts
const DIFF_WINDOW_MARGIN_LINES = 32;
// ...
export function generateEditDiff(
	path: string,
	baseContent: string,
	newContent: string,
	replacements: TextReplacement[],
	contextLines = 4,
): EditDiff {
	const lineNumWidth = String(Math.max(countLines(baseContent), countLines(newContent))).length;
	const skipMarker = ` ${"".padStart(lineNumWidth, " ")} ...`;
	const output: string[] = [];
	const hunks: Diff.StructuredPatchHunk[] = [];
	let firstChangedLine: number | undefined;
	for (const window of getDiffWindows(baseContent, replacements)) {
		const oldText = baseContent.slice(window.oldStart, window.oldEnd);
		const newText = newContent.slice(window.newStart, window.newEnd);
		const shown = formatDisplayDiff(
			Diff.diffLines(oldText, newText),
			window.oldLine + 1,
			window.newLine + 1,
			lineNumWidth,
			contextLines,
		);
		firstChangedLine ??= shown.firstChangedLine;
		// Both windows around a run of unchanged lines mark it as skipped; the whole-file diff shows one marker.
		if (output.at(-1) === skipMarker && shown.output[0] === skipMarker) shown.output.shift();
		// A loop, not push(...lines): spreading a replacement of many lines overflows the call stack.
		for (const line of shown.output) output.push(line);
		const patch = Diff.structuredPatch(path, path, oldText, newText, undefined, undefined, { context: contextLines });
		for (const hunk of patch.hunks) {
			hunks.push({ ...hunk, oldStart: hunk.oldStart + window.oldLine, newStart: hunk.newStart + window.newLine });
		}
	}
	const patch = Diff.formatPatch(
		{ oldFileName: path, newFileName: path, oldHeader: undefined, newHeader: undefined, hunks },
		Diff.FILE_HEADERS_ONLY,
	);
	return { diff: output.join("\n"), patch, firstChangedLine };
}
```

## !!steps Computing the windows

`getDiffWindows` walks the sorted replacements once. For each it extends backwards to the start of a line and 32 lines further, and forwards past the end of the match's last line and 32 more. The matching window in the new content is found by carrying the running offset and line-count deltas of the earlier replacements. A window that starts before the previous one ends is merged into it. Line numbers are counted with a cursor that only moves forward, so the whole walk is linear in the size of the file and no line array is ever built.

```ts ! edit-diff.ts
function getDiffWindows(baseContent: string, replacements: TextReplacement[]): DiffWindow[] {
	const windows: DiffWindow[] = [];
	// Offset and line deltas of the replacements before the current one, and a line-counting cursor.
	let offsetDelta = 0;
	let lineDelta = 0;
	let cursorOffset = 0;
	let cursorLine = 0;
	for (const replacement of replacements) {
		const matchEnd = replacement.matchIndex + replacement.matchLength;
		let start = lineStartBefore(baseContent, replacement.matchIndex);
		for (let i = 0; i < DIFF_WINDOW_MARGIN_LINES && start > 0; i++) {
			start = lineStartBefore(baseContent, start - 1);
		}
		let end = matchEnd;
		for (let i = 0; i <= DIFF_WINDOW_MARGIN_LINES && end < baseContent.length; i++) {
			const lineFeed = baseContent.indexOf("\n", i === 0 ? Math.max(matchEnd - 1, replacement.matchIndex) : end);
			end = lineFeed === -1 ? baseContent.length : lineFeed + 1;
		}
		const replacementOffsetDelta = replacement.newText.length - replacement.matchLength;
		const replacementLineDelta =
			countLineFeeds(replacement.newText, 0, replacement.newText.length) -
			countLineFeeds(baseContent, replacement.matchIndex, matchEnd);
		const previous = windows.at(-1);
		if (previous && start <= previous.oldEnd) {
			previous.oldEnd = Math.max(previous.oldEnd, end);
			previous.newEnd = previous.oldEnd + offsetDelta + replacementOffsetDelta;
		} else {
			cursorLine += countLineFeeds(baseContent, cursorOffset, start);
			cursorOffset = start;
			windows.push({
				oldStart: start,
				oldEnd: end,
				oldLine: cursorLine,
				newStart: start + offsetDelta,
				newEnd: end + offsetDelta + replacementOffsetDelta,
				newLine: cursorLine + lineDelta,
			});
		}
		offsetDelta += replacementOffsetDelta;
		lineDelta += replacementLineDelta;
	}
	return windows;
}
```

## !!steps Previewing without writing

`computeEditsDiff` mirrors the real tool: check read access, read, strip the BOM, normalize, apply, then diff with the same windowed `generateEditDiff`. It returns either a diff or an `error` string and never throws, which suits UI preview. It checks only `R_OK`, while the real edit also requires write access.

```ts ! edit-diff.ts
export async function computeEditsDiff(
	path: string,
	edits: Edit[],
	cwd: string,
): Promise<EditDiffResult | EditDiffError> {
	const absolutePath = resolveToCwd(path, cwd);

	try {
		// Check if file exists and is readable
		try {
			await access(absolutePath, constants.R_OK);
		} catch (error: unknown) {
			const errorMessage = error instanceof Error && "code" in error ? `Error code: ${error.code}` : String(error);
			return { error: `Could not edit file: ${path}. ${errorMessage}.` };
		}

		// Read the file
		const rawContent = await readFile(absolutePath, "utf-8");

		// Strip BOM before matching (LLM won't include invisible BOM in oldText)
		const { text: content } = splitBom(rawContent);
		const normalizedContent = normalizeToLF(content);
		const { baseContent, newContent, replacements } = applyEditsToNormalizedContent(normalizedContent, edits, path);

		// Generate the diff
		const { diff, firstChangedLine } = generateEditDiff(path, baseContent, newContent, replacements);
		return { diff, firstChangedLine };
	} catch (err) {
		return { error: err instanceof Error ? err.message : String(err) };
	}
}
```

Callers are the edit tool and its renderer; the paths come from [path-utils.ts](/docs/src/core/tools/path-utils.ts) and BOM handling from [text.ts](/docs/src/utils/text.ts). `computeEditDiff`, the single-edit wrapper at the end of the file, is kept for convenience.

Because uniqueness is always checked in normalized space, an exact, unique `oldText` can still be rejected as duplicated when a second location differs from it only by trailing whitespace, quote style or similar. The error text says to add context, which does fix it. Matching also still builds a few file-sized strings (the LF-normalized text and the fuzzy normalization used for counting), so a very large file can run out of memory there, but that happens before anything is written.
