`grep` searches file contents. It always uses ripgrep (`rg`), located or
downloaded by [tools-manager.ts](/docs/src/utils/tools-manager.ts), and reads
ripgrep's `--json` event stream line by line. Both match lines and context
lines come from that stream, so the tool never opens a matched file itself and
its memory does not grow with the size of the files it searches. Output lines
are formatted as events arrive and joined after ripgrep exits.

Only one filesystem operation is pluggable: checking whether the path is a
directory. The search itself is always local ripgrep, unlike
[find.ts](/docs/src/core/tools/find.ts), which can swap the whole backend; to
search a remote system an extension overrides `execute()`. Truncation constants
come from [truncate.ts](/docs/src/core/tools/truncate.ts), and rendering is in
[renderers/grep.ts](/docs/src/core/tools/renderers/grep.ts).

## !!steps The schema

Seven parameters, all but `pattern` optional. `literal` switches to fixed-string
matching, `ignoreCase` is explicit, and `context` asks for surrounding lines.
The `glob` description spells out that the pattern is relative to `path`, and
that a pattern with no slash matches file names at any depth. The default limit
is 100 matches, lower than the default of 1000 in `find`.

```ts ! grep.ts
const grepSchema = Type.Object({
	pattern: Type.String({ description: "Search pattern (regex or literal string)" }),
	path: Type.Optional(Type.String({ description: "Directory or file to search (default: current directory)" })),
	glob: Type.Optional(
		Type.String({
			description:
				"Filter files by glob pattern, relative to path, e.g. '*.ts', 'src/**/*.ts' or '**/*.spec.ts'. A pattern without '/' matches file names at any depth",
		}),
	),
	ignoreCase: Type.Optional(Type.Boolean({ description: "Case-insensitive search (default: false)" })),
	literal: Type.Optional(
		Type.Boolean({ description: "Treat pattern as literal string instead of regex (default: false)" }),
	),
	context: Type.Optional(
		Type.Number({ description: "Number of lines to show before and after each match (default: 0)" }),
	),
	limit: Type.Optional(Type.Number({ description: "Maximum number of matches to return (default: 100)" })),
});
```

## !!steps Pluggable operations and decoding

`GrepOperations` used to include `readFile` for context lines. Now that context
comes from ripgrep, only `isDirectory` remains, and the comment says plainly
that this hook does not make grep work remotely. ripgrep's JSON carries paths
and line text as `text` when they are valid UTF-8 and as base64 in `bytes`
otherwise; `decodeRgText` accepts both, so non-UTF-8 file names and lines are
still shown.

```ts ! grep.ts
/**
 * Pluggable operations for the grep tool.
 * The search itself always runs the local ripgrep; to search a remote system, override the tool's execute().
 */
export interface GrepOperations {
	/** Check if path is a directory. Throws if path does not exist. */
	isDirectory: (absolutePath: string) => Promise<boolean> | boolean;
}

const defaultGrepOperations: GrepOperations = {
	isDirectory: async (p) => (await fsStat(p)).isDirectory(),
};

/** Decode a ripgrep JSON text field (path or line). Non-UTF-8 data arrives base64-encoded in `bytes`. */
function decodeRgText(data: { text?: string; bytes?: string } | undefined): string {
	if (typeof data?.text === "string") return data.text;
	if (typeof data?.bytes === "string") return Buffer.from(data.bytes, "base64").toString("utf-8");
	return "";
}
```

## !!steps Setting up the search

The tool first makes sure `rg` exists. It then asks `isDirectory`, and any error
from that call, including a missing path, becomes a `Path not found` error.
`context` is floored and clamped to zero or more, and capped at the largest safe
integer so `String()` never produces exponent notation that ripgrep would
reject. The limit is floored with a minimum of one, so `limit: 0` cannot turn
the search into an immediate no-op.

```ts ! grep.ts
						const rgPath = await ensureTool("rg");
						if (!rgPath) {
							settle(() => reject(new Error("ripgrep (rg) is not available and could not be downloaded")));
							return;
						}

						const searchPath = resolveToCwd(searchDir || ".", ctx?.cwd || cwd);
						const ops = customOps ?? defaultGrepOperations;
						let isDirectory: boolean;
						try {
							isDirectory = await ops.isDirectory(searchPath);
						} catch {
							settle(() => reject(new Error(`Path not found: ${searchPath}`)));
							return;
						}

						// Clamp so String() never yields exponent notation, which rg rejects.
						const contextValue =
							context && context > 0 ? Math.min(Math.floor(context), Number.MAX_SAFE_INTEGER) : 0;
						const effectiveLimit = Math.max(1, Math.floor(limit ?? DEFAULT_LIMIT));
```

## !!steps The ripgrep command

`--no-config` keeps the tool's behavior independent of a user's
`RIPGREP_CONFIG_PATH`. `--json` gives structured events, and `--hidden` includes
dotfiles while ripgrep's ignore rules still apply. A leading `./` is stripped
from the glob because ripgrep never matches it. `--context` makes ripgrep emit
the surrounding lines as `context` events. The pattern follows `--`, so a
pattern beginning with a dash is not parsed as a flag.

ripgrep always anchors `--glob` at its own working directory, so a directory
search starts ripgrep inside `searchPath` and searches `.`. Without that, a glob
such as `migrations/main/*.js` was matched against pi's start folder and found
nothing. Searching `.` rather than the absolute path also keeps globs working
when `searchPath` goes through a symlink. A single-file search keeps the
absolute path, since ripgrep cannot start inside a file.

```ts ! grep.ts
						// --no-config: the tool contract (literal, glob, limit, ...) must not depend on
						// ambient user config like RIPGREP_CONFIG_PATH. Users can customize via bash or extensions.
						const args: string[] = ["--no-config", "--json", "--line-number", "--color=never", "--hidden"];
						if (ignoreCase) args.push("--ignore-case");
						if (literal) args.push("--fixed-strings");
						// rg never matches a leading "./" ("./src/*.ts" finds nothing), so drop it; "!" negates.
						if (glob) args.push("--glob", glob.replace(/^(!?)(?:\.\/)+/, "$1"));
						// rg emits the surrounding lines as `context` events, so no matched file is ever read here (#9276).
						if (contextValue > 0) args.push("--context", String(contextValue));
						// rg roots --glob at its own cwd, so a directory search runs inside searchPath (#11807).
						// It searches "." because rg canonicalizes its cwd: with an absolute path, a symlinked
						// searchPath (macOS /tmp) would no longer lie under the glob root.
						args.push("--", pattern, isDirectory ? "." : searchPath);

						const child = spawn(rgPath, args, {
							cwd: isDirectory ? searchPath : undefined,
							stdio: ["ignore", "pipe", "pipe"],
						});
```

## !!steps Display paths

For a directory search ripgrep reports paths like `./src/a.ts`. `formatPath`
resolves them against `searchPath` and prints them relative to it with forward
slashes, the same form a glob uses. When the search target is a single file,
or a path somehow falls outside the directory, only the basename is shown.

```ts ! grep.ts
						const formatPath = (filePath: string): string => {
							if (isDirectory) {
								const relative = path.relative(searchPath, path.resolve(searchPath, filePath));
								if (relative && !relative.startsWith("..")) {
									return relative.replace(/\\/g, "/");
								}
							}
							return path.basename(filePath);
						};
```

## !!steps Formatting and counting output lines

`pushLine` formats one event. Match lines are `path:line: text` and context
lines `path-line- text`, the classic grep convention. Only the line terminator
is stripped, so a lone CR inside a line stays content, as in the read tool, and
text copied from grep output still matches in `edit`. Each line goes through
`truncateLine`. Lines past the 50KB output cap are counted but not stored,
because the final byte truncation would drop them anyway; the running totals
are what the truncation notice reports.

```ts ! grep.ts
						// Size of the full output, including lines past the byte cap that are counted but not stored.
						let outputBytes = 0;
						let outputLineCount = 0;
						let lastFile: string | undefined;
						// Set at the last allowed match. rg still sends that match's trailing context, kept up to
						// trailingContextEnd, and the limit notice waits for proof of one more match.
						let limitHit = false;
						let trailingContextEnd = 0;
						let done = false;
						const finish = () => {
							done = true;
							stopChild(true);
						};
						const pushLine = (filePath: string, lineNumber: number, lineText: string, isMatch: boolean) => {
							lastFile = filePath;
							const relativePath = formatPath(filePath);
							// Strip only the line terminator: a lone CR inside a line is content, as in the read tool.
							const sanitized = lineText.replace(/\r?\n?$/, "");
							// Truncate long lines so grep output stays compact.
							const { text: truncatedText, wasTruncated } = truncateLine(sanitized);
							if (wasTruncated) linesTruncated = true;
							const line = isMatch
								? `${relativePath}:${lineNumber}: ${truncatedText}`
								: `${relativePath}-${lineNumber}- ${truncatedText}`;
							// Byte truncation below drops everything past the cap, so keep counting but stop storing (#9276).
							// outputBytes counts a newline after every line; the joined output has one fewer.
							if (outputBytes - 1 <= DEFAULT_MAX_BYTES) outputLines.push(line);
							outputBytes += Buffer.byteLength(line, "utf-8") + 1;
							outputLineCount++;
						};
```

## !!steps Stopping at the limit

Only `match` and `context` events matter. Before the limit, every line is
pushed and matches are counted. At the last allowed match the tool records how
far that match's trailing context reaches, because ripgrep sends that context
after the match. Lines in that window are still shown, and a further match
inside it is shown as context. The limit notice is set only when ripgrep sends
one more match, so exactly N matches with `limit: N` no longer claims results
were cut. Once that proof has arrived and the window is complete, `finish`
kills ripgrep and flags the kill as intentional. The cost is that a search with
exactly N matches runs to the end instead of stopping at the Nth. ripgrep
merges overlapping context, so lines shared by nearby matches are printed once.

```ts ! grep.ts
						rl.on("line", (line) => {
							if (done || !line.trim()) return;
							let event: any;
							try {
								event = JSON.parse(line);
							} catch {
								return;
							}
							const isMatch = event.type === "match";
							if (!isMatch && event.type !== "context") return;
							const filePath = decodeRgText(event.data?.path);
							const lineNumber = event.data?.line_number;
							if (!filePath || typeof lineNumber !== "number") return;
							const lineText = decodeRgText(event.data?.lines);
							if (!limitHit) {
								pushLine(filePath, lineNumber, lineText, isMatch);
								if (!isMatch) return;
								matchCount++;
								if (matchCount >= effectiveLimit) {
									limitHit = true;
									trailingContextEnd = lineNumber + contextValue;
								}
								return;
							}
							const inWindow = filePath === lastFile && lineNumber <= trailingContextEnd;
							// A match inside the last match's trailing context is shown as context.
							if (inWindow) pushLine(filePath, lineNumber, lineText, false);
							// Only another match proves that the limit cut results off.
							if (isMatch) matchLimitReached = true;
							if (matchLimitReached && !(inWindow && lineNumber < trailingContextEnd)) finish();
						});
```

## !!steps Exit codes

A spawn failure rejects with `Failed to run ripgrep`. Ripgrep exits 0 with
matches and 1 with none, and both are normal. Any other code is an error, unless
the tool killed the process itself. Zero matches returns the text
`No matches found`.

```ts ! grep.ts
						child.on("error", (error) => {
							cleanup();
							settle(() => reject(new Error(`Failed to run ripgrep: ${error.message}`)));
						});
						child.on("close", (code) => {
							cleanup();
							if (aborted) {
								settle(() => reject(new Error("Operation aborted")));
								return;
							}
							if (!killedDueToLimit && code !== 0 && code !== 1) {
								const errorMsg = stderr.trim() || `ripgrep exited with code ${code}`;
								settle(() => reject(new Error(errorMsg)));
								return;
							}
							if (matchCount === 0) {
								settle(() =>
									resolve({ content: [{ type: "text", text: "No matches found" }], details: undefined }),
								);
								return;
							}
```

## !!steps Byte truncation and three kinds of notice

The stored lines go through byte truncation with no line limit, since the match
cap bounds rows. Because lines past the cap were never stored, the totals in the
truncation result are overwritten with the counted ones. Up to three notices
can be combined: match limit reached, output bytes truncated, and some lines
shortened, the last pointing the model to the read tool for full lines.
`details` carries the same facts for renderers.

```ts ! grep.ts
							const rawOutput = outputLines.join("\n");
							// Apply byte truncation. There is no line limit here because the match limit already capped rows.
							const truncation = truncateHead(rawOutput, { maxLines: Number.MAX_SAFE_INTEGER });
							truncation.totalLines = outputLineCount;
							truncation.totalBytes = outputBytes - 1;
							let output = truncation.content;
							const details: GrepToolDetails = {};
							// Build actionable notices for truncation and match limits.
							const notices: string[] = [];
							if (matchLimitReached) {
								notices.push(
									`${effectiveLimit} matches limit reached. Use limit=${effectiveLimit * 2} for more, or refine pattern`,
								);
								details.matchLimitReached = effectiveLimit;
							}
							if (truncation.truncated) {
								notices.push(`${formatSize(DEFAULT_MAX_BYTES)} limit reached`);
								details.truncation = truncation;
							}
							if (linesTruncated) {
								notices.push(
									`Some lines truncated to ${GREP_MAX_LINE_LENGTH} chars. Use read tool to see full lines`,
								);
								details.linesTruncated = true;
							}
							if (notices.length > 0) output += `\n\n[${notices.join(". ")}]`;
```

The structure follows [find.ts](/docs/src/core/tools/find.ts) and
[ls.ts](/docs/src/core/tools/ls.ts), with results gathered, truncated and then
described with actionable notices. One difference from `find`: grep registers its
abort listener only after spawning the process, and does not check
`signal.aborted` after the awaited `ensureTool` and `isDirectory` calls, so an
abort that arrives during the tool download is missed and the search runs to
completion.
