This file renders shell tool calls and results. It is split from the execution code in [tools/bash.ts](/docs/src/core/tools/bash.ts) so a process that only displays tool output does not have to load the execution path or its parameter schema. The header comment says the execution file spreads these renderers into its tool definition, so the public shape of the tool is unchanged.

One factory serves both shells. `createShellRenderers(prompt)` takes the prompt string (`$` or `PS>`) and returns `renderCall` and `renderResult`. [renderers/index.ts](/docs/src/core/tools/renderers/index.ts) calls it for bash and powershell, and [powershell.ts](/docs/src/core/tools/powershell.ts) shares the same display behavior through that factory.

## !!steps Constants

Collapsed output shows the last five visual lines. `BASH_UPDATE_THROTTLE_MS` is exported so the execution side can throttle streaming updates to the same 100 ms cadence. The duration formatting and the elapsed-time logic that used to live here moved into [render-utils.ts](/docs/src/core/tools/render-utils.ts) as `startToolTimer` and `toolTimerText`, so the codemode renderer can show the same timer.

```ts ! bash.ts
import { getTextOutput, invalidArgText, startToolTimer, str, toolTimerText } from "../render-utils.ts";
import { DEFAULT_MAX_BYTES, formatSize } from "../truncate.ts";

const BASH_PREVIEW_LINES = 5;
export const BASH_UPDATE_THROTTLE_MS = 100;
```

## !!steps The call line

The header is the prompt followed by the command, in bold title style, with an optional muted `(timeout Ns)` suffix. The three cases for the command come from `str`: `null` (wrong type) shows `[invalid arg]`, an empty string shows `...` (arguments still streaming), otherwise the command itself.

`str` and `invalidArgText` come from [render-utils.ts](/docs/src/core/tools/render-utils.ts).

```ts ! bash.ts
function formatShellCall(args: { command?: string; timeout?: number } | undefined, prompt: string): string {
	const command = str(args?.command);
	const timeout = args?.timeout as number | undefined;
	const timeoutSuffix = timeout ? theme.fg("muted", ` (timeout ${timeout}s)`) : "";
	// !mark
	const commandDisplay = command === null ? invalidArgText(theme) : command ? command : theme.fg("toolOutput", "...");
	return theme.fg("toolTitle", theme.bold(`${prompt} ${commandDisplay}`)) + timeoutSuffix;
}
```

## !!steps Stripping the duplicate truncation footer

The execution side appends a footer such as a bracketed note about the full output file to the text it returns to the model. The renderer shows its own warning line, so it removes that footer from the display text. It does this only for a final (not partial) result that is truncated, has a full-output path, and whose text ends with `]`.

The footer is located by the last blank line followed by `[`, and is cut only if it actually mentions the output path. That guard prevents trimming real command output that happens to end in a bracket.

```ts ! bash.ts
	component.clear();

	let output = getTextOutput(result as any, showImages).trim();
	const truncation = result.details?.truncation;
	const fullOutputPath = result.details?.fullOutputPath;
	// !mark(1:6)
	if (!options.isPartial && truncation?.truncated && fullOutputPath && output.endsWith("]")) {
		const footerStart = output.lastIndexOf("\n\n[");
		if (footerStart !== -1 && output.slice(footerStart).includes(fullOutputPath)) {
			output = output.slice(0, footerStart).trimEnd();
		}
	}
```

## !!steps Expanded versus collapsed output

Expanded mode prints every line. Collapsed mode hands the text to `VisualLinePreview` with `keep: "end"`, so the user sees the most recent five visual lines (wrapped lines count as several), which is what matters for a running command. The hint line reports how many earlier lines are hidden and which key expands, using [keybinding-hints.ts](/docs/src/modes/interactive/components/keybinding-hints.ts). The preview component lives in [visual-truncate.ts](/docs/src/modes/interactive/components/visual-truncate.ts).

```ts ! bash.ts
	if (output) {
		const styledOutput = output
			.split("\n")
			.map((line) => theme.fg("toolOutput", line))
			.join("\n");

		if (options.expanded) {
			component.addChild(new Text(`\n${styledOutput}`, 0, 0));
		} else {
			component.addChild(new Spacer(1));
			component.addChild(
				// !mark(1:3)
				new VisualLinePreview({
					text: styledOutput,
					maxVisualLines: BASH_PREVIEW_LINES,
					keep: "end",
					formatHint: (hidden) =>
						theme.fg("muted", `... (${hidden} earlier lines,`) +
						` ${keyHint("app.tools.expand", "to expand")}${theme.fg("muted", ")")}`,
				}),
			);
		}
	}
```

## !!steps Truncation warnings and the timer line

If output was truncated or spilled to a file, a single yellow bracketed line lists the full output path and how the cut happened: by lines (showing N of M) or by bytes (the limit from [truncate.ts](/docs/src/core/tools/truncate.ts), defaulting to `DEFAULT_MAX_BYTES`).

The last line is the timer text computed by the result renderer, such as `Elapsed 3.1s` or `Took 12.0s`, added only when there is one.

```ts ! bash.ts
	if (truncation?.truncated || fullOutputPath) {
		const warnings: string[] = [];
		if (fullOutputPath) {
			warnings.push(`Full output: ${fullOutputPath}`);
		}
		if (truncation?.truncated) {
			// !mark(1:5)
			if (truncation.truncatedBy === "lines") {
				warnings.push(`Truncated: showing ${truncation.outputLines} of ${truncation.totalLines} lines`);
			} else {
				warnings.push(
					`Truncated: ${truncation.outputLines} lines shown (${formatSize(truncation.maxBytes ?? DEFAULT_MAX_BYTES)} limit)`,
				);
			}
		}
		component.addChild(new Text(`\n${theme.fg("warning", `[${warnings.join(". ")}]`)}`, 0, 0));
	}

	if (timerText) component.addChild(new Text(`\n${theme.fg("muted", timerText)}`, 0, 0));
}
```

## !!steps Call and result renderers

`createShellRenderers` returns the two hooks. `renderCall` runs repeatedly as arguments stream in; it starts the row's clock through `startToolTimer` once execution begins, and reuses the previous `Text` component when one exists instead of allocating a new one on each update.

`renderResult` asks `toolTimerText` for the timing line. That helper keeps a one-second redraw interval running while the result is partial, so the elapsed time ticks even when the command prints nothing, and for a final result prefers the duration recorded with the result, which survives a session reload. The component is then rebuilt from scratch and invalidated, which is simpler than diffing and cheap for a handful of children.

```ts ! bash.ts
export function createShellRenderers(prompt: string): Pick<ToolDefinition<any, any>, "renderCall" | "renderResult"> {
	return {
		renderCall(args, _theme, context) {
			startToolTimer(context);
			const text = (context.lastComponent as Text | undefined) ?? new Text("", 0, 0);
			text.setText(formatShellCall(args as { command?: string; timeout?: number } | undefined, prompt));
			return text;
		},
		renderResult(result, options, _theme, context) {
			const timerText = toolTimerText(context, options.isPartial);
			const component = (context.lastComponent as Container | undefined) ?? new Container();
			rebuildBashResultRenderComponent(component, result as any, options, context.showImages, timerText);
			component.invalidate();
			return component;
		},
```

The type for the hooks comes from [extensions/types.ts](/docs/src/core/extensions/types.ts), the same `ToolDefinition` that extension authors implement, so built-in and custom tools render through one interface. Structurally the file is a pure view: no I/O, all state passed through the render context. One quirk: the theme is imported as a singleton here while the sibling renderers receive it as a parameter.
