The edit tool changes an existing file by replacing exact snippets of text. The model supplies a path and a list of `oldText`/`newText` pairs; every `oldText` must occur exactly once in the original file. This file handles the tool plumbing: schema, tolerant argument parsing, file access, encoding details and the result. The matching and diffing algorithms are in [edit-diff.ts](/docs/src/core/tools/edit-diff.ts).

Like [write.ts](/docs/src/core/tools/write.ts), writes are serialized per path through [file-mutation-queue.ts](/docs/src/core/tools/file-mutation-queue.ts), and file access is replaceable through `EditOperations`.

## !!steps Schema and prompt guidance

Each edit is matched against the original file, not against the result of earlier edits, and edits must not overlap. The schema descriptions and the exported prompt guidelines both say this repeatedly, because models otherwise tend to emit chained or overlapping edits.

```ts ! edit.ts
const replaceEditSchema = Type.Object(
	{
		oldText: Type.String({
			description:
				"Exact text for one targeted replacement. It must be unique in the original file and must not overlap with any other edits[].oldText in the same call.",
		}),
		newText: Type.String({ description: "Replacement text for this targeted edit." }),
	},
	{},
);

const editSchema = Type.Object(
	{
		path: Type.String({ description: "Path to the file to edit (relative or absolute)" }),
		edits: Type.Array(replaceEditSchema, {
			description:
				"One or more targeted replacements. Each edit is matched against the original file, not incrementally. Do not include overlapping or nested edits. If two changes touch the same block or nearby lines, merge them into one edit instead.",
		}),
	},
	{},
);
```

These two strings are merged into the system prompt along with the other tools. They ask for one call per file with several `edits[]` entries rather than several calls, and for short, unique, non-overlapping `oldText` without padded context. See [system-prompt.ts](/docs/src/core/system-prompt.ts).

## !!steps Operations: readable and writable

`EditOperations` needs read, write and an `access` check. The local access check requires both `R_OK` and `W_OK`, so a read-only file fails fast, before any content is read.

```ts ! edit.ts
export interface EditOperations {
	/** Read file contents as a Buffer */
	readFile: (absolutePath: string) => Promise<Buffer>;
	/** Write content to a file */
	writeFile: (absolutePath: string, content: string) => Promise<void>;
	/** Check if file is readable and writable (throw if not) */
	access: (absolutePath: string) => Promise<void>;
}

const defaultEditOperations: EditOperations = {
	readFile: (path) => fsReadFile(path),
	writeFile: (path, content) => fsWriteFile(path, content, "utf-8"),
	access: (path) => fsAccess(path, constants.R_OK | constants.W_OK),
};

export interface EditToolOptions {
	/** Custom operations for file editing. Default: local filesystem */
	operations?: EditOperations;
}
```

## !!steps Repairing malformed arguments

`prepareArguments` runs before schema validation and fixes shapes that real models produce. Some send `edits` as a JSON string, some send a single edit object instead of an array, and older prompts used top-level `oldText` and `newText`.

All three are normalized to the canonical `edits` array, with a legacy top-level pair appended as one more entry. A string that fails to parse is left alone, and the schema validation that follows reports the problem. Note that the function mutates the input object for the first two repairs.

```ts ! edit.ts
function prepareEditArguments(input: unknown): EditToolInput {
	if (!input || typeof input !== "object") {
		return input as EditToolInput;
	}

	const args = input as Record<string, unknown>;

	// Some models (Opus 4.6, GLM-5.1) send edits as a JSON string instead of an array.
	// Others send a single edit object instead of a one-element edits array.
	if (typeof args.edits === "string") {
		try {
			const parsed = JSON.parse(args.edits);
			if (Array.isArray(parsed)) {
				args.edits = parsed;
			} else if (isSingleEditInput(parsed)) {
				args.edits = [parsed];
			}
		} catch {}
	} else if (isSingleEditInput(args.edits)) {
		args.edits = [args.edits];
	}

	const legacy = args as LegacyEditToolInput;
	if (typeof legacy.oldText !== "string" || typeof legacy.newText !== "string") {
		return args as EditToolInput;
	}

	const edits = Array.isArray(legacy.edits) ? [...legacy.edits] : [];
	edits.push({ oldText: legacy.oldText, newText: legacy.newText });
	const { oldText: _oldText, newText: _newText, ...rest } = legacy;
	return { ...rest, edits } as EditToolInput;
}
```

## !!steps Locking, abort checks and access

After resolving the path, the whole read-modify-write cycle runs inside the mutation queue. The abort comment is the same as in the write tool: check `signal.aborted` after every await rather than rejecting from a listener, so the queue stays locked until in-flight I/O settles.

The access failure is rewritten into a short message with the error code, such as `ENOENT`, so the model sees why the file could not be edited.

```ts ! edit.ts
		async execute(_toolCallId, input: EditToolInput, signal?: AbortSignal, _onUpdate?, ctx?: ExtensionContext) {
			const { path, edits } = validateEditInput(input);
			const absolutePath = resolveToCwd(path, ctx?.cwd || cwd);

			return withFileMutationQueue(absolutePath, async () => {
				// Do not reject from an abort event listener here: that would release the
				// mutation queue while an in-flight filesystem operation may still finish.
				// Checking signal.aborted after each await observes the same aborts while
				// keeping the queue locked until the current operation has settled.
				const throwIfAborted = (): void => {
					if (signal?.aborted) throw new Error("Operation aborted");
				};

				throwIfAborted();

				// Check if file exists.
				try {
					await ops.access(absolutePath);
				} catch (error: unknown) {
					throwIfAborted();
					const errorMessage =
						error instanceof Error && "code" in error ? `Error code: ${error.code}` : String(error);
					throw new Error(`Could not edit file: ${path}. ${errorMessage}.`);
				}
				throwIfAborted();
```

## !!steps BOM, matching and diffing before the write

The file is read as UTF-8, and a leading BOM is split off with `splitBom` from [text.ts](/docs/src/utils/text.ts), because the model will never include an invisible BOM in `oldText`. The text is normalized to LF and the edits are applied to that normalized text, which also returns the list of replacements made.

The diff is computed next, before anything is written. `generateEditDiff` diffs only a window around each replacement, so a two-line edit of a huge file no longer needs memory proportional to the file, and if diffing does fail the file is still unchanged. Earlier versions wrote first and diffed the whole file afterwards, which could crash after the edit was already on disk.

```ts ! edit.ts
				// Read the file.
				const buffer = await ops.readFile(absolutePath);
				const rawContent = buffer.toString("utf-8");
				throwIfAborted();

				// Strip BOM before matching. The model will not include an invisible BOM in oldText.
				const { bom, text: content } = splitBom(rawContent);
				const normalizedContent = normalizeToLF(content);
				const { baseContent, newContent, replacements } = applyEditsToNormalizedContent(
					normalizedContent,
					edits,
					path,
				);
				// Diff before writing, so diff computation cannot fail after the write.
				const editDiff = generateEditDiff(path, baseContent, newContent, replacements);
				throwIfAborted();
```

## !!steps Writing with the original line endings

When the file contains no CR at all, the normalized result is already the final text. Otherwise the replacements are spliced into the original text with `applyReplacementsToOriginal`, so every untouched line keeps its own line ending and only the new lines take the ending of the line they replace. The tool used to detect one line ending from the first line break and rewrite the whole file with it, which converted the other lines of mixed-ending files. The BOM is put back in front either way.

```ts ! edit.ts
				// Splice into the original text, so untouched lines keep their line endings. Without any CR
				// the original is the normalized text, and the normalized result is already final.
				const finalContent =
					bom + (content === normalizedContent ? newContent : applyReplacementsToOriginal(content, replacements));
				await ops.writeFile(absolutePath, finalContent);
				throwIfAborted();
```

## !!steps The result: message, diff and patch

The `EditDiff` from the earlier step becomes `details` as is: a display diff with line numbers and limited context, a standard unified patch, and `firstChangedLine` so an editor-like UI can jump to the change. The message to the model only reports how many blocks were replaced; it does not echo the diff.

```ts ! edit.ts
				return {
					content: [
						{
							type: "text",
							text: `Successfully replaced ${edits.length} block(s) in ${path}.`,
						},
					],
					details: editDiff,
				};
			});
		},
		...editRenderers,
	};
}
```

</Scrollycoding>

The tool is registered by [index.ts](/docs/src/core/tools/index.ts) and displayed by the edit renderer in [edit.ts](/docs/src/core/tools/renderers/edit.ts), which also uses the diff helpers to preview changes before execution. The model-facing contract is deliberately strict: no match, several matches, overlapping edits and no-op edits are all errors raised in edit-diff.ts.

Structurally, `validateEditInput` only checks that `edits` is a non-empty array; the types of each entry are trusted from the schema. The constant `EditToolDetails` documents `diff` as display-oriented and `patch` as standard, which is the split the renderers rely on.

The final `throwIfAborted()` runs after `writeFile` has succeeded, so an abort that lands during the write reports `Operation aborted` even though the edit is on disk.
