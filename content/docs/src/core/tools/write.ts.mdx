The smallest of the built-in file tools, and a good template for the others. It accepts a path and full contents, makes sure the parent directory exists, and writes the file. Everything interesting is in how it is wrapped: file access goes through a replaceable `WriteOperations` object, writes to the same path are serialized, and aborts are handled so they cannot leave a half-finished operation behind.

The sibling tools [edit.ts](/docs/src/core/tools/edit.ts) and [read.ts](/docs/src/core/tools/read.ts) follow the same shape: a schema, an operations interface with a local default, a `createXToolDefinition` factory and a thin `createXTool` wrapper.

## !!steps Schema and prompt contribution

The input is just `path` and `content`. The exported `writeToolSystemPromptContribution` is the text the system prompt builder uses for this tool: a one-line snippet and a guideline that steers the model toward `edit` for anything short of a new file or a complete rewrite. See [system-prompt.ts](/docs/src/core/system-prompt.ts).

## !!steps Pluggable operations

`WriteOperations` is the seam for remote filesystems. An SSH or container backend supplies its own `writeFile` and `mkdir`, and the tool logic stays the same. The local defaults write UTF-8 and create directories recursively; the trailing `then` discards the first-created-path value that `mkdir` returns, so the signature stays `Promise<void>`.

```ts ! write.ts
/**
 * Pluggable operations for the write tool.
 * Override these to delegate file writing to remote systems (for example SSH).
 */
export interface WriteOperations {
	/** Write content to a file */
	writeFile: (absolutePath: string, content: string) => Promise<void>;
	/** Create directory recursively */
	mkdir: (dir: string) => Promise<void>;
}

const defaultWriteOperations: WriteOperations = {
	writeFile: (path, content) => fsWriteFile(path, content, "utf-8"),
	mkdir: (dir) => fsMkdir(dir, { recursive: true }).then(() => {}),
};

export interface WriteToolOptions {
	/** Custom operations for file writing. Default: local filesystem */
	operations?: WriteOperations;
}
```

## !!steps Serialized writes and abort checks

`withFileMutationQueue` from [file-mutation-queue.ts](/docs/src/core/tools/file-mutation-queue.ts) makes concurrent mutations of the same path run one after another, which matters because the agent can issue parallel tool calls.

The comment explains a deliberate choice. Rejecting from an abort event listener would resolve the caller early and release the queue lock while a filesystem call may still be running. Instead the code checks `signal.aborted` between awaits, so the lock is held until the current operation really finishes. The consequence is that an abort during the final write is reported as an error even though the file has already been written.

```ts ! write.ts
			return withFileMutationQueue(absolutePath, async () => {
				// Do not reject from an abort event listener here: that would release the
				// mutation queue while an in-flight filesystem operation may still finish.
				// Checking signal.aborted after each await observes the same aborts while
				// keeping the queue locked until the current operation has settled.
				const throwIfAborted = (): void => {
					if (signal?.aborted) throw new Error("Operation aborted");
				};

				throwIfAborted();
				// Create parent directories if needed.
				await ops.mkdir(dir);
				throwIfAborted();

				// Write the file contents.
				await ops.writeFile(absolutePath, content);
				throwIfAborted();
```

## !!steps Result and the tool wrapper

The result text echoes the path as the model supplied it. `details` is `undefined`, since there is nothing to render beyond the message. The renderers from [write.ts](/docs/src/core/tools/renderers/write.ts) are spread in last so the TUI can draw the call and result.

`createWriteTool` converts the definition into the plain `AgentTool` form with `wrapToolDefinition` from [tool-definition-wrapper.ts](/docs/src/core/tools/tool-definition-wrapper.ts).
