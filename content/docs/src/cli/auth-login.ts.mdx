`pi auth login <provider>` does from the shell what `/login` does inside a session: it signs in to a model provider with an account, or saves an API key, and exits. That makes first-time setup and CI images possible without starting the TUI. Account sign-in is the default and takes the provider's browser method; `--no-browser` picks another method such as a device code, and `--api-key` saves a key instead.

The provider flows themselves live in pi-ai and run through `login` on [model-runtime.ts](/docs/src/core/model-runtime.ts), which stores the result in `auth.json` via [auth-storage.ts](/docs/src/core/auth-storage.ts). This file adapts their prompts and events to a plain line-based terminal, defined in [auth-terminal.ts](/docs/src/cli/auth-terminal.ts). [main.ts](/docs/src/main.ts) builds the runtime and terminal and calls `runAuthLogin`. The interactive counterpart is [login-dialog.ts](/docs/src/modes/interactive/components/login-dialog.ts), and the sibling command is [auth-logout.ts](/docs/src/cli/auth-logout.ts).

## !!steps Injected dependencies and the parsed request

Everything the command touches comes in through `AuthLoginOptions`: the runtime, the terminal, directories, a device id source and an abort signal. Tests can therefore script a whole login without a real terminal or network.

The request has only three fields. `browser` starts out true and is turned off by `--no-browser`; it controls both which sign-in method is picked and whether a browser is opened.

```ts ! auth-login.ts
/** Dependencies of `runAuthLogin`, injected so tests can script the terminal. */
export interface AuthLoginOptions {
	modelRuntime: ModelRuntime;
	terminal: LoginTerminal;
	agentDir: string;
	cwd: string;
	getDeviceId: () => string;
	/** Aborts the login, e.g. on Ctrl+C. */
	signal: AbortSignal;
}

const AUTH_LOGIN_USAGE = `${APP_NAME} auth login <provider> [--api-key] [--no-browser]`;

/** Parsed `pi auth login` arguments. */
interface LoginRequest {
	providerRef: string;
	/** Log in with an API key instead of an account. */
	apiKey: boolean;
	/** Open the browser and take the browser sign-in method without asking. */
	browser: boolean;
}
```

## !!steps Strict argument parsing

The parser accepts exactly one provider and the two flags. Any other option, or a second positional, prints the usage line. `--no-browser` together with `--api-key` is rejected with a specific message, because choosing a sign-in method means nothing when no account sign-in happens.

```ts ! auth-login.ts
	const usage = { type: "invalid", message: `Usage: ${AUTH_LOGIN_USAGE}` } as const;
	const request: LoginRequest = { providerRef: "", apiKey: false, browser: true };
	for (const arg of args) {
		if (arg === "--api-key") request.apiKey = true;
		else if (arg === "--no-browser") request.browser = false;
		else if (arg.startsWith("-") || request.providerRef) return usage;
		else request.providerRef = arg;
	}
	if (!request.providerRef) return usage;
	if (request.apiKey && !request.browser) {
		return { type: "invalid", message: "--no-browser only applies to account sign-in; omit it with --api-key." };
	}
	return { type: "valid", request };
```

## !!steps Finding the provider

`findMatchingProviders` from [provider-matching.ts](/docs/src/core/provider-matching.ts) matches the reference against provider ids and display names, ignoring case. An unknown name lists the providers that offer some kind of login. The typed reference is echoed through `replaceControlCharacters`, so a pasted escape sequence cannot reach the terminal.

Only then is the terminal checked. Login prompts need a real TTY on both stdin and stdout, so a piped invocation fails with a clear message instead of hanging on a prompt nobody can answer.

```ts ! auth-login.ts
	const provider = findMatchingProviders(modelRuntime.getProviders(), providerRef)[0];
	if (!provider) {
		const loginProviders = modelRuntime
			.getProviders()
			.filter((candidate) => candidate.auth.oauth || candidate.auth.apiKey?.login)
			.map((candidate) => candidate.id)
			.sort();
		terminal.error(`Unknown provider "${replaceControlCharacters(providerRef)}".`);
		terminal.error(`Providers: ${loginProviders.join(", ")}`);
		return 1;
	}
	if (!terminal.interactive) {
		terminal.error(`"${AUTH_LOGIN_USAGE}" requires an interactive terminal`);
		return 1;
	}
```

## !!steps Account or API key

`selectAuthType` picks the kind of login. Account login (`oauth`) is used unless `--api-key` asked otherwise. A provider without account login falls back to its API key login, since that is the only way in.

Two cases have no login at all. `--api-key` on an account-only provider gets a hint to drop the flag. A provider with neither login is configured outside pi, for example through an environment variable, and the message names that method.

```ts ! auth-login.ts
function selectAuthType(
	provider: Provider,
	apiKey: boolean,
): { type: AuthType } | { type: "unavailable"; message: string } {
	const hasApiKeyLogin = provider.auth.apiKey?.login !== undefined;
	if (!apiKey && provider.auth.oauth) return { type: "oauth" };
	if (hasApiKeyLogin) return { type: "api_key" };
	if (apiKey && provider.auth.oauth) {
		return { type: "unavailable", message: `${provider.name} has no API key login. Omit --api-key to sign in.` };
	}
	const method = provider.auth.apiKey?.name ?? "ambient credentials";
	return { type: "unavailable", message: `${provider.name} is configured outside ${APP_NAME} (${method}).` };
}
```

## !!steps Choosing the sign-in method

Providers ask which method to use through a `select` prompt, with the browser sign-in listed first, as in `/login`. The command answers it from the flags instead of asking. By default it takes the first option and remembers the others, so it can mention them later. With `--no-browser` it takes the single other method, asks only when there are several, and falls back to the browser method without opening a browser when that is all the provider has. API key setup asks every selection, numbered, until the user enters a valid number.

```ts ! auth-login.ts
	// Account logins list the browser sign-in first, as /login; API key setup asks every selection.
	const methodChoice = authType === "api_key" ? "ask" : request.browser ? "browser" : "other";
	let skippedMethods: string[] = [];

	async function selectMethod(prompt: Extract<AuthPrompt, { type: "select" }>, promptSignal: AbortSignal) {
		const [first, ...others] = prompt.options;
		if (methodChoice === "ask" || !first) {
			return selectInTerminal(prompt.message, prompt.options, terminal, promptSignal);
		}
		if (methodChoice === "browser") {
			skippedMethods = others.map((option) => option.label);
			return first.id;
		}
		const [onlyOther, ...moreOthers] = others;
		// A provider whose only method is the browser sign-in still gets it, without opening the browser.
		if (!onlyOther) return first.id;
		if (moreOthers.length > 0) return selectInTerminal(prompt.message, others, terminal, promptSignal);
		terminal.write(`${prompt.message} ${onlyOther.label}`);
		return onlyOther.id;
	}
```

## !!steps Prompts and provider events

The returned `AuthInteraction` is what pi-ai drives. A prompt can carry its own signal, because a browser callback may finish a step before the user pastes a code; that cancels only the prompt, while Ctrl+C cancels the whole login. Secret prompts read without echo.

Events become lines. URLs pass through `displayUrl` and `webUrl` from [web-url.ts](/docs/src/utils/web-url.ts), so only `http` and `https` URLs are opened, and an untrusted string cannot end a terminal hyperlink early or inject escape sequences. After an auth URL, the user learns which other methods were skipped and how to rerun with `--no-browser`.

```ts ! auth-login.ts
		prompt(prompt) {
			// The browser callback can finish a step before the pasted code, cancelling just that prompt.
			const promptSignal = prompt.signal ? AbortSignal.any([signal, prompt.signal]) : signal;
			if (prompt.type === "select") return selectMethod(prompt, promptSignal);
			const placeholder = prompt.placeholder ? ` (${prompt.placeholder})` : "";
			const message = `${prompt.message}${placeholder}: `;
			return prompt.type === "secret"
				? terminal.secret(message, promptSignal)
				: terminal.question(message, promptSignal);
		},
		notify(event) {
			if (event.type === "auth_url") {
				terminal.write(`Open this URL to sign in:\n  ${displayUrl(event.url)}`);
				if (event.instructions) terminal.write(event.instructions);
				const target = webUrl(event.url);
				if (target !== undefined && request.browser) terminal.openUrl(target);
				// Providers without a method choice have nothing else to offer, so they get no hint.
				const rerun = `"${APP_NAME} auth login ${providerId} --no-browser"`;
				const [onlyMethod, ...moreMethods] = skippedMethods;
				if (onlyMethod !== undefined && moreMethods.length === 0) {
					terminal.write(`To use "${onlyMethod}" instead, run ${rerun}`);
				} else if (onlyMethod !== undefined) {
					const labels = skippedMethods.map((label) => `"${label}"`).join(", ");
					terminal.write(`Other sign-in methods: ${labels}. Run ${rerun} to choose one.`);
				}
```

## !!steps Running the login

The login itself is one call. Errors are sorted into three messages. A `CredentialSynchronizationError` means the credential was saved but the runtime could not rebuild its model state, so the user is told the login worked. An aborted signal or pi-ai's "Login cancelled" message is a cancellation. Everything else is a failure. All three exit with 1.

```ts ! auth-login.ts
	try {
		await modelRuntime.login(
			provider.id,
			authType.type,
			createLoginInteraction(provider.id, authType.type, request, terminal, signal),
			{ getDeviceId: options.getDeviceId },
		);
	} catch (error: unknown) {
		const message = error instanceof Error ? error.message : String(error);
		if (error instanceof CredentialSynchronizationError) {
			terminal.error(`Logged in to ${provider.name}, but local model state could not be synchronized: ${message}`);
		} else if (signal.aborted || message === "Login cancelled") {
			terminal.error("Login cancelled.");
		} else {
			terminal.error(`Failed to log in to ${provider.name}: ${message}`);
		}
		return 1;
	}
```

## !!steps Refreshing the model catalog

Some providers have dynamic catalogs that stay empty until the first authenticated refresh, so the command fetches the catalog right away instead of leaving the first session without models. The refresh has a 15 second timeout and is also cancelled by Ctrl+C. Since the login is already saved at this point, none of its outcomes fails the command: a timeout, an error or a cancellation only prints a note that pi will retry on the next start.

```ts ! auth-login.ts
	// The login is saved by now, so Ctrl+C only skips the refresh.
	const cancelled = () => {
		terminal.write(`Skipped the ${provider.name} model catalog refresh; ${APP_NAME} refreshes it on next start.`);
	};
	try {
		const result = await modelRuntime.refresh({
			providers: [provider.id],
			signal: AbortSignal.any([signal, AbortSignal.timeout(15_000)]),
		});
		if (signal.aborted) {
			cancelled();
		} else if (result.aborted) {
			terminal.write(
				`The ${provider.name} model catalog refresh timed out; ${APP_NAME} refreshes it on next start.`,
			);
		} else if (result.errors.size > 0) {
			terminal.write(
				`The ${provider.name} model catalog could not be refreshed; ${APP_NAME} retries on next start.`,
			);
		}
```

## !!steps Pointing the Radius MCP server at the login

For the Radius provider (see [radius.ts](/docs/src/core/radius.ts)), the login is also what its MCP server needs. `planRadiusMcpServer` from [radius-mcp.ts](/docs/src/core/radius-mcp.ts) works out the global `mcp.json` entry that uses this login, or returns nothing when one already does. The command writes it without asking, because the user just signed in for exactly this; `/login` asks instead. A write failure is reported but does not change the exit code.

```ts ! auth-login.ts
function configureRadiusMcpServer(provider: Provider, options: AuthLoginOptions): void {
	const { terminal } = options;
	const plan = planRadiusMcpServer(provider.id, options.agentDir, options.cwd);
	if (!plan) return;
	try {
		const replaced = addMcpServerConfig(plan.mcpPath, plan.name, plan.config);
		terminal.write(
			`${replaced ? "Updated" : "Added"} MCP server "${plan.name}" in ${plan.mcpPath} to use the ${provider.name} login.`,
		);
	} catch (error: unknown) {
		terminal.error(`Could not update ${plan.mcpPath}: ${error instanceof Error ? error.message : String(error)}`);
	}
}
```

</Scrollycoding>

The command returns an exit code rather than calling `process.exit`, and every message goes through the injected terminal, which is why the whole flow is testable. The MCP config write uses `addMcpServerConfig` from [config.ts](/docs/src/extensions/mcp/config.ts), the same helper `pi mcp add` and `/login` use.
