The Harness from pi-durable is a library and knows nothing about pi's settings files, proxy configuration or model defaults. This file is the glue that carries those host concerns into it, in four small functions that [runtime.ts](/docs/src/experimental/vacation/runtime.ts) calls while opening a session.

It mirrors [durable/harness-setup.ts](/docs/src/experimental/durable/harness-setup.ts), minus the coding tools and execution environments: the registry here installs only the vacation extensions from [vacation.ts](/docs/src/experimental/vacation/vacation.ts).

<Scrollycoding>

## !!steps HTTP setup

pi configures a proxy and idle timeouts for its HTTP client in one undici dispatcher. The doc comment gives the reason this must be repeated here: without it some provider streams break off. The two settings come from [settings-manager.ts](/docs/src/core/settings-manager.ts), and the dispatcher functions from [http-dispatcher.ts](/docs/src/core/http-dispatcher.ts).

```ts ! harness-setup.ts
import type { ModelThinkingLevel } from "@earendil-works/pi-ai";
import { createRegistry, type HarnessSettings, type ModelRef, type Registry } from "@earendil-works/pi-durable";
import { applyHttpProxySettings, configureHttpDispatcher } from "../../core/http-dispatcher.ts";
import { findInitialModel, resolveCliModel } from "../../core/model-resolver.ts";
import type { ModelRuntime } from "../../core/model-runtime.ts";
import type { SettingsManager } from "../../core/settings-manager.ts";
import { Search, Vacation } from "./vacation.ts";

/** pi's HTTP setup: proxy, idle timeouts, and one undici for fetch. Without it, some provider streams break off. */
// !mark(1:4)
export function configureHarnessHttp(settingsManager: SettingsManager): void {
	applyHttpProxySettings(settingsManager.getGlobalSettings().httpProxy);
	configureHttpDispatcher(settingsManager.getHttpIdleTimeoutMs());
}
```

## !!steps Settings read on every use

`createHarnessSettings` returns an object of getters rather than a snapshot, so each access re-reads the settings manager. The stream settings combine the provider retry settings with the HTTP idle timeout: if the provider sets no timeout, an idle value of zero (meaning disabled) becomes the largest 32-bit timer value, 2147483647, instead of a zero that would fire at once.

```ts ! harness-setup.ts
/** Harness settings read at every use from pi's settings as loaded at startup. */
export function createHarnessSettings(settingsManager: SettingsManager): HarnessSettings {
	return {
		get stream() {
			const provider = settingsManager.getProviderRetrySettings();
			const idle = settingsManager.getHttpIdleTimeoutMs();
			return {
				// !mark
				timeoutMs: provider.timeoutMs ?? (idle === 0 ? 2147483647 : idle),
				maxRetryDelayMs: provider.maxRetryDelayMs,
				...(provider.maxRetries === undefined ? {} : { maxRetries: provider.maxRetries }),
			};
		},
```

## !!steps A registry without coding tools

The registry installs two extensions: `Vacation`, the planner, and `Search`, used by the research subagent. There is no bash, read or edit, and no pi system prompt. The main conversation is configured with only `Vacation` (see [runtime.ts](/docs/src/experimental/vacation/runtime.ts)); the subagent selects `Search` itself.

```ts ! harness-setup.ts
/** A registry with the vacation planner and its research subagent's search. No coding tools, no pi prompt. */
export function createVacationRegistry(): Registry {
	const registry = createRegistry();
	// !mark(1:2)
	registry.install(Vacation);
	registry.install(Search);
	return registry;
}
```

## !!steps Choosing the initial model

`findInitialAgentModel` has two paths. With an explicit CLI provider and model it resolves them through [model-resolver.ts](/docs/src/core/model-resolver.ts) and throws if resolution fails. Without one it asks `findInitialModel` to apply pi's defaults from settings, with no scoped models and not treating the run as a continuation.

The result is converted to the Harness's model reference shape. A fallback message is passed on so the UI can tell the user why a different model was chosen.

```ts ! harness-setup.ts
/** The model a new root conversation starts with: an explicit `--provider`/`--model`, or pi's default resolution. */
export async function findInitialAgentModel(
	settingsManager: SettingsManager,
	modelRuntime: ModelRuntime,
	cli?: { readonly provider?: string; readonly model: string },
): Promise<InitialModel> {
	// !mark
	if (cli !== undefined) {
		const resolved = resolveCliModel({ cliProvider: cli.provider, cliModel: cli.model, modelRuntime });
		if (resolved.error !== undefined || resolved.model === undefined) {
			throw new Error(`Could not resolve model: ${resolved.error ?? cli.model}`);
		}
		return {
			model: { provider: resolved.model.provider, modelId: resolved.model.id },
			...(resolved.thinkingLevel === undefined ? {} : { thinkingLevel: resolved.thinkingLevel }),
		};
	}
	// !mark(1:8)
	const initial = await findInitialModel({
		scopedModels: [],
		isContinuing: false,
		defaultProvider: settingsManager.getDefaultProvider(),
		defaultModelId: settingsManager.getDefaultModel(),
		defaultThinkingLevel: settingsManager.getDefaultThinkingLevel(),
		modelRuntime,
	});
	return {
		...(initial.model === undefined
			? {}
			: {
					model: { provider: initial.model.provider, modelId: initial.model.id },
					thinkingLevel: initial.thinkingLevel,
				}),
		...(initial.fallbackMessage === undefined ? {} : { fallbackMessage: initial.fallbackMessage }),
	};
```

The vacation runtime never passes the `cli` argument, so the first branch is unused here.
