The coding agent's documentation includes a field-by-field reference for `models.json`, `docs/models-configuration.md`. That page is generated. The descriptions and defaults live in the schemas that validate `models.json` at runtime, the provider, model and override schemas in [model-config.ts](/docs/src/core/model-config.ts) plus pi-ai's input limit and compatibility schemas, and this script renders them as Markdown tables. A field documented in its schema therefore shows up in the reference, and the reference cannot describe a field the code does not accept.

It runs through `npm run generate:references`. `test/references.test.ts` fails when the committed page differs from what `renderReferences` produces; the test calls itself a regression test for an issue in which `models.json` fields lost their reference documentation. [generate-schemas.ts](/docs/scripts/generate-schemas.ts) is the sibling script that publishes the same schemas as JSON Schema files.

<Scrollycoding>

## !!steps Just enough JSON Schema

The renderer reads only a handful of keywords: `type`, `const`, `enum`, `anyOf`, `items`, `properties`, `required`, `description` and `default`. `ReferenceSchema` names exactly those, and the TypeBox and pi-schema objects are cast to it when rendered.

A page is a title, an intro and a list of sections. A section can have a schema whose properties become table rows. `links` makes a top-level field link to another section instead of expanding its nested fields inline, and `collapsed` lists fields that get one row with no nested rows.

```ts ! generate-references.ts
/** The subset of JSON Schema that reference pages render. */
interface ReferenceSchema {
	type?: string;
	const?: unknown;
	enum?: readonly unknown[];
	anyOf?: readonly ReferenceSchema[];
	items?: ReferenceSchema;
	properties?: Readonly<Record<string, ReferenceSchema>>;
	required?: readonly string[];
	description?: string;
	default?: unknown;
}

interface ReferenceSection {
	heading: string;
	intro?: string;
	/** Object schema whose properties become table rows. */
	schema?: TSchema;
	/** Top-level fields whose type links to another section instead of listing nested fields. */
	links?: Readonly<Record<string, string>>;
	/** Top-level fields listed without their nested fields. */
	collapsed?: readonly string[];
}
```

## !!steps APIs that share a compatibility schema

pi-ai's `CompatSchemasByApi` maps every API to the schema of the `compat` fields it accepts. Several APIs share one schema object, for example the three OpenAI Responses variants. Grouping by object identity gives one section per schema, headed by the first API, with an "Also applies to" line naming the others.

```ts ! generate-references.ts
/** APIs grouped by the compatibility schema they share, in first-seen order. */
const compatSchemaApis = new Map<TSchema, string[]>();
for (const [api, schema] of Object.entries(CompatSchemasByApi)) {
	// !mark
	compatSchemaApis.set(schema, [...(compatSchemaApis.get(schema) ?? []), api]);
}

const formatList = (items: readonly string[]) =>
	items.length > 1 ? `${items.slice(0, -1).join(", ")} and ${items.at(-1)}` : (items[0] ?? "");
```

## !!steps The page definition

There is one artifact, the models reference. Its sections follow the shape of the file: providers, models, model overrides, input limits and compatibility. The intros carry prose that has no home in a schema, such as what a provider ID means and how unknown override IDs are treated.

Links keep the tables flat. The provider table links `models`, `modelOverrides` and `compat` to their own sections instead of nesting their rows. The OpenRouter and Vercel gateway routing objects are collapsed into single rows.

```ts ! generate-references.ts
const referenceArtifacts: readonly ReferenceArtifact[] = [
	{
		path: "docs/models-configuration.md",
		title: "Models Configuration",
// ...
		sections: [
			{
				heading: "Providers",
				intro: "Each key under `providers` is a provider ID. A built-in provider ID changes that provider. Any other ID adds a provider, which needs `baseUrl` and an `api` at provider or model level.",
				schema: ModelsJsonSchemas.provider,
				// !mark
				links: { models: "#models", modelOverrides: "#model-overrides", compat: "#compatibility" },
			},
// ...
			...[...compatSchemaApis].map(([schema, [api, ...aliases]]) => ({
				heading: `### \`${api}\``,
				intro: aliases.length > 0 ? `Also applies to ${formatList(aliases.map((alias) => `\`${alias}\``))}.` : undefined,
				schema,
				// !mark
				collapsed: ["openRouterRouting", "vercelGatewayRouting"],
			})),
		],
	},
];
```

## !!steps A type for each cell

`referenceType` turns a field schema into the short type text shown in the table. A `const` becomes its JSON literal, an `enum` a union of literals, and an `anyOf` the union of its branches with duplicates removed. Arrays get `[]`, with parentheses when the item type is itself a union, so `("a" | "b")[]` reads correctly.

```ts ! generate-references.ts
function referenceType(schema: ReferenceSchema): string {
	if (schema.const !== undefined) return JSON.stringify(schema.const);
	if (schema.enum) return schema.enum.map((value) => JSON.stringify(value)).join(" | ");
	if (schema.anyOf) return [...new Set(schema.anyOf.map(referenceType))].join(" | ");
	if (schema.type === "array") {
		const item = schema.items ? referenceType(schema.items) : "unknown";
		// !mark
		return item.includes(" | ") ? `(${item})[]` : `${item}[]`;
	}
	return schema.type ?? "unknown";
}
```

## !!steps Rows and nesting

Each property becomes a row with its path, type, default and description, and "Required." is put in front of the description when the property is required. Plain one-word types stay as text, while anything more complex is set in code style. Pipes and `<` are escaped so they do not break the Markdown table.

A nested object gets rows of its own, with dotted paths such as `cost.input`, or with a `[]` suffix for arrays of objects. `documentedObject` allows that only when at least one nested field has a description or default, so undocumented internal objects stay a single row.

```ts ! generate-references.ts
function referenceRows(schema: ReferenceSchema, section: ReferenceSection, prefix = ""): string[] {
	const rows: string[] = [];
	for (const [name, field] of Object.entries(schema.properties ?? {})) {
		const path = `${prefix}${name}`;
		const link = prefix === "" ? section.links?.[name] : undefined;
		const type = escapeTableText(referenceType(field));
		const typeText = /^[a-z]+$/.test(type) ? type : `\`${type}\``;
		const defaultText = field.default === undefined ? "" : `\`${escapeTableText(JSON.stringify(field.default))}\``;
		const description = [schema.required?.includes(name) ? "Required." : undefined, field.description]
			.filter((text) => text !== undefined)
			.join(" ");
		rows.push(
			`| \`${path}\` | ${link ? `[${typeText}](${link})` : typeText} | ${defaultText} | ${escapeTableText(description)} |`,
		);
		// !mark(1:3)
		if (link || (prefix === "" && section.collapsed?.includes(name))) continue;
		const nested = documentedObject(field);
		if (nested) rows.push(...referenceRows(nested.schema, section, `${path}${nested.suffix}.`));
	}
	return rows;
}
```

## !!steps Rendering and the staleness test

`renderReference` assembles the page: the title, an HTML comment saying the file is generated, the intro, then each section's heading, intro and table. A heading that already starts with `#` is used as is, which is how the per-API compatibility sections become level-three headings under "Compatibility".

As in generate-schemas.ts, rendering returns a map of paths to contents for the test, and the files are written only when the script is run directly.

```ts ! generate-references.ts
function renderReference(artifact: ReferenceArtifact): string {
	const blocks = [`# ${artifact.title}`, `<!-- ${generatedComment} -->`, artifact.intro];
	for (const section of artifact.sections) {
		// !mark
		blocks.push(section.heading.startsWith("#") ? section.heading : `## ${section.heading}`);
		if (section.intro) blocks.push(section.intro);
		if (section.schema) {
			const rows = referenceRows(section.schema as ReferenceSchema, section);
			blocks.push(["| Field | Type | Default | Description |", "|---|---|---|---|", ...rows].join("\n"));
		}
	}
	return `${blocks.join("\n\n")}\n`;
}

export function renderReferences(): ReadonlyMap<string, string> {
	return new Map(referenceArtifacts.map((artifact) => [artifact.path, renderReference(artifact)]));
}
```

</Scrollycoding>

The design is general, a list of artifacts each with sections, but only the models reference uses it so far. Settings and keybindings have schemas with descriptions too, and adding a reference for them would mean adding an artifact here rather than writing a new renderer.
